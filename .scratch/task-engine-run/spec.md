# Spec: 把任务启动仪式收进任务引擎

Status: ready-for-agent

## Problem Statement

后台**任务**的启动、进度上报与收尾，今天由 17 个启动点各自手抄同一套五步流程：申请任务槽位 → 写元数据 → 写并发上限 → 建可取消可暂停的上下文 → 起后台 goroutine 并在其中手写「取消 / 失败 / 完成」三条收尾分支。

这带来三类可观察的损害：

**对维护者。** 这套流程的正确性完全依赖「抄对」。代码里已经留下了事故记录：某个启动点曾多套了一层 goroutine，导致停机竞态下该任务被静默丢弃、且已登记的运行时句柄泄漏在内存里；修复注释写的是「与其余 34 个调用点保持一致」——也就是说 35 个调用点的正确性没有任何结构性保障。加一个新任务类型，要在四五个地方复制同样的骨架，漏掉任何一步都不会有编译错误。

**对终端用户。** 同一套流程被抄了 17 遍，行为就不一致：外部库传输自带一套手写的 500ms 进度节流，与引擎自身的节流水位并存且更粗，还丢掉了「阶段名变化必须立刻推送」这条规则，于是任务气泡会长时间停在过期的阶段名上。ComicInfo 回写因为还停在字面量文案接口上，它的启动与完成文案是硬编码中文，英文用户在任务中心看到的是中文。

**对测试。** 任务引擎的接口是三条轴交叉出来的约 25 个方法：可取消/可暂停、i18n 消息码/字面量文案、简单进度/详细进度。其中一整支（字面量文案版）在测试里被调用 76 次、在生产代码里只剩 5 处残留（集中在 ComicInfo 回写，其文案还是硬编码中文，英文用户也看到中文）——绝大多数用例在验证一条生产几乎不走的路。而生产真正走的那条路上，有几条不变量至今零覆盖：任务体 panic 后是否被置为失败态、运行时句柄是否在每条退出路径上都被清理。

## Solution

任务引擎对外只暴露**一个**启动入口：调用方提交一份任务声明和一个任务体，引擎负责其余全部——槽位闸门、上下文、后台 goroutine 的生命周期、进度节流、三条终态分支、以及 panic 兜底。

任务体只做两件事：干活，以及报告「做完了多少」（**计数推进**）和「在做什么」（**阶段**）。任务体不再接触任务键，不再自己判断终态，不再自己起 goroutine。

调用方视角的变化：

- 启动一个任务从「五次调用 + 一个手写三分支的闭包」变成「一次调用」。
- 「做完了多少」和「在做什么」成为两个独立的动作，不再被塞进同一个九参数方法，「别动总数」的哨兵值随之消失。
- 消息词汇只剩 i18n 码一种；字面量文案的入口整支删除。
- 「谁有资格写某个任务的进度」从「谁会拼那个任务键字符串」变成「谁被交给了进度句柄」。

## User Stories

1. 作为维护者，我希望启动一个后台任务只需要一次调用，这样我不必记住五步顺序，也不会漏掉其中一步。
2. 作为维护者，我希望任务体只需要返回错误，由引擎决定进入哪个**终态**，这样「取消」「失败」「**完成**」三条分支不再被手抄 17 遍。
3. 作为维护者，我希望后台 goroutine 的申领与停机登记由引擎统一完成，这样「多套一层 goroutine 导致任务被静默丢弃」这类缺陷在结构上写不出来。
4. 作为维护者，我希望**运行时句柄**的清理由引擎保证，这样我不必在每条退出路径上手写延迟清理，也不会因为漏写而泄漏。
5. 作为维护者，我希望任务体 panic 时任务必定被置为失败态，并且这条路径有用例覆盖，这样服务不会因为一个后台任务而进入「任务永远停在运行中」的状态。
6. 作为维护者，我希望**任务键**由引擎绑定进进度句柄，这样任务体内部不再重复出现同一个字符串（今天某个任务体里出现 8 次）。
7. 作为维护者，我希望「**计数推进**」和「**阶段**」是两个独立的方法，这样我播报阶段时不必编造凑数的计数值。
8. 作为维护者，我希望「不改变总数」通过「调用另一个方法」来表达，而不是通过传 `-1` 这个必须先知道才能用对的哨兵值。
9. 作为维护者，我希望消息词汇只有 i18n 码一种，这样不会再出现「生产走一支、测试走另一支」的分裂。
10. 作为维护者，我希望终态文案的默认值写在任务声明里、而变体（如「部分成功」「目标为空」「第一阶段失败」）由任务体在返回时指定，这样常规任务不必为收尾写任何代码，特殊任务也不被迫走通用路径。
11. 作为维护者，我希望启动入口返回错误而不是布尔值，这样「同类任务已在运行」这个原因不会在门口丢失，**重启函数**也不必把布尔值再转换回哨兵错误。
12. 作为维护者，我希望缩略图重建任务的进度写入资格是一个被交给我的句柄，而不是一个谁都能拼出来的字符串，这样「哪些代码能改这个任务」有了结构约束。
13. 作为维护者，我希望缩略图重建那四处外部进度写入点不再各自判断「重建是否在进行中」，因为「有没有拿到进度句柄」本身就是这个判定。
14. 作为维护者，我希望进度节流只有一处实现，这样我不必在新的长任务里判断「要不要自己再加一层节流」。
15. 作为维护者，我希望为任务引擎写用例时不需要数据库、配置管理器、归档池和扫描器，这样一个契约用例是毫秒级而不是秒级。
16. 作为维护者，我希望能注入一个同步执行的后台运行能力，这样任务的终态分支可以被确定性地断言，而不是靠等待真实 goroutine。
17. 作为维护者，我希望测试往任务表里放一条任务有一个专门的辅助方法，且它建立在真实的启动路径之上，这样「同一个**任务键**同时只能有一个**活动态**任务」这道闸门在测试中仍然被覆盖。
18. 作为终端用户，我希望所有长任务的进度推送节奏一致，这样任务气泡不会在某些任务上明显更迟钝。
19. 作为终端用户，我希望**阶段**名变化时立刻看到更新，即使计数还没推进，这样我知道任务正在往前走而不是卡住了。
20. 作为终端用户，我希望后台任务失败时明确显示为失败并可重试，而不是停在运行中不动。
21. 作为终端用户，我希望取消一个任务后它明确进入「已取消」终态，无论它此前处于哪个**阶段**。
22. 作为终端用户，我希望**暂停闸门**在所有长任务上行为一致——按下暂停后任务停在下一个可中断点而不丢失已完成的工作。
23. 作为 AFK agent，我希望新增一个任务类型时只需要写任务声明和任务体两样东西，这样我不会遗漏那些没有编译期约束的步骤。
24. 作为 AFK agent，我希望任务引擎的接口小到可以完整读进上下文，这样我在修改任务相关代码时不必先通读一个两千行的文件。

## Implementation Decisions

### 深化后的模块与接口

**模块**：任务引擎（`internal/api` 内的任务子域）。它今天已经独占任务子域的全部可变状态与锁，本次把「一个任务从启动到终态」的完整生命周期也收进来。

**新增第四个装配期注入依赖**：一个「开一个受停机管辖的 goroutine」的能力。引擎此前已注入三样（落盘用的存储、SSE 投递、停机信号），这是第四样。全仓库仅有两个构造点（生产装配处与一处引擎白盒测试），因此这是两行改动。

**接口形状**（下列类型形状来自本次盘问，比散文更精确地编码了决定，故内联）：

```go
type TaskSpec struct {
    Key, Type   string
    StartCode   string              // 起始文案的 i18n 码
    Params      map[string]string
    Total       int
    CanCancel   bool
    CanPause    bool
    Metadata    map[string]string   // 原独立的元数据写入
    ScopeName   string
    Limits      TaskLimits          // 原独立的并发上限写入
    CompleteCode, CancelCode, FailCode string   // 三条终态分支的默认文案码
}

type TaskResult struct {
    Code   string              // 覆盖 TaskSpec 里对应分支的默认码；零值表示用默认
    Params map[string]string
}

func (e *taskEngine) Run(spec TaskSpec,
    fn func(ctx context.Context, tp *TaskProgress) (TaskResult, error)) error

func (tp *TaskProgress) Advance(current, total int, code string, params map[string]string)
func (tp *TaskProgress) Stage(phase, code string, params map[string]string)
func (tp *TaskProgress) Metrics(m map[string]int64)
func (tp *TaskProgress) Item(name string)
```

### 关键决定

1. **启动入口挂在任务引擎上**，而不是新建一个组合模块、也不是留在 HTTP 控制器上。理由：控制器今天已经反向伸手进引擎写失败态（panic 兜底那条路），把后台运行能力改为注入之后方向理顺——引擎向外索取能力，而非外部伸手进来改任务表。

2. **任务体单出口**：返回 `(TaskResult, error)`。不提供「任务体自行调用收尾方法」的第二条路径——那正是要消灭的隐式约定。引擎按错误决定分支：`nil` → **完成**；`context.Canceled` → 已取消；其余 → 失败。

3. **领域副作用留在任务体内**，不做成任务声明上的成功/失败钩子。引擎负责状态机与文案，任务体负责缓存失效、预热、串联后续任务等领域动作。

4. **任务体收两个参数**：`ctx` 保持为纯粹的 `context.Context`（既有的扫描、同步、**暂停闸门**调用一律不改），进度句柄单独作为第二个参数并已绑定**任务键**。

5. **进度接口按真实用途切开**。实测 28 处进度调用里约 15 处是真计数推进、约 12 处是**阶段**播报（计数值是凑数的，其中 3 处依赖 `-1` 哨兵表示「别动总数」）。切开后哨兵值消失。

6. **字面量文案那一整支删除**：起始、进度、失败、完成的非 i18n 版本全部移除。生产侧仅存 5 处调用点（外部库扫描、缩略图清理各一处，ComicInfo 回写三处），随各自所属的迁移批次转走；ComicInfo 回写因此需要新增两个语种的文案键，是唯一一处非机械的迁移。

7. **测试脚手架用专门的辅助方法**，且必须建立在真实启动路径之上（而非直接写内存表），以保留「同键同时只能有一个活动态任务」这道闸门的覆盖。

8. **缩略图重建的进度句柄由任务体交给聚合器**。这是唯一一个进度由任务体**之外**写入的任务——它的写入者是扫描器的 goroutine，不在任务体调用栈上。资格因此从「拼字符串」变为「持有句柄」，并顺带消除四处重复的「重建是否在进行中」判定。

9. **启动入口返回 `error`**，`nil` 表示已启动，沿用既有的「同类任务已在运行」哨兵错误。16 个独立的启动函数今天有三种返回形状（布尔 5 个、错误 9 个、`(任务键, 布尔)` 2 个；第 17 个启动点内联在 ComicInfo 回写的 handler 里，直接回 409），统一为错误；需要回传任务键的两处直接使用自己写进声明里的键。

10. **保持不变的不变量**：启动闸门同步执行、任务体异步执行——启动入口返回时任务体尚未运行，HTTP 层才能立即返回 202。

11. **外部库传输手写的 500ms 节流删除**，改由引擎统一的节流水位承担。引擎的水位除时间外还记录已发布的展示态，**阶段**或文案跃迁不会被吞。

12. **不改动**：**重启函数**注册表（见 ADR-0001）、SSE 投递组件、节流水位的判定规则、任务快照的落盘结构与线上契约。

### 迁移

分批提交，但老接口的删除必须落在**同一个 PR** 内。理由：本仓库接口里现存的「i18n 码版 / 字面量版」这条轴，就是一次停在半路的迁移冻结进签名的产物；用同样的方式收尾只会再造一条相同的疤。

提交顺序：

1. 启动入口、任务声明、进度句柄、测试脚手架辅助方法，加契约用例；只转换资料库扫描任务（最典型的形状）。
2. **缩略图重建任务**——最难的一个排第二位，而不是留到最后。它是这套形状的证伪点：如果进度句柄的所有权模型不成立，要在第二个提交就暴露，而不是在转换完十几个之后。它同时门控其余全部迁移批次——这是刻意牺牲并行度换来的。
3. 其余按子域分批转换，其中 ComicInfo 回写需一并补齐两个语种的文案键。
4. 删除字面量文案家族与旧的启动/收尾方法；测试脚手架统一改用辅助方法。

## Testing Decisions

**什么是好测试**：只断言外部可观察的行为——投递出去的任务状态载荷、启动入口的返回值、任务体是否被执行。不断言内部字段布局、不断言方法调用次数、不断言锁的持有情况。

**唯一的新 seam**：任务引擎的启动入口，经由已有的引擎构造点注入依赖。这不是凭空新增——该构造点今天已是本包最窄的注入面（全仓库两个调用点），且已有用例在其上做无数据库、无配置、无扫描器的确定性测试。本次只是多注入一样能力。

**契约用例**（全部在这一个 seam 上，注入同步执行的后台运行能力 + 可控时钟 + 捕获式投递）：

- 三条终态分支：任务体返回 `nil` → **完成**；返回取消错误 → 已取消；返回其它错误 → 失败。
- `TaskResult` 中的文案码覆盖任务声明里的默认码；零值时使用默认码。
- 同一**任务键**已有**活动态**任务时，启动入口返回「已在运行」哨兵错误，**且任务体不被执行**。
- 无论任务体走哪条退出路径，**运行时句柄**都被清理。
- **任务体 panic → 任务置为失败态**（今天零覆盖）。
- **计数推进**与**阶段**播报分别只影响各自的字段;**阶段**跃迁不被节流水位吞掉。
- 缩略图重建的进度句柄交接：启动一个任务、把句柄交给聚合器、驱动聚合器、断言投递出去的载荷。**不为此新增第二个 seam。**

**不新增的 seam**：17 个启动点各自的行为继续走既有的控制器级用例；**重启函数**注册表与 SSE 投递组件的用例不动。

**先例**：本包已有的任务进度节流用例——它用三个注入依赖加一个假时钟构造引擎、断言投递次数与时序，是本包最快也最精确的一组用例。契约用例照它的形状写。

**回归面**：既有的 76 处任务脚手架调用改走辅助方法，用法本身不变;引擎白盒用例的构造调用需补第四个参数。

## Out of Scope

- **重启函数注册表**。它已是深化过的产物（取代了两份需手工同步的硬编码清单），且 ADR-0001 记录了它为什么不能由任务声明携带。本次零改动。
- **SSE 投递组件**与**节流水位的判定规则**。前者已是干净的深模块，后者的取值与规则有充分的成文依据。
- **SSE 载荷的类型契约**（今天发出 7 种事件、前端只认 2 种）。这是另一条候选，独立于本次。
- **存储令牌 / 暂停闸门的取用仪式**（今天在 9 个工作点被手抄）。它天然嵌在任务体内部，是本次之后的下一步，不在本次范围。
- **HTTP 控制器的其余部分**：域逻辑外迁、权限模型、缓存布局。
- **任务快照的落盘结构、线上 SSE 契约、前端任何代码**。两处例外是刻意的对外行为变更，各自在所属批次里单独验证：外部库传输的推送节奏变准（阶段跃迁不再被吞）、ComicInfo 回写的文案从硬编码中文改为按语种渲染。
- **服务重启中断提示的国际化**。现存缺陷：该提示文案硬编码为中文、无 i18n 码，英文用户也会看到中文;前端另有一条按中文子串匹配来反推**中断**的兜底判定。已记录，另行处理。

## Further Notes

- 词汇以仓库根部的领域词汇表为准。特别注意其中钉死的两处：**终态**共四种（完成 / 已取消 / 失败 / **中断**），「完成」只指其中一种，不得用于泛指;**中断**不是失败，它是服务重启时活动态任务被转入的终态，可重试。今天代码里用「完成」这个词写入「已取消」终态的那 25 处，正是本次要消除的模糊。
- **取消中**属于**活动态**：取消已请求但任务体尚未收尾时，同一**任务键**不得再次启动。这条不变量在改造后必须继续成立。
- 引擎中「带出临界区的任务快照必须先克隆」这条约定不受本次影响，但任何新增的取快照路径都必须遵守——违反的后果是运行时 throw，`recover` 与 HTTP 中间件都拦不住。
- 本次改造的度量：启动相关接口从约 25 个方法收到 3 个;17 处手抄的五步流程归零;25 处「以已取消终态收尾」的调用归零;3 处手写节流归 1;`-1` 哨兵消失;新增 5 条此前无法覆盖的不变量的用例。
