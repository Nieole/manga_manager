# 11 — 队列、合并与槽位上限

**What to build:** 冲突不再丢弃。同一个任务已有活动运行时，后来者进**排队中**；已经有一条排队的，
再来的**合并**进那一条并计数。槽位占用在实况区可见，全局并发上限可配（默认 2）。

**Blocked by:** 10

**Status:** done

## 三条规则

1. **排队**：同一任务已有活动运行 → 新发起进排队中，不再返回「已在运行」。
2. **合并**：已有一条排队中的运行 → 不新建，并进那一条，`coalesced_count` 加一。
   守护扫描要的只是「确保扫过」，合并与各排一条效果相同，而后者会堆成一串一模一样的运行。
3. **槽位**：全局同时运行数不超过上限，超限的留在排队中等放行。

## 槽位按单一全局数字，不按卷（ADR 0005，知情取舍）

按 `storageio` 的卷键限更贴近真实瓶颈——两个库在两块盘上本可以并行——但一个数字更好解释、
界面上也画得出「槽位 2/2」。**代价是多盘用户会看到一条运行在排队，而它要等的那块盘是空的。**
这条已被裁定并接受，实现时不要顺手改成按卷。

## 边界

- **排队中的运行可以取消**，取消后进已取消。它从未占过槽位，因此不必结算暂停时长。
- 排队中**不是活动态**：它不占槽位，但**永不被保留裁剪带走**（票 18 会用到这条）。
- 上限从运行时配置读，改配置后对**新的放行**生效，不打断已经在跑的。
- 合并计数要能在界面上看见（「已合并 2 次」），否则用户不知道那条排队代表了几次发起。
