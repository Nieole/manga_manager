# 07 — 引擎接线到新模型

**What to build:** `api` 的任务引擎内部换成 `internal/task` + `taskstore`，运行落进新表。
**重试从此不再抹掉上一次**——用户在任务中心开始看到同一个任务的多条运行。对外 JSON 形状与启动入口
签名**暂不变**，前端仍是平铺列表，因此 17 个启动点不必改。旧 `tasks` 表并存但不再被写入。

**Blocked by:** 04, 05, 06

**Status:** ready-for-agent

## 这一票是整批的接线点

它把票 05 的领域包、票 06 的表和票 04 已经显式声明的身份四要素接到一起。**旧表刻意留着**：
接线出问题时数据还在，回滚只是把装配换回去。删除留给票 08。

对外形状不变意味着：列表接口仍返回今天那个形状的数组，只是同一个任务键可能出现多条（各是一次运行），
每条多带一个运行标识。前端不改也能工作——它今天就是按数组渲染的。

## 一并接上的两样

- **运行标识进日志。** 票 02 已经把任务键放进任务 ctx 并由 handler 附加；本票在同一个 handler 上
  加上运行标识。**不要新开第二条通道。**
- **任务身份的懒建。** 启动时按四要素查身份，没有就建一条。身份行上的禁用与退避字段本票只建不读，
  它们的行为属于票 14。

## 必须逐处确认的

- **内存表的角色变了。** 今天内存表是活动任务的唯一可写副本，且列表要把它与 DB 合并。准入下沉到
  数据库之后，这层合并还要不要留、留多少，本票要给出答案并写进包 doc——不要两处各存一份真相。
- **异步落盘与清除的串行**（先内存后库、`persistMutex` 的嵌套顺序）这条既有约束要么原样继承、
  要么在新形状下重新论证。它防的是「删掉的行被在途的写回来」。
- **投递水位在终态时清掉**这条要继承：同名任务重跑时首帧必须无条件放行。
