# 18 — 分层保留与清理运行

**What to build:** 运行历史自动清理，清理本身也是一条可见的**串联**运行。这套设计因此能跑过一年。

**Blocked by:** 12

**Status:** ready-for-agent

## 为什么这不是优化

按 5 个库、每小时一次守护扫描粗算：

| | 每天 | 每年 |
| --- | --- | --- |
| 运行 | ~120 行 | ~44,000 行 |
| **运行事件** | ~1,200 行 | ~44 万行 |
| **采样**（10s 一次） | ~7,000 行 | ~260 万行 |

这是个单机 SQLite。**不定保留策略，这套设计跑一年会自己把自己压垮。**

## 分层

| 对象 | 保留 |
| --- | --- |
| 运行 | 每任务最近 20 次，且**终态**运行 ≤90 天，取先到者 |
| 事件 | 随运行级联删 |
| 采样 | ≤7 天（运行还在，曲线没了） |

**活动态与排队中的运行永不被带走。** 三个阈值可在设置里改。

## 清理自己是一条运行

每天跑一次，发起方「串联」，在任务中心可见——它什么时候跑的、清了多少有据可查。
它是**可续跑**的，但它自己产生的运行也受同一套保留策略约束，不要给它开特例。

清理不得清掉自己正在跑的那一条。

## 验收

- [ ] 三层保留按阈值执行，SQL 侧的选中集合用例见票 06
- [ ] 活动态与排队中的运行永不被清
- [ ] 清理是一条可见运行，每天一次，发起方串联
- [ ] 清理不清掉自己正在跑的那一条
- [ ] 三个阈值可配，改配置下一次清理即生效
- [ ] 清理运行报出清了多少（运行数、事件数、采样数）
