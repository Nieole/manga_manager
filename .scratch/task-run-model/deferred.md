# 挂账清单 · task-run-model

跑票过程中冒出的非阻塞选择。流程不为它们停；由用户挑时机逐条处理。

## D1 · 票 05 · 作用域 id 用 `int64` 零值表示「没有」，还是 `*int64`

- **问：** 身份四要素里的作用域 id 今天在 `api.TaskStatus` 上是 `*int64`（JSON 侧要 omitempty）。
  领域包改成了 `int64`，0 表示系统级没有作用域对象。理由是身份的唯一约束要比较这一列，
  而 SQL 里 NULL 不等于 NULL——留 NULL 的话同一个系统级身份会被建出任意多条。
- **选项：** A `int64` + 0 表示没有（推荐，唯一约束天然成立，`Identity.Validate` 顺带把
  「系统级不得带 id」与「库级必须带 id」两条判掉）｜ B `*int64`，由 `taskstore` 在写入时 coalesce 成 0，
  代价是那条 coalesce 漏掉一处不会有编译错误
- **不处理会怎样：** 已按 A 落地。票 06 建表时 `scope_id` 应为 NOT NULL DEFAULT 0，
  接线时 api 的 DTO 要在边界上做一次 0 ↔ nil 的转换。
- **状态：** open

## D2 · 票 05 · 运行的展示标签落在哪张表

- **问：** 规格的表形状列了六张表（runs / run_events / run_samples / run_metrics / run_limits / run_args），
  没有标签的去处；而 `RunSpec.Labels` 与 `taskrun.Frame.Labels`（刮削源名等）今天确实存在，
  它们既不是重启入参也不是指标。领域包为此在端口上开了 `MergeRunLabels`。
- **选项：** A 单开一张 `run_labels`（推荐，与「五类语义各回各家」一致，读回时不必按前缀分拣）｜
  B 并进 `run_args`，靠键前缀区分，代价是那张表重新混进两类语义——这正是 `params` 堆的成因｜
  C 判定标签属于展示态、升为 `runs` 的定长真列，代价是加一个标签要改 schema
- **不处理会怎样：** 票 06 已按 A 落地：`run_labels` 单开一张。改成 B 只动适配器一侧，
  领域端口不动；但两类语义会重新同居一个命名空间。
- **状态：** open

## D3 · 票 05 · 落盘是同步写端口，还是承接今天那条异步落盘 goroutine

- **问：** 今天的引擎有一条 500ms 节流的落盘 goroutine（待写集合按键合并、终态唤醒立即刷、
  停机前再刷一次），它防的是「在临界区里同步写 SQLite 阻塞任务 API」。领域包对着的是一个端口，
  纯内存下这套机械没有意义，因此本票写成了同步调用。票 07 的验收里点名要重新论证这条。
- **选项：** A 领域同步写，节流与批量交给 `taskstore` 适配器（推荐，领域层因此没有「待写集合」这类
  与规则无关的状态，票 07 只需在适配器一侧决定怎么攒批）｜ B 把异步落盘原样搬进领域包，
  代价是端口多一条「刷盘」语义，而纯内存用例要为它另写一套等待
- **不处理会怎样：** 已按 A 落地。票 07 接线时若发现同步写真的压着任务 API，
  要在适配器里加节流，而不是把它加回领域层。
- **状态：** open

## D4 · 票 05 · 控制能力（可暂停 / 可取消 / 可恢复）落不落列

- **问：** 今天这三个布尔值是 `tasks` 表的真列。规格的新表形状里没有它们，而它们的事实来源是
  「这条运行的**暂停闸门**此刻还在不在」——闸门活在进程里。领域包因此把它们做成了
  `Capabilities`，由引擎按运行的活性派生，随快照一起投递。
- **选项：** A 派生、不落列（推荐，落成列的话重启后那几个布尔值会集体说谎：库里写着可暂停，
  而闸门早已随进程消失）｜ B 落成 `runs` 的列，读回时再按活性覆盖一遍，代价是同一件事有两个来源
- **不处理会怎样：** 已按 A 落地。票 07 接线时 api 的 DTO 要从 `Snapshot.Capabilities` 取这三个值，
  而不是从运行行上读。
- **状态：** open

## D5 · 票 05 · **排队中**运行的开始时刻留零值

- **问：** 排队中的运行还没开跑，`started_at` 写什么。领域包留零值，等它真的进入运行中才写——
  写入队时刻的话，排了一小时队的运行会被算成跑了一小时，速率与 ETA 一路失真。
- **选项：** A 留零值，放行时补写（推荐，速率的分母因此只包含真的在跑的那段）｜
  B 写入队时刻，另加一列记真正的开跑时刻，代价是多一列且两列的语义要靠命名区分
- **不处理会怎样：** 已按 A 落地。票 06 建表时 `runs.started_at` 必须可空（或接受零值），
  不能加 NOT NULL 且无默认。
- **状态：** open

## D6 · 票 05 · `taskrun` 的包 doc 仍把句柄的归属写作 api 的任务引擎

- **问：** `internal/taskrun` 的 package doc 写着「句柄由 api 的任务引擎构造并交给任务体」，
  而票 07 接线之后构造它的是 `internal/task` 的引擎。本票隔离在 worktree 里、不改现有文件，
  因此没有动它。词汇上「任务句柄」也该随规格改名为**运行句柄**。
- **选项：** A 留给票 09 的符号对齐一并改（推荐，那一票本来就要改名与重生成契约）｜
  B 票 07 接线时顺手改，代价是改名散在两票里
- **不处理会怎样：** 过渡期内那段包 doc 指着一个即将不成立的归属。
- **状态：** open

## D7 · 票 05 · 落盘端口只有写入面，**运行事件**的读取与计数还没有去处

- **问：** 票 05 只要求端口容得下「将来的**写入**」，因此端口上只有 `AppendRunEvents` 与
  `AppendRunSamples`。票 16 的「条目失败每次运行最多留 500 条，超出只累加计数并落一条
  『还有 N 条未列出』」要先问一句「这条运行已经存了几条 item 事件」，那是读，端口今天答不出。
- **选项：** A 等票 16 落地时按它真正要的形状加读取方法（推荐，读取面的分页与筛选口径由详情页
  决定，现在猜出来的签名多半要改）｜ B 本票就加一个 `CountRunEvents(runID, kind)`，
  代价是端口多一个没有实现也没有调用方的方法
- **不处理会怎样：** 票 16 要往端口上加方法。票 05 的验收没有欠账——它只要求容得下写入。
- **状态：** open

## D8 · 票 05 · `AGENTS.md` 的 `internal/*` 包清单漏掉 `internal/task`

- **问：** `AGENTS.md` 的 Project Structure 一节逐个点名了 `internal/*` 下的包，新建的
  `internal/task` 不在其中；票 06 的 `internal/taskstore` 落地后同样会缺。这是共享文件，
  本票按隔离纪律没有动它。
- **选项：** A 等两个新包都落地后一次性补进去（推荐，一次改动补齐两个名字）｜
  B 每建一个包就改一次，代价是共享文件在批次里被反复碰
- **不处理会怎样：** 清单少两个包名，新来的 agent 得自己 `ls internal/` 才知道它们存在。
- **状态：** done（票 07 按 A 补上，两个包都落地了，同一句话里一起加）

## D9 · 票 06 · 身份表在过渡期不能叫 `tasks`

- **问：** 规格的表形状把身份表写作 `tasks`，而旧引擎那张同名表此刻仍在被读写，
  票 07 的验收还要求它「并存但不再被写入，也未被删除」。同一个库里两张同名表不可能并存，
  改名旧表会当场打断正在跑的旧引擎。本票因此把身份表建作 `task_identities`。
- **选项：** A 票 08 丢弃旧表时顺手 `ALTER TABLE task_identities RENAME TO tasks`（推荐，
  最终名字与规格、ADR 0004 与领域类型 `task.Task` 对齐；SQLite 会一并改写 `runs` 上那条外键引用）｜
  B 永久留作 `task_identities`，代价是库里的表名与规格的表形状对不上
- **不处理会怎样：** 票 08 不做这一步就等于选了 B。表形状、四列唯一约束与两条部分唯一索引
  在两种选择下完全一样，改的只是一个名字。
- **状态：** open

## D10 · 票 06 · i18n 占位参数落成 `runs` 的一列，还是自己一张侧表

- **问：** 规格写「i18n 占位参数随 `message_code` 落在 `runs` 上」，而 `Run.MessageParams` 是一张
  `map[string]string`，表形状里没有给它列。本票落成 `runs.message_params` 一列，内容是 JSON 对象。
- **选项：** A 落成 `runs` 的一列（推荐，与 `message_code` 同行整份改写，进度帧的热路径上不多两条语句；
  它不是 ADR 0004 否掉的那个堆——那个堆挤着五类语义且指标不可聚合，这一列只装一类且从不参与查询）｜
  B 单开 `run_message_params(run_id, key, value)`，与另外四张侧表同形，代价是每次文案变化都要
  先删后插，而那是逐条目进度在走的路
- **不处理会怎样：** 已按 A 落地。改成 B 只动 `taskstore` 一侧，领域端口不变。
- **状态：** open

## D11 · 票 06 · 时间列存 epoch 毫秒而不是 `DATETIME` 文本

- **问：** 新表的每一个时刻都存整数毫秒，与仓里既有表的 `DATETIME` 文本列不同。
  理由是保留裁剪的 DELETE 与聚合查询都要拿时间列做比较，而本仓已经吃过「两个写入方写出两种文本
  格式、SQLite 比的却是文本」的亏。
- **选项：** A 存整数毫秒（推荐，比较与聚合没有歧义，也不必再为时区与格式各写一个规范化函数）｜
  B 与既有表一致存文本，由 `taskstore` 保证只有一个写入方、只用一种格式，代价是那条保证没有任何
  机制守着
- **不处理会怎样：** 已按 A 落地。代价是直接用 sqlite CLI 翻这几张表时要自己换算时刻。
- **状态：** open

## D12 · 票 06 · 新表不推 `currentSchemaVersion`

- **问：** 建表语句是幂等的 `CREATE TABLE IF NOT EXISTS`，不带任何回填，因此本票没有把
  `internal/database` 的 `currentSchemaVersion` 加一——那个版本号门控的是随库规模线性增长的全量重算
  （系列首字母、统计、标签计数、来源、FTS 重建），为几张空表推一次会让每个存量库白算一遍。
- **选项：** A 不推，靠幂等 DDL 每次启动重放（推荐，与 KOReader 账号、书签用户隔离那两次的做法一致，
  也与那个常量自己的注释一致：「新增需要全量回填的 schema 变更时才 +1」）｜
  B 推一版当作 schema 变更的记号，代价是全体存量库在升级后的首启多跑一轮全量回填
- **不处理会怎样：** 已按 A 落地。票 08 丢弃旧表时若要推版本，那是它自己的决定，与本票无关。
- **状态：** open

## D13 · 票 06 · 侧表只有写入面，入参与上限的读回还没有去处

- **问：** 端口对四张键值侧表只声明了写入（`MergeRunArgs` / `MergeRunLabels` / `SetRunMetrics` /
  `AddRunMetrics` / `SaveRunLimits`），没有任何读回。而**重启函数**要读回原始入参、运行详情页要读回
  标签与当时生效的上限。D7 记的是**运行事件**那一半，这是键值侧表这一半。
- **选项：** A 等票 07（重启入参）与票 16/17（详情页）各自按真正要的形状往端口上加（推荐，
  读取面的形状由消费方决定）｜ B 本票就把四个读取方法加上，代价是端口多出一批没有调用方的方法
- **不处理会怎样：** 已按 A 落地：`taskstore` 今天只实现端口声明的写入面，聚合查询另有
  `AverageRunDuration` 与 `SumRunMetrics` 两个本包自己的方法。
- **状态：** open

## D14 · 票 06 · `AGENTS.md` 说 SQL 来源只有 `sql/query.sql` 与 `schema.sql`

- **问：** `AGENTS.md` 的 Project Structure 一节写着「SQL sources are in `sql/query.sql` and
  `internal/database/schema.sql`」，而任务与运行那几张表的 DDL 在 `internal/taskstore/schema.go` 的

- **选项：** A 与 D8 一并补进 `AGENTS.md`（推荐，同一节、同一次改动）｜
  B 把 DDL 挪进 `schema_handwritten.sql`，代价是表结构与它的迁移分居两个包
- **不处理会怎样：** 照那句话去找表的人找不到 `runs`，得先 `grep CREATE TABLE`。
- **状态：** done（票 07 按 A 补上，与 D8 同一次改动）

## D15 · 票 06 · `internal/database` 反过来依赖 `internal/taskstore`

- **问：** 新表的建表语句由 `database.Migrate` 调 `taskstore.Migrate` 落地，于是 `database` 依赖了
  `taskstore`，而仓内其余方向都是别人依赖 `database`。挂在这里是因为 `Migrate(dbPath)` 是全仓唯一的
  迁移入口，挂别处就得靠每个调用方记得再调一次，而 `internal/database` 自己的用例也拿不到新表。
- **选项：** A 留在 `database.Migrate`（推荐，迁移只有一个入口，忘不掉）｜
  B 由装配期（`cmd/server`）依次调两个 Migrate，`database` 因此不认识 `taskstore`，
  代价是新增入口时要记得补第二条调用，且 `internal/database` 的用例里没有新表
- **不处理会怎样：** 已按 A 落地。票 07 接线时若把 `taskstore` 的构造挪进装配期，可以顺便重看这条。
- **状态：** open

## D16 · 票 04 · **变体**落盘走任务参数还是给老表加一列

- **问：** 身份四要素里类型、作用域、作用域 id 三项都是 `tasks` 表的真列，**变体**没有。本票让它随
  任务参数（`params` TEXT）落盘再读回，理由是这张表随票 08 整表丢弃，而加一列要动 `schema.sql`、

- **选项：** A 维持随任务参数走（推荐，因为这张表两票之后就没了，而新表本来就有 variant 列）｜
  B 现在就加 `variant` 列并写迁移，让四要素在老表上也齐整
- **不处理会怎样：** 已按 A 落地。升级前落下的刮削与书哈希重建历史行读不回变体，
  `taskStatusFromRecordLive` 会按当前注册表把它们算成不可重试——界面上那个重试按钮消失（而不是

- **状态：** open

## D19 · 票 02 · 任务体路径上的日志调用形状

- **问：** 票据的边界写着「不要为此改任何一处 `slog.Info/Warn/Error` 的调用形状」，但 Go 的 slog
  包级函数把 `context.Background()` 传给 handler——ctx 里的任务键因此永远到不了 `Handle`。要让
  handler 读得到，调用点必须改成 `slog.InfoContext(ctx, …)` 一族。同一条边界的另一句
  （「scanner 的日志在跑在任务 ctx 上时同样应当带上，守护/watcher/首扫那几条路径仍不带」）
  反过来要求调用点认 ctx：同一段代码带不带只由跑在谁的 ctx 上决定，只有带 ctx 的调用做得到。
- **选项：** A 三类任务走到的日志改成带 ctx 的形式（已落地）｜ B 全仓一次改齐，让「写日志用带 ctx
  的调用」成为无例外的仓内惯例｜ C 放弃 ctx 通道，改用 goroutine 局部存储读当前任务键——Go 没有
  官方支持，只能靠解析 `runtime.Stack` 或 `//go:linkname`，而且扫描器的 worker 是子 goroutine、
  继承不到
- **已按 A 改到的地方：** `internal/scanner`（扫描三阶段、封面 worker、软链遍历、收尾指标行）、
  `internal/metadata`（各 Provider 的搜索与上游失败）、`internal/images`（转码告警）、
  `internal/diskwork`（等令牌等太久那条）与 `internal/api` 的任务体。**其中两处不只服务任务**：
  `images.ProcessImage` / `ProcessImageDetailed` 是导出签名，前台阅读取页也从那儿走（那条路径
  永远取不到任务键，只是跟着改了形参）；`metadata` 各 Provider 的 `SearchMetadata` 同时服务
  交互式搜索端点。
- **不处理会怎样：** 已按 A 落地，代价是仓里两种调用形状并存：任务走到的认 ctx、请求处理与后台
  常驻那些不认。新写的日志落在哪一侧没有编译期约束，写错的后果是那一行在「查看日志」里过滤不到
