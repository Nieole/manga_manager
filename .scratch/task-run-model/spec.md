# Spec: 任务与运行分家，后台工作全部可见

Status: ready-for-agent

## Problem Statement

用户打开任务中心，是想回答两个问题：**我的盘现在在干什么**，和**上一次那件事跑成什么样**。
今天这两个问题都答不出。

**半夜硬盘在转，任务中心一片空白。** 四类会动磁盘的后台工作根本不建任务行：定时守护扫描、
watcher 派生的扫描与清理、建库后的首扫、异步的封面生成。它们一律交出 nil **扫描观察者**，
于是用户听见盘响、机器变卡，界面上什么也没有——**也没有任何东西可以暂停或取消**。

**重试当场抹掉被重试的那一次。** **任务键**是主键、写入走 upsert，一个任务键在库里永远只有一行。
上周那次扫描花了多久、扫出多少、失败了哪些，重试一次就没了；同一个库的两次扫描无从对比；
用户点下重试的那一刻，他刚才正在看的那条**中断**记录消失了。

**「查看日志」按钮基本是空的。** 它的实现是在日志文件里 grep `task_key=` 子串，而全仓只有 4 处
日志带这个字段，且全部是引擎自身的故障（落盘失败、序列化失败、panic、重试失败）。**任务体自己
一行都不带。** 用户点开看到的是空列表。

**失败只有一个计数。** `failed_archives: 7` 答不出是哪 7 个文件、各自因为什么失败。
唯一的去处是全局日志，而那里也没有任何字段能把一行对回某一次扫描。

**阶段没有时间线。** 只知道「现在在生成封面」，不知道读元数据那段跑了 40 分钟还是 40 秒、
什么时候切过去的。「这次为什么这么慢」答不出。

**「扫描完成」不等于封面好了。** 只有缩略图重建会等封面队列排空；普通的资料库扫描在归档处理完
就进**终态**，此后封面仍在后台生成，而那些迟到的报文被终态守卫丢弃。用户看到 100% 完成，
书库里还有一片无封面的书。

**按下全局暂停之后，每条运行还写着「运行中 62%」。** 系统里有两套互不相干的暂停：每个任务体
经**暂停闸门**停在下一个可中断点，和 `storageio` 的后台暂停让磁盘作业取令牌前阻塞。后者不改
任务状态，于是进度一动不动，界面却说它在跑。词汇表里只有前者，后者一个字都没有。

**不可达的资料库被无限重试。** 库挂在一块被拔掉的移动硬盘上，守护扫描每小时试一次、每小时失败
一次——没有任何刹车，任务中心被同一条失败刷屏，每次还白转一遍盘。

**冲突靠丢弃。** 守护扫描撞上手动扫描时静默跳过、等下一个 tick，用户永远不知道那次自动扫描
没跑。而且拒绝它的是 `scanner` 自己那把按扫描目标判的闸门，与引擎按**任务键**判的闸门是两套，
判据不一样。

**没有全局并发上限。** 启动入口立刻起 goroutine，17 类任务可以同时全开。只有**磁盘作业**受
`storageio` 限流，哈希、图像编解码、AI 分组这些吃 CPU 而不吃盘的部分不受任何约束。

**重启之后逐条点重试。** 服务重启把全部**活动态**任务批量盖成**中断**，等人一条条点。
那一笔 UPDATE 还把 `updated_at` 一起盖成重启时刻，于是中断运行连速率都算不出来——
代码里已经明确放弃了这个数。

对维护者，这一层还有三处结构性的债：

- **作用域从字符串反解。** 启动点手里明明有 `lib.ID`，却先拼进 `scan_library_1`，再由
  `inferTaskScope` 猜回来——类型名 `Contains("library")` 判库级、键末段 `ParseInt` 当 id。
  `scan_external_library_3_<sessionID>` 的末段是 session id，猜不回来。
- **一类多键靠按键 switch。** 书哈希重建有前台与低优先级回填两条键、刮削有全库与单库两条，
  **重启函数**注册表按类型分发，因此要在下游再按键分一次。
- **1950 行与 60 个 handler 同居一个包。** 任务引擎、启动仪式、模型转换与 HTTP 层全在
  `internal/api`，而这次要加的队列、槽位、**退避**、保留、**运行事件**、**采样**只会让它更重。

**指标不可查询。** 表只有 16 列，其余一切——展示态、累计指标、并发上限、i18n 占位参数、
以及重启函数要读回的原始入参——五类语义挤进一个 `params` TEXT，靠一对手工配对的编解码函数维持。
「这个库最近十次扫描平均多久」在今天是一段 Go 循环，不是一句 SQL。

## Solution

把**任务**与**运行**分成两个概念：任务是身份（某个目标上的某类工作，可被反复发起），
运行是它的一次具体执行，一次一行。凡是会动磁盘的后台工作都建一次运行，并标出**发起方**。

用户视角的变化：

- 任务中心分两层。上半是**现在**——在跑的与**排队中**的运行常驻置顶，带槽位占用与全部暂停；
  下半是**任务清单**——一个任务一行，写着上次结果、连败次数与开关，展开看它的历次运行。
- 半夜自动跑的扫描在列表里，带着「定时」或「监听」的标记，可以暂停、可以取消。
- 重试是**新一次运行**，上一次原样留着。同一个库的历次扫描可以并排看。
- 冲突不再丢弃：撞上了就排队；已经有一条排队的，后来者**合并**进去并计数。
- 每次运行有自己的详情页：阶段时间线（每段花了多久）、事件流（哪些文件失败、为什么）、
  吞吐曲线（卡在哪一段）、以及按运行过滤的原始日志。
- 「完成」开始说真话：封面生成是它自己的一条运行，扫描完成就是扫描完成。
- 「暂停」只有一个意思：全部暂停把每条活动运行逐个按下，状态如实变成**已暂停**。
- 拔掉硬盘的那个库连败几次后自动停发并标红，不再每小时白转一遍盘；也可以直接禁用它。
- 重启之后，扫描这类可重入的工作自己接着跑；改磁盘内容或花钱的那些停在中断，等人拿主意。

## User Stories

1. 作为终端用户，我希望半夜自动跑的扫描出现在任务中心，这样我能回答「我的盘现在在干什么」。
2. 作为终端用户，我希望每条运行标出是谁叫来的（手动 / 定时 / 监听 / 串联 / 恢复），这样我知道该去改哪个设置。
3. 作为终端用户，我希望自动发起的扫描也能暂停和取消，这样我要用机器时能让它让路。
4. 作为终端用户，我希望建库后的首扫也可见，这样我知道它跑到哪了、还要多久。
5. 作为终端用户，我希望封面生成是自己的一条运行，这样「扫描完成」不再是一句谎话。
6. 作为终端用户，我希望能单独暂停封面生成而不打断扫描，这样我可以只让出一部分磁盘。
7. 作为终端用户，我希望点重试之后原来那条记录还在，这样我不会在点下去的一瞬间失去正在看的东西。
8. 作为终端用户，我希望能看到同一个任务的历次运行，这样我能回答「这次是不是比上次慢」。
9. 作为终端用户，我希望每次运行有阶段时间线，这样「为什么这次要跑一夜」答得出。
10. 作为终端用户，我希望看到哪些文件失败了、各自因为什么，而不是只有一个数字 7。
11. 作为终端用户，我希望失败条目多到几千条时界面不会卡死，只列前一批并告诉我还有多少条。
12. 作为终端用户，我希望有一条吞吐曲线，这样「它是不是卡住了」不用靠猜。
13. 作为终端用户，我希望「查看日志」按钮点开真有东西，而不是一个空列表。
14. 作为终端用户，我希望冲突时后来的那次排队而不是被丢掉，这样定时扫描不会因为我正在手动扫而整轮跳过。
15. 作为终端用户，我希望重复的自动发起合并成一条并计数，这样列表里不会堆出一串一模一样的排队项。
16. 作为终端用户，我希望排队中的运行也能取消，这样我不必等它开跑再停它。
17. 作为终端用户，我希望按下全部暂停后，每条受影响的运行状态如实写作已暂停，而不是继续写运行中。
18. 作为终端用户，我希望不可暂停的运行在界面上明说它不受全部暂停影响，而不是让我以为暂停失灵了。
19. 作为终端用户，我希望重启之后扫描自己接着跑，这样无人值守的机器不需要我登录去点。
20. 作为终端用户，我希望改磁盘内容的工作（外部库传输、ComicInfo 回写）**不要**在无人看着时自己重跑。
21. 作为终端用户，我希望中断的运行也能算出速率，这样那条记录不是残废的。
22. 作为终端用户，我希望任务中心默认不被自动运行淹没，一眼能找到我刚发起的那一条。
23. 作为终端用户，我希望列表里能看到「上次成功是什么时候」，这样我知道某个库是不是很久没扫了。
24. 作为终端用户，我希望丢帧之后界面自己纠正，而不是停在一个过期的进度上等下一次轮询。
25. 作为运维者，我希望不可达的资料库连败几次后自动停发，这样它不再每小时白转一遍盘。
26. 作为运维者，我希望停发的任务在界面上标红并写明原因，这样我知道要去修什么。
27. 作为运维者，我希望手动发起一次或成功一次就把退避复位，这样修好之后不用等退避走完。
28. 作为运维者，我希望能人工禁用某个任务的自动发起，同时保留手动发起的能力。
29. 作为运维者，我希望有全局并发上限，这样几个重活不会同时开满把机器压垮。
30. 作为运维者，我希望看得到槽位占用（几分之几），这样我知道排队是因为限额还是因为别的。
31. 作为运维者，我希望上限可以在设置里改，这样强机器上可以放开。
32. 作为运维者，我希望运行历史自动清理，这样一年之后数据库不会自己把自己压垮。
33. 作为运维者，我希望清理本身也是一条可见的运行，这样它什么时候跑、清了多少有据可查。
34. 作为运维者，我希望活动态与排队中的运行永不被清理带走。
35. 作为运维者，我希望任务体的每一行日志都带运行标识，这样十几个并发运行的日志能分得开。
36. 作为运维者，我希望详情页里能一键跳到按这次运行过滤的原始日志，这样排障不用自己拼搜索词。
37. 作为运维者，我希望指标可以聚合查询，这样「这个库最近十次扫描平均多久」是一句 SQL。
38. 作为运维者，我希望知道某次运行当时实际生效的并发上限是多少，这样我能判断调参有没有生效。
39. 作为维护者，我希望「同一任务同时只有一次活动运行」由数据库约束保证，而不是靠内存表判定。
40. 作为维护者，我希望「最多一条排队」同样由数据库约束保证。
41. 作为维护者，我希望作用域是列而不是从任务键里猜出来的。
42. 作为维护者，我希望一类多键由**变体**表达，这样重启函数不必再按键 switch 分一次。
43. 作为维护者，我希望准入只剩一处，这样「什么叫已经在跑」不再有两个答案。
44. 作为维护者，我希望落盘不留 JSON 堆，这样加字段是改 schema 而不是往 map 里塞键。
45. 作为维护者，我希望领域规则能在纯内存里测，这样退避曲线、保留裁剪、合并计数不必穿过 SQLite。
46. 作为维护者，我希望 HTTP 层只剩状态码映射与装配，这样任务子域的状态机不与 60 个 handler 同居。
47. 作为维护者，我希望**重启函数**继续在装配期注册（ADR 0001 不变），这样这次不动那条已经成立的约束。
48. 作为维护者，我希望封面作业自带它属于哪次运行的句柄，而不是让接收侧靠一张带锁的侧表反查。
49. 作为维护者，我希望「往任务表里放一条运行」只能经启动入口发生，这样准入闸门在整片测试里始终有覆盖。
50. 作为维护者，我希望**运行事件**的种类是一个封闭枚举，这样它不会长成第二个日志系统。
51. 作为维护者，我希望事件必须显式发出，不做「日志自动转事件」的魔法，这样用户看不到与他无关的技术噪音。
52. 作为 AFK agent，我希望新增一个任务类型时，作用域、变体、发起方、是否**可续跑**都在声明里写明，而不是靠命名约定被猜出来。
53. 作为 AFK agent，我希望漏掉其中任何一项会有编译错误，而不是运行期才表现成猜错的作用域。
54. 作为 AFK agent，我希望排队、合并、槽位、退避、保留这几样的规则各有毫秒级用例，这样我改动它们时有靠山。

## Implementation Decisions

### 模块

- **`internal/task`（新）**——**任务**与**运行**的领域模型、状态机、队列与槽位、**合并**、
  **退避**、分层保留的判定、**运行事件**与**采样**的写入意图、投递节流。**它不知道 SQL。**
- **`internal/taskstore`（新）**——表结构、迁移、查询与聚合。
- **`internal/api`**——只剩 HTTP handler 与装配；**重启函数**仍在装配期注册（ADR 0001）。
- **`internal/scanner`**——交出**扫描观察者**的四条无归属入口改为归属某次运行；
  `ErrScanAlreadyRunning` 删除；封面作业携带它所属运行的**运行句柄**。
- **`internal/logger`**——新增经 ctx 携带运行标识的 slog handler。
- **`web`**——任务中心改两层结构，新增运行详情子页。

两包而不是一包是 ADR 0006 的决定，那里也记了它与 `proposal` / `koreader` 的惯例不一致。

### 表形状

形状来自本次盘问，比散文更精确地编码了决定，故内联。不含类型细节与索引全集。

```
tasks     id, type, scope, scope_id, variant,
          disabled, last_success_at, fail_streak, backoff_until
          UNIQUE(type, scope, scope_id, variant)

runs      id, task_id, trigger, nth_run, status,
          phase, current_item, current, total,
          paused_at, control_paused_ms, coalesced_count,
          message_code, error, started_at, updated_at, finished_at, sequence
          UNIQUE(task_id) WHERE status IN ('running','paused','cancelling')
          UNIQUE(task_id) WHERE status = 'queued'

run_events    run_id, at, kind, payload      kind ∈ {phase, item, control, warn}
run_samples   run_id, at, current, rate_per_minute
run_metrics   run_id, key, value
run_limits    run_id, + 11 列并发上限
run_args      run_id, key, value
```

### 状态机

```
排队中 ──→ 运行中 ──→ 完成 / 已取消 / 失败
  │          ↕
  │      已暂停 / 取消中
  └──→ 已取消（排队时被取消）

重启：活动态与排队中 ──→ 中断
                        ├─ 可续跑类型 → 自动重排队（发起方「恢复」）
                        └─ 其余      → 停在中断，等人裁决
```

**排队中**既不是**活动态**也不是**终态**：不占运行槽位，却仍会开跑。

### 关键决定

1. **任务是身份，运行才是一行**（ADR 0004）。身份由类型、**作用域**、作用域 id 与**变体**四项
   唯一确定。两条部分唯一索引取代内存表判定——**准入由数据库保证**。**重试**是同一个任务的
   新一次运行，`nth_run` 递增，上一次原样留着。

2. **落盘全部结构化，不留 JSON 堆**（ADR 0004）。今天 `params` 里的五类语义各回各家：
   展示态升为 `runs` 的真列，指标进 `run_metrics`（因此可聚合），上限进 `run_limits`，
   重启入参进 `run_args`，i18n 占位参数随 `message_code` 落在 `runs` 上。
   代价是新增一个上限字段要改 schema——这是明知的交换，「往 map 里塞」正是今天指标不可查询的原因。

3. **凡动磁盘的后台工作都建运行，准入闸门只留一处**（ADR 0005）。守护扫描、watcher 派生扫描
   与清理、建库首扫、封面生成都建运行并标**发起方**；作品群重建与仪表板统计预热这类毫秒级内存活
   不建。`scanner.ErrScanAlreadyRunning` 删除。

4. **冲突进队列，重复的合并。** 同一任务已有活动运行时后来者进**排队中**；已有排队的，
   再来的合并进那一条并把 `coalesced_count` 加一。守护扫描要的只是「确保扫过」，
   合并与各排一条效果相同，而后者会堆成一串一模一样的运行。

5. **槽位按单一全局数字限，默认 2，设置可改。** 不按 `storageio` 已有的卷键限。
   按卷更贴近真实瓶颈（两个库在两块盘上本可并行），一个数字更好解释、界面上也画得出「槽位 2/2」。
   **这是知情的取舍**：多盘用户会看到一条运行在排队，而它要等的那块盘是空的。

6. **退避与禁用挂在任务上。** 连败后按 ×2 拉长自动发起的间隔、封顶 24h，连败 ≥6 次停发并标红；
   手动发起一次或成功一次即复位。另有人工禁用开关：禁用后定时与监听不再为它发起，手动仍可。
   退避只约束自动**发起**，不影响已经在跑的运行。

7. **中断续跑按类型白名单。** 可续跑：资料库扫描、系列扫描、封面生成、重建缩略图、清理缩略图、
   书哈希重建与低优先级回填、文件身份重建、KOReader 进度对账与匹配刷新。
   不可续跑（只标中断，等人裁决）：清理资料库、外部库扫描与传输、ComicInfo 回写、刮削、AI 分组——
   它们要么改磁盘内容、要么花钱。全局开关默认开。**可续跑比可重试严格**，两者不得合成一个标志。

8. **分层保留：每任务留最近 20 次运行、终态运行 ≤90 天（取先到者）；事件随运行级联删；
   采样 ≤7 天。** 活动态与排队中的运行永不被带走。清理本身是一条「串联」发起的系统运行，
   每天跑一次，在任务中心可见。三个阈值可在设置里改。

9. **运行事件是封闭枚举的四类，必须显式发出：** 阶段切换、条目失败、控制动作（暂停 / 恢复 /
   取消 / 被合并）、运行级告警（降级、批量跳过、护栏触发）。**不做「日志自动转事件」的魔法**——
   全仓 132 处 `slog.Warn/Error` 里绝大多数是技术噪音，自动转会把它们当用户信息推出去。
   条目失败每次运行最多留 500 条，超出只累加计数并落一条「还有 N 条未列出」。

10. **采样每 10s 一点**（计数与速率），只用来看趋势；计数的事实来源仍是运行行本身。

11. **日志双轨，事件流为主。** 任务体的每一行日志经 ctx 注入的 slog handler 统一带上运行标识
    与**任务键**；详情页的事件流给用户看，原始日志按运行过滤给排障看。同一件事不写两处：
    事件是「用户该知道的」，日志是「排障要的」。

12. **推送是全量运行快照 + 一种轻量实况汇总帧**（槽位占用、活动数、排队数、全局暂停）。
    快照带单调序号，前端发现缺口就整份重拉，轮询从 15s 降为 60s 兜底。
    事件与采样不推，详情页按需拉。今天的节流水位规则原样保留。

13. **暂停统一成一个概念。** 「全部暂停」= 把每条活动运行逐个按下**暂停闸门**，状态如实变成
    **已暂停**；`storageio` 的后台暂停降为内部机制，只服务于「阅读时降载」，不再是用户按钮。
    不可暂停的运行不受影响，界面上明说。

14. **封面每库一条运行，作业自带句柄。** 封面作业入队时带上它属于哪一次运行，报文直接写进那条
    运行；**扫描观察者**只管扫描本身。**ADR 0002 因此被 ADR 0005 取代**——它当时判定观察者不设
    撤销机制，理由正是「封面帧还要经它推进」。缩略图重建也不再需要把归档处理与封面生成拼成
    一个分母来避免过早 100%，它的第二阶段从此是另一条运行。今天那个全局 `coverWG` 改成按批计数。

15. **控制端点的作用对象分明：** 暂停 / 恢复 / 取消作用在**运行**上，重试 / 禁用作用在**任务**上，
    清除作用在运行上。今天六个端点全部按任务键寻址，这次按对象改。

16. **符号全量对齐术语。** `TaskStatus` → `RunStatus`、`TaskSpec` → `RunSpec`、
    `taskrun.Handle` → **运行句柄**、SSE `task_progress` → `run_snapshot`。
    `TaskRuntime` 这个名字继续指引擎内部登记的 ctx + 闸门 + cancel，不让给别的类型。
    前端生成契约随之重生。

17. **迁移是 `DROP TABLE tasks`，不转换。** 老表一个任务键只有一行，转过来也只是每个任务孤零零
    一条运行，而那段解析代码只跑一次却要连测试一起维护。后果可自愈：资料库的扫描模式与间隔不在
    这张表里，升级后第一个守护 tick 就会把身份重新建出来，丢的只是「上次成功是什么时候」。

18. **顺带按 bug 修一条：中断运行的时间戳。** 今天批量标中断时把 `updated_at` 一起盖成重启时刻，
    于是分母里整段停机时长都算成了在干活，速率因此被放弃。改成 `finished_at` 取原 `updated_at`——
    落盘 goroutine 本来每 500ms 刷一次进度，那个字段本身就是心跳。

### 迁移与提交顺序

**顺序与切分见同目录 `issues/` 下的 19 张小票**，此处只记它们共同遵守的硬约束。

**每一票之间必须保持可编译、可运行、用例全绿。** 任务子域今天被 60 多个 handler 引用，
因此新旧并存的那一段要明确画出来：接线（票 07）与丢弃旧表（票 08）分成两张，
接线出问题时数据还在，回滚只是把装配换回去。

**改名不走类型别名。** 爆炸半径已量过：`TaskStatus` 非测试引用 114 处、`taskrun.` 127 处，
**都只在 `internal/api` 一个包**，外加契约生成器与前端生成产物。单包内的机械改动编译器能全量兜住，
过渡期别名只会把一次半途而废的迁移冻结进签名——本仓接口里那条「i18n 码版／字面量版」的疤
就是这么来的。

**先落四张不需要新模型的票**（中断时间戳、日志带任务键、暂停统一、身份四要素显式声明）。
它们各自都是完整竖切、当天可演示，且每一张都让后面那次切换小一圈。

## Testing Decisions

**什么是好测试**：只断言外部可观察的行为——投递出去的载荷、交给落盘端口的调用、数据库真实拒绝了
什么、HTTP 状态码、渲染结果。不断言内部字段布局，不断言方法调用次数。

**四道接缝，一道不新开**——今天这块已经有这四道，本次原样承接：

1. **`internal/task` 的构造点**（承接今天守着 `newTaskEngine` 的那道）。注入落盘端口、投递函数、
   停机信号、开后台 goroutine 的能力、**磁盘作业**入口与可控时钟。把后台执行换成同步版后，
   **终态**在调用返回时就已落定，不必 sleep 或轮询。**大头的用例压在这里**：状态机与四条终态、
   排队与合并计数、槽位与放行顺序、退避曲线与复位、可续跑白名单、保留裁剪的判定、
   事件与采样的写入意图、投递节流。观测面是投递出去的载荷加落盘端口收到的调用。
2. **`internal/taskstore` 对真 SQLite**（临时目录建库）。**只测只有 SQL 才答得出的**：
   两条部分唯一索引真的拒绝了第二条活动运行与第二条排队运行、事件与采样随运行级联删除、
   分层保留的 DELETE 选中了正确的行、聚合查询的结果。
3. **HTTP**（既有的测试 Controller + `httptest`）。只测端点契约：状态码映射（哪些是 409、
   哪些是 404、哪些是 500）、筛选参数、列表的合并与定序。
4. **前端 vitest**（props 驱动，i18n mock 掉）。实况区与折叠清单的渲染、序号缺口触发重拉、
   排队与停发的展示、不可暂停运行的说明文案。

**必须保留并加强的结构性守卫**：今天那套播种脚手架守的是「往任务表里放一条任务只能经启动入口
发生」——直接写内存表也能让消费方跑绿，但那样准入闸门会在整片测试里失去覆盖。新模型里这条更重要，
因为闸门下沉到了数据库约束：播种必须同时穿过领域层与落盘层，否则第 2 道接缝的索引用例是唯一
知道它存在的地方。

**先例**：
- `internal/api/task_engine_seam_test.go` 给出第 1 道接缝的整套装置（同步后台、可控时钟、
  观测投递载荷），照它的形状搬。
- `internal/api/task_seed_test.go` 给出播种脚手架的写法与它守的不变量。
- `internal/database/*_test.go` 给出第 2 道接缝的建库方式。
- `internal/api/controller_test.go` 给出第 3 道接缝的构造。
- `web/src/components/tasks/TaskCenter.test.tsx` 给出第 4 道接缝的写法，含 i18n mock 的口径。
- `internal/taskcontrol/pause_gate_test.go` 给出驱动暂停态的写法，本次暂停统一要用到。

**回归面**：既有的终态、文案码、并发徽章、筛选与定序用例必须继续绿，必要时只改名不改断言。
对外行为变更集中在三处，各自要有用例：扫描运行不再等封面（第 14 条）、
中断运行开始发速率（第 18 条）、全局暂停改变运行状态（第 13 条）。

## Out of Scope

- **`diskwork`、`storageio`、`taskcontrol` 自身**：限流规则、上限表、令牌、闸门实现与它挂在
  上下文上的方式。本次只改取用与呈现，不动机制。ADR 0001（重启函数装配期注册）同样不动。
- **`storageio` 的「阅读时降载」策略本身**。它继续存在，只是不再作为用户按钮暴露。
- **前台阅读取页**：它不是**磁盘作业**，不过闸门，也不属于任何运行。
- **作品群重建与仪表板统计预热**：毫秒级内存活，不建运行（关键决定 3）。
- **扫描器的三阶段流水线、批量入库、改名认领与 `dirtySeries` 刷新**：本次只改它把报文交给谁。
- **刮削、AI 分组、提案裁决的领域逻辑**：只改它们的运行声明与重启口径。
- **自动重试失败的运行**（区别于重启后续跑）：本次不做，失败仍等人点重试。
- **跨设备 / 多实例的任务协调**：这是单机自托管服务，槽位与队列都是进程内的。
- **指标的长期归档与外部导出**（Prometheus 之类）：采样只留 7 天，只服务于详情页曲线。
- **把运行事件做成通用日志系统**：种类是封闭枚举（关键决定 9）。
- **老 `tasks` 表数据的转换**：整表丢弃（关键决定 17）。

## Further Notes

- 词汇以仓库根部的领域词汇表为准。本次盘问已落地新增 9 条（**运行**、**发起方**、**排队中**、
  **合并**、**变体**、**运行事件**、**采样**、**退避**、**可续跑**）与重写 12 条，动手前先读它。
- 本次相关的 ADR：**0004**（任务是身份、运行才是一行，含落盘全部结构化与否掉的两个替代）、
  **0005**（自动工作纳入运行、准入闸门合并、封面帧走自带通道）、**0006**（两包拆分及其与仓内
  惯例的偏离）。**0002 已被 0005 取代**，原文保留。**0001 不受影响。**
- 盘问中查实、值得在动手时再确认一遍的五件事：
  1. 只有缩略图重建会等封面队列排空；普通库扫描不等，迟到的封面帧被终态守卫丢弃。
  2. 全仓只有 4 处日志带 `task_key`，全部是引擎自身的故障；ComicInfo 与外部库那两处
     `"task_key"` 是 JSON 响应字段，不是日志属性。
  3. `internal/api` 与 `internal/scanner` 合计 132 处 `slog.Warn/Error`——这是关键决定 9
     拒绝「日志自动转事件」的量级依据。
  4. 定时守护扫描每分钟检查一次、按库的间隔触发，撞车时靠 `ErrScanAlreadyRunning` 静默跳过。
  5. 库列表的排序主键是引擎单调发放的序号而不是时间列，因为两个写入方用两种文本格式写
     `updated_at`，而 SQLite 比的是文本。新表沿用序号，不要退回时间列。
- 数据量的量级（5 个库、每小时一次守护扫描）：运行每年约 4.4 万行，事件约 44 万行，
  采样若不清理约 260 万行。分层保留不是优化，是这套设计能不能跑过一年的前提。
