# Spec: 入参不是标签——声明说得清，合并才知道自己丢了什么

Status: ready-for-agent

## Problem Statement

**点了系列的强制重扫，界面回「已发起」，而强制在路上没了。** 这个系列所属的库已经排着一次扫描时
（守护 tick 或监听扫描在长扫期间排下的，很常见），这次发起会**合并**进那一条：跑的仍是先排上那份
不带强制的普通扫描。界面上两个入口——整理页的问题修复与资料库卡片的重扫——都发的是带强制的请求，
两个都会这样。**资料库扫描的同一个毛病上一批已经治好了，系列扫描是它隔了一百行的孪生兄弟，原样留着。**

**点了重建封面的重试，那次运行什么都不做。** 封面运行有一个「自己去找活」的开关：串联发起时为假
（处理扫描递过来的那一批），重启与重试时为真（进程里那批已经没了，必须自己扫库找）。这个开关**完全不在
运行的声明里**，只是一个 Go 形参。于是重试撞上一条排着的串联封面运行时，它被**合并**掉——用户点了重试，
拿到的是一条不会自己找活的运行，而界面照样回「已发起」。

**运行详情里那些「这次是在什么条件下跑的」的格子，有的是编的、有的报了两遍。** 跨库遍历的四个任务
（文件身份重建、低优先级哈希回填、两个 KOReader 任务）头上各挂着**一块盘**的存储档位与卷键——那是它
**最后一次真的读了盘**的那本书所在的盘，而它逐本走遍了每一个资料库。配了按库策略的用户会照着一个
答非所问的档位去调设置。同一批任务还把 IO 等待、暂停时长与哈希文件数**同时**报进**指标**与运行参数，
同一件事记了两遍；扫描等级也在声明与**上限**表里各有一份。

**这四件事看起来是四个毛病，其实是一个。** 一次运行的声明今天装在一个格子里，而那个格子里混着两种
东西：**会改变这次运行怎么跑的**（强制、刮削来源、语种、「自己去找活」），与**只描述它在什么条件下跑的**
（存储档位、卷键、并发数、执行模式）。混着，就没有人说得清哪一格是什么意思——于是有的该在没在、
有的不该在却在、有的两边都在。**而合并因此判不出自己丢了什么**：引擎在合并时只加一次计数，
**运行事件**只在第一次被合并时落一条。那条规则本身有充分理由（守护与监听扫描会在一次长扫里反复撞上
同一条排队运行，每次落一条能在一条还没起跑的运行上堆出几千行），但它恰好吞掉了唯一有损的那一种：
守护 tick 先并进来落了事件，用户随后点的强制并进来时**一条都不落**——丢掉东西的那一次，
正是没留下痕迹的那一次。

## Solution

把一次运行的**声明**分成两格，判据是一句话：**把它从声明里去掉，重启出来的那次会不会跑成另一个样子？**
会，它是**重启入参**；不会，它是**声明标签**。（见 ADR 0008 与 `CONTEXT.md` 这两个词条。）

分开之后，**合并**第一次判得出自己丢没丢东西：两次发起的**重启入参**不同即为**有损**。有损的合并
每次都落一条**运行事件**，不论它是第几次；无损的维持「只落第一次」——守护与监听那一路什么都不丢，
噪音防护原封不动。

在此之上，用户看得见的三件事跟着好转：系列的强制重扫被合并时，界面像资料库扫描那样**如实说明**；
重建封面的重试被合并时同样如实说明；跨库运行不再报一块它答不出来的盘，参数面板里不再堆着与**指标**、
与**上限**表重复的项。

**语义一个字不改。** 合并仍是合并，排队那条运行的**发起方**与它自己的参数一个字不动；
本次发起仍然不新建运行。改的只是「它说不说得出自己丢了什么」。

## User Stories

1. 作为一个点了系列强制重扫的用户，我想在这次发起被**合并**掉时看到一句说明，以便我知道跑的不是强制那一份，而不是以为强制已经在跑了。
2. 作为一个从整理页点「重新扫描」修某个系列问题的用户，我想在强制被丢掉时立刻知道，以便我不会在问题依旧时怀疑是扫描器坏了。
3. 作为一个从资料库卡片点重扫的用户，我想要与整理页一致的回答，以便同一个动作在两个入口上说的是同一句话。
4. 作为一个点了重建封面重试的用户，我想在这次重试被合并进一条不会自己找活的运行时被告知，以便我知道封面不会因此补上。
5. 作为一个队列里没有排队运行时点强制重扫的用户，我想要它照常新建一条运行并且强制完整保住，以便"如实回话"不会变成"每次都推脱"。
6. 作为一个没在等答案的守护扫描或监听扫描，我不希望被合并时弹出任何提示，以便界面不会为无人等待的事情说话。
7. 作为一个事后回看一条排队运行的用户，我想在事件流里看到每一次**有损**的合并，以便我能查出"我明明点了强制，为什么跑的不是强制"。
8. 作为一个在一次长扫期间被守护 tick 反复合并的用户，我不希望事件流被几千条"又被合并了一次"淹没，以便真正有内容的那几条还看得见。
9. 作为一个先被守护 tick 合并、随后自己点了强制的用户，我想让**我这一次**留下痕迹，即使它不是第一次合并，以便先来的噪音不会把我的那一次挤掉。
10. 作为一个服务重启后让系统自动续跑的用户，我想让被丢掉的**重启入参**在事件流里留痕，以便没有人在等答案时仍有据可查。
11. 作为一个配了按库存储策略的用户，我不想在跨库遍历的运行上看到一块盘的存储档位，以便我不会照着一个答非所问的数去调设置。
12. 作为一个看文件身份重建运行详情的用户，我想让它不报存储档位与卷键，以便我不必判断那到底是哪一块盘的。
13. 作为一个看 KOReader 任务运行详情的用户，我想要同上的一致行为，以便"跨库的运行没有单一的盘可报"这条判据在界面上处处成立。
14. 作为一个看任何一条运行详情的用户，我想让 IO 等待、暂停时长与哈希文件数只出现一次，以便我不必判断参数面板里那个数与指标面板里那个数是不是同一个。
15. 作为一个看扫描运行详情的用户，我想让扫描等级只出现在**上限**那一处，以便同一件事不在两个地方各说一遍。
16. 作为一个看运行详情参数面板的用户，我想让那里只剩真正的**重启入参**，以便"这次是照什么参数发起的"这个问题有一个干净的答案。
17. 作为一个点重试的用户，我想让**重启函数**读得回这次运行原本的每一个入参，以便重试出来的那次跑法与原来一致，而不是静默回落到默认值。
18. 作为一个开发者，我想让 `RunSpec` 上那两格各自的 doc 与它们实际装的东西相符，以便下一个加启动点的人知道自己新加的那一项该放哪一格。
19. 作为一个新加任务类型的开发者，我想让"这次合并有没有损"对我的新类型自动成立，以便我不必去某张按类型的例外表上登记。
20. 作为一个读代码的人，我想让**发起方**仍然只回答"谁叫来的"，以便界面上那枚徽章不会开始夹带"它会怎么跑"。
21. 作为一个维护者，我想让判据在落地期间有一个机械对账（**重启函数**读回哪些键是 grep 得出来的），以便每个启动点的归位判断有据可查而不是凭感觉。
22. 作为一个升级上来的用户，我想让升级前落下的运行仍然显示得出它们当时的那些数，以便这次搬家在界面上看不出断层。
23. 作为一个直接读运行 JSON 的脚本作者，我想在声明分格导致对外形状变化时从 `CHANGELOG.md` 得到明确说明，以便我知道该改哪一段。

## Implementation Decisions

**声明分两格。** `RunSpec` 上今天那个混装的元数据格子拆成两个：一格是**重启入参**（**重启函数**照着它
再发起一次才跑得出同一件事），一格是**声明标签**（描述这次在什么条件下跑，重启函数一项都不读）。
两格各自的 doc 写明判据，并写明判错的后果——把入参判成标签，重启函数读不回它、静默回落到默认值。

**每个启动点的声明重新归位一次。** 这是一次性的人工判断，落地期间的对账工具是：**重启函数**里
按键取参数的那些调用点，读到的就是入参，其余是标签。实测今天读回的只有扫描的**强制**、刮削的来源、
AI 分组的语种、哈希回填的发起理由四种。

**「自己去找活」进声明，归重启入参。** 它今天完全不在声明里，只是封面运行启动点的一个 Go 形参。
它满足判据——去掉它，重启出来的那次什么都不做。它的取值今天总跟**发起方**一起变（串联为假、恢复与
重试为真），但那不是**发起方**在改跑法：**发起方**只回答"谁叫来的"（`CONTEXT.md` 该词条已就此补过一句）。
**重启函数**在重启时把它固定为真是对的，那是重启函数的知识，不是原运行的属性——两件事分开之后不矛盾。

**合并按有损与无损分开处置。** 引擎在合并分支上比较本次发起与排队那条的**重启入参**：不同即**有损**。
有损每次都落一条**运行事件**（控制类，被**合并**那一种），不论第几次；无损维持现有的「只在第一次落」。
合并计数与排队运行的声明、任务体一概不动——被并掉的仍是后来那一次。**这条规则是引擎的，不是启动点的**：
"这次合并丢没丢东西"需要同时看两份声明，而启动点只有自己那一份。

**三处启动点各自处置。** 系列扫描与封面运行的**手动**发起在被有损合并时，端点回一句说明，
复用资料库扫描那一批已经落地的判据函数与 i18n 文案码；**重启函数**那条路**不回话只留痕**——
它是系统在重启后自己跑的，没有人在等答案，事件流才是它该说话的地方。

**跨库运行不报单一存储画像。** 文件身份重建、低优先级哈希回填与两个 KOReader 任务的 IO 实况上报里，
存储档位与卷键撤掉——按判据它们是**声明标签**，而跨库的运行没有单一的盘可标。这与上一批治好
重建缩略图的是同一条判据；差别只在来源（那边是从没观测过的全局默认，这边是最后一次真读了盘的那一块），
**呈现上是同一个答非所问**。执行模式一类与盘无关的标签保留。

**同一件事只报一次。** 那四个任务把 IO 等待、暂停时长与哈希文件数同时送进**指标**与运行参数的第二份
撤掉——可聚合的计数与时长归**指标**。扫描等级在声明与**上限**表里各有一份，归**上限**表。
参数面板从此只剩真正的**重启入参**。

**对外契约。** 声明分格若改变投递出去的运行快照形状，重生生成的前端契约类型并通过 CI 的漂移检查；
参数面板的取数改判新的那一格。撤掉的标签与去重的那一份对已经落盘的历史运行不做回填——
旧运行照原样显示，取数保持"先读**指标**、读不到再退回参数"的既有口径，因此界面上看不出断层。

**ADR 0008 的状态行在这批票收尾时改成已实施。** 它现在写着「已裁决，尚未实施」。

## Testing Decisions

好的用例只断言外部行为：**投递出去的载荷**长什么样、事件流里有没有那一条、端点回给用户的是哪一句。
不断言某个函数被调了几次、某个 map 里有几个键这类实现细节。三条缝**全部已经存在**，本 spec 不新开缝。

**任务引擎 seam（`internal/api`）——声明里每一格落在对的那一边。** 构造点注入落盘端口、投递与可控时钟，
观测面固定为投递出去的载荷，与 SSE 订阅者看到的完全一致。在这里断言：每个启动点的**重启入参**与
**声明标签**各自出现在对的那一格；跨库运行的载荷上没有存储档位与卷键、而执行模式仍在；
IO 等待/暂停/哈希文件数只出现在**指标**里、不在参数里；扫描等级不在声明里；封面运行的
「自己去找活」出现在**重启入参**里。**前例**：上一批「十三个数搬进指标」与「重建缩略图撤存储画像」
两张票的验收条逐字就是"在任务引擎 seam 上断言"，都在这里落的。

**领域装置（`internal/task`）——合并规则本身。** 在这里断言：两次发起的**重启入参**相同时，
五十次合并仍只落一条事件；不同时，每一次都落一条；先无损后有损的顺序下，有损那一次照落
（这一条正是今天规则吞掉的那种）；有损与否都不改排队运行的声明、任务体与**发起方**。
**前例**：该包已有一条断言「五十次合并只落一条控制事件」的用例，新规则是同一处的第二个 case，
不是新装置。

**真路由（`internal/api`）——端点跟用户说了什么。** `SetupRoutes` 起真服务、真管理员会话与 CSRF，
摆出「一条活动运行 + 一条排队运行 + 再来一次带强制的发起」的局面，断言 HTTP 响应说的是被合并、
不是「已发起」，且回的是 i18n 文案码不是裸串。守两条边界：队列里没有排队运行时强制照常新建一条
排队运行并保住强制；守护扫描与监听扫描被合并时**不**回这句话。**前例**：上一批为资料库扫描建的
那个合并用例文件，扩它而不是新建；它注入的可控扫描存储能让扫描停在可控点并由用例放行。

**迁移与兼容。** 若声明分格触及落盘形状，照本仓既有的幂等迁移写法补一条迁移用例：
存量形状 → 迁移两遍 → 数据一条不少、旧形状不在。

## Out of Scope

- **把跨库运行改报逐盘的 IO。** 那要给 IO 实况开一张按卷键分组的表，是另一件事；本 spec 只撤掉
  那个答非所问的单一档位，不替它造一个答得出的。
- **刮削与维护那几条端点被合并时的回话。** 它们的发起没有会被丢掉的**重启入参**，被并进的那条跑的
  确实是同一件事，回「已发起」不算说谎。本 spec 不动它们。
- **跨运行聚合的取数路径。** 「这个库最近十次扫描平均处理了多少归档」缺的是端口、领域方法、端点与
  界面四层，独立立项，与本 spec 无依赖。
- **前端组件层的命名。** 那一族按旧概念取名的组件与视图类型另有其事，不在本 spec。
- **历史运行的回填。** 撤掉的标签与去重的那一份不追溯改写已落盘的运行。
- **`RunSpec` 上除那两格之外的字段。** 文案码、占位参数、可取消可暂停、作用域显示名一概不动。

## Further Notes

**这批票的判据会被反复引用**，票面不必每张重述：**把它从声明里去掉，重启出来的那次会不会跑成
另一个样子？** 引 ADR 0008 与 `CONTEXT.md` 的**重启入参** / **声明标签**两个词条即可。

**「只落第一次」那条规则不是要被推翻的。** 它有自己写下的充分理由，本 spec 只给它加一个例外，
且例外的判据是普适的（比两份**重启入参**），不是一张按任务类型的例外表——后者在新类型出现时
会静默漏项，那正是上一批论证过要避开的形状。

**归位判错的后果是安静的。** 把入参判成标签，**重启函数**读不回它、静默回落到默认值，
`RunSpec` 起始文案那一格的 doc 已经记着这样一处先例（AI 分组的语种）。因此每个启动点的归位
都值得对着**重启函数**实际读回的键核一遍。

**本 spec 的七项来自上一轮结算的挂账**（`report-truthfully` D3、D12、D23 与实测新增的扫描等级重复），
它们原本被记成四条互不相干的待办，是同一条判据把它们并成一件事的。
