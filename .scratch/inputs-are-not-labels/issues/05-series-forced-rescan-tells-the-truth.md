# 05 — 系列强制重扫被合并时如实回话

**What to build:** 用户从整理页修某个系列的问题、或从资料库卡片点重扫（两个入口发的都是**带强制**的
请求），而这个系列所属的库已经排着一次扫描时——今天界面回一句「已发起」，**而强制在路上没了**：
这次发起被**合并**进那一条，跑的仍是先排上的普通扫描。用户会在问题依旧时怀疑扫描器坏了。

资料库扫描的同一个毛病上一批已经治好，**系列扫描是它隔了一百行的孪生兄弟**，判据函数与文案码现成可用。

**Blocked by:** 04

**Status:** ready-for-agent

- [ ] 系列扫描的手动发起不再丢弃引擎交回的发起结果
- [ ] 手动发起、带**强制**、且本次发起被**有损合并**时，端点回一句说明：已并入正在排着的那次扫描，那次不是强制的
- [ ] 复用资料库扫描那条已经落地的判据函数与 i18n 文案码，**不新造第二套说法**
- [ ] 在**真路由**上守它：摆出「一条活动运行 + 一条排队运行 + 再来一次强制」，断言 HTTP 响应说的是被合并、不是「已发起」，且回的是文案码不是裸串
- [ ] 守边界：队列里**没有**排队运行时，强制照常新建一条排队运行并写下本次的强制
- [ ] 守边界：守护扫描与监听扫描被合并时**不**回这句话——没有人在等它们的答案
- [ ] 整理页与资料库卡片两个入口都拿得到这句话：前端读响应体，不再弹写死的 toast
- [ ] **不做**：不把强制立成**变体**；不让本次发起顶替排队那条的声明与任务体
- [ ] `CHANGELOG.md` 记一条
- [ ] 后端与前端门禁全绿，**含 `gofmt -l ./cmd ./internal` 与 `golangci-lint run`**
