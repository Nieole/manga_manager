# 04 — 合并判得出自己丢了什么

**What to build:** 用户事后回看一条**排队中**的运行时，事件流里查得到「我明明点了强制，为什么跑的
不是强制」。今天查不到：引擎在**合并**时只把计数加一，**运行事件**只在**第一次**被合并时落一条。
那条规则本身有充分理由——守护与监听扫描会在一次长扫期间反复撞上同一条排队运行，每次落一条能在
一条还没起跑的运行上堆出几千行——**但它恰好吞掉了唯一有损的那一种**：守护 tick 先并进来落了事件，
用户随后点的强制并进来时**一条都不落**，丢掉东西的那一次正是没留痕的那一次。

分格之后（票 02、03）引擎第一次比得出来：**两次发起的重启入参不同即为有损。**

**语义一个字不改。** 合并仍是合并：被并掉的仍是后来那一次的声明与任务体，排队那条运行照跑。

**Blocked by:** 02, 03

**Status:** ready-for-agent

- [ ] 引擎在合并分支上比较本次发起与排队那条的**重启入参**
- [ ] 不同即**有损**：每次都落一条控制类**运行事件**（被**合并**那一种），**不论它是第几次**
- [ ] 相同即**无损**：维持现有的「只在第一次落」——守护与监听那一路的噪音防护原封不动
- [ ] 合并计数照旧累加；排队那条运行的声明、任务体与**发起方**一个字不动
- [ ] 判据写进合并那一段的符号 doc，并写明**为什么这条规则属于引擎**：需要同时看两份声明，而启动点只有自己那一份
- [ ] 领域用例：五十次**无损**合并仍只落一条事件
- [ ] 领域用例：**有损**合并每一次都落
- [ ] 领域用例：**先无损后有损**，有损那一次照落——这正是今天的规则吞掉的那种
- [ ] 领域用例：有损与否都不改排队运行的声明、任务体与发起方
- [ ] **重启函数**那条路的有损合并因此**自动留痕**，本票不为它另写代码
- [ ] 判据是普适的：新任务类型带了新的重启入参时自动成立，**不引入任何按类型的例外表**
- [ ] 后端与前端门禁全绿，**含 `gofmt -l ./cmd ./internal` 与 `golangci-lint run`**
