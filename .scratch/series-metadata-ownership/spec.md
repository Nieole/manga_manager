# Spec: 系列元数据规则归属

Status: done

Implementation verification: [验收记录](verification.md)

## Problem Statement

作为长期维护这个程序的人，用户希望继续迭代时不必在越来越多的文件和入口之间追踪同一套业务规则，并希望改善整个项目的功能归属与代码结构。

首期聚焦系列元数据。人工编辑、批量编辑、扫描和提案都能改变同一个系列的内容，但字段处理、集合写入、锁、来源记录和派生刷新分别嵌在不同流程中。修改一个字段时，维护者需要重新查找全部来源，判断哪些规则应一致、哪些差异必须保留。单纯再拆文件不能降低这种认知负担。

现有差异具有实际含义：人工替换与批量增量编辑不同，扫描追加关联与提案整体替换不同；提案关单、扫描书入库和整批编辑也各有不可拆散的事务关系。重构若只追求一个写入函数或删除行数，可能破坏已有数据、并发保护、扫描性能和错误行为。

## Solution

建立独立的系列元数据 module，以按来源表达意图的 interface 集中本期字段规则。人工、批量、扫描和提案继续表达各自业务意图，调用流程保留原有事务、裁决、身份管理和刷新安排。

用户使用程序的行为保持不变。维护者修改元数据规则时，有一个明确归属可以审查各来源的适用方式，并通过同一业务测试面验证结果。接入完成后，删除被替代的旧规则副本；全局标签维护等范围外动作保留独立归属。

这是一轮后端结构调整。它是“让功能 module 拥有完整行为、逐步收缩 Controller 职责”的第一条业务流程，不代表全项目架构调整已经完成，也不包含前端工作流重构。

## User Stories

以下故事共同构成验收范围；其中维护者与实现代理是本次架构改进的直接使用者，管理员与阅读者的故事约束行为兼容。

1. 作为维护者，我希望系列元数据规则有明确的 module 归属，以便修改字段时不用重新遍历所有写入入口。
2. 作为维护者，我希望人工、批量、扫描和提案都接入这份规则归属，以便首期不会只覆盖一个方便迁移的入口。
3. 作为维护者，我希望各来源通过表达真实意图的 interface 使用规则，以便不必组合通用策略标志才能正确调用。
4. 作为维护者，我希望理解 module 不需要先理解整个 Controller，以便实现和测试具备 locality。
5. 作为维护者，我希望调用流程不再逐字段拼接已经集中维护的规则，以便新的 module 提供实际 depth。
6. 作为维护者，我希望迁移完成后删除被替代的规则副本，以便以后不会出现两套并行演进的行为。
7. 作为维护者，我希望按规则集中程度、调用方知识负担和兼容结果验收，以便不会为了减少行数删除必要保护。
8. 作为实现代理，我希望范围外的写入动作被明确列出，以便不会误认为所有相关数据库表都只能由新 module 修改。
9. 作为管理员，我希望手工保存后的标量字段保持既有空值语义，以便重构不会改变清空标题、简介或评分的结果。
10. 作为管理员，我希望人工编辑中的标签、作者和链接缺席时保持原样，以便没有提交的集合不会被清空。
11. 作为管理员，我希望明确提交空集合时仍清空对应关联，以便清空动作继续有效。
12. 作为管理员，我希望人工编辑仍能修改被锁字段及锁本身，以便字段锁不会变成人工编辑限制。
13. 作为管理员，我希望人工保存保留现有空白过滤和实际落库值，以便重构不会擅自增加 trim、去重或值归一化。
14. 作为管理员，我希望手工编辑仍使用内容指纹进行并发保护，以便来自其他来源的改动仍能使旧编辑版本失效。
15. 作为管理员，我希望版本检查与内容写入仍处于同一个事务，以便并发保存不会双双通过旧版本检查。
16. 作为现有客户端使用者，我希望省略版本字段和提交空版本仍有各自原有结果，以便旧客户端兼容与空版本保护同时保留。
17. 作为管理员，我希望人工保存的关联写入失败仍回滚整次修改，以便不会出现内容被清空但接口报告成功。
18. 作为管理员，我希望人工保存的统计刷新与写入仍保持原有原子关系，以便读取结果与当前行为一致。
19. 作为管理员，我希望批量编辑仍只修改现有支持的状态、出版社和标签，以便不会因重构意外扩大批量编辑能力。
20. 作为管理员，我希望批量状态和出版社未提供时仍不修改，以便选区中其他字段保持原样。
21. 作为管理员，我希望批量标签仍先添加后删除，以便同一个标签同时出现在两份输入时结果不变。
22. 作为管理员，我希望批量标签保持现有空白处理、缺失系列容忍和重复选区行为，以便大选区编辑不出现兼容回归。
23. 作为管理员，我希望整批编辑仍然全部成功或全部回滚，以便内部 SQL 分块不会造成部分选区已修改。
24. 作为大资料库维护者，我希望批量编辑保留集合式 SQL 和参数分块，以便处理大量系列不会退化为逐系列读取和整行写回。
25. 作为管理员，我希望批量编辑保留当前字段锁和来源记录处理，以便此次结构调整不会悄悄改变权限或审计语义。
26. 作为管理员，我希望批量提交后的统计刷新失败仍按现有方式记录并返回，以便成功结果不会被新的刷新策略改写。
27. 作为资料库管理员，我希望扫描首次创建系列时仍以目录名初始化标题并默认锁定标题，以便新系列的初值不变。
28. 作为维护者，我希望首次创建的元数据默认值与后续写入规则集中审查，以便同一字段的初值不会成为遗漏的写入来源。
29. 作为资料库管理员，我希望扫描继续管理系列身份、路径和书记录，以便元数据重构不会引入额外身份创建流程。
30. 作为管理员，我希望扫描对已有标题的保留和兜底行为保持不变，以便人工标题不会被目录名覆盖。
31. 作为管理员，我希望扫描保留 ComicInfo 各标量的既有写入与锁判据，以便此次改动不会调整空值或锁的实际效力。
32. 作为管理员，我希望扫描标签和作者继续按现有方式追加，以便一次扫描不会整体替换系列关联。
33. 作为维护者，我希望扫描首建失败、已有行更新失败和关联写入失败保留不同的处理方式，以便不会被通用错误规则改成整批失败。
34. 作为资料库管理员，我希望扫描元数据仍与身份及书记录参与原有批次事务，以便不会出现先建空系列再单独补内容的新窗口。
35. 作为大资料库维护者，我希望扫描仍按原有节流和收尾方式刷新派生数据，以便不会因逐书或逐批全量重算降低性能。
36. 作为维护者，我希望扫描快照和缓存更新时机保持不变，以便规则内聚不会顺便改变扫描覆盖行为。
37. 作为管理员，我希望扫描取消时的派生刷新收尾仍保持现有规则，以便已提交的工作不会失去应有的收尾处理。
38. 作为管理员，我希望提案的待裁决状态、字段选择和去重继续由提案 module 管理，以便元数据写入不会接管提案生命周期。
39. 作为管理员，我希望提案标量仍按现有非空覆盖和状态归一规则写入，以便应用结果不变。
40. 作为管理员，我希望参与本次写入的提案标签和作者整体替换当前集合，以便删除错误关联的提案仍能生效。
41. 作为管理员，我希望未参与本次写入的提案集合不被清空，以便部分应用不会破坏未处理字段。
42. 作为管理员，我希望提案的锁过滤与写入处锁保护保持原样，以便应用流程仍能表达锁定跳过等既有结果。
43. 作为管理员，我希望只补空字段的判定及读取时机不变，以便这次重构不会调整提案裁决语义。
44. 作为管理员，我希望元数据写入、来源记录、提案字段删除或关单仍保持原有事务关系，以便不会把内容和裁决状态拆成独立提交。
45. 作为管理员，我希望提案并发抢先和部分应用仍返回原有分类，以便界面和现有客户端无需调整。
46. 作为管理员，我希望提案不支持修改的语言与字段锁保持原样，以便提案入口不会因共用 module 获得额外能力。
47. 作为管理员，我希望已有来源、地址、置信度、提案关联和值的记录保持现有格式，以便来源沿革与现有数据一致。
48. 作为管理员，我希望 Bangumi 来源链接继续遵守现有追加和判重规则，以便它不会被当成人工链接整体替换。
49. 作为管理员，我希望人工、批量和扫描不因本次调整新增来源记录，以便结构改进不会伪造新的沿革事实。
50. 作为维护者，我希望标题与首字母索引继续联动，以便列表索引不会因规则迁移与实际标题分离。
51. 作为阅读者，我希望搜索索引、标签计数和现有派生统计继续按原方式更新，以便浏览结果与重构前一致。
52. 作为管理员，我希望全局标签改名、合并和删除继续有效，以便本期范围之外的多系列动作不会被新 module 阻断。
53. 作为阅读者，我希望系列身份、书、封面、阅读进度和关联内容不被此次重构改写，以便已有资料和阅读状态得到保留。
54. 作为维护者，我希望外部元数据获取与 AI 的 module 保持现有职责，以便它不会为了集中写入而依赖数据库。
55. 作为维护者，我希望数据库不反向依赖新的业务 module，以便不会形成循环依赖或新的业务中心。
56. 作为维护者，我希望批量编辑的高层编排迁出数据库后仍保留原事务和效率，以便依赖方向调整不会成为性能改写。
57. 作为维护者，我希望提案与新 module 通过明确的事务能力交接协作，以便不需要运行时类型强转或暴露全局存储能力。
58. 作为维护者，我希望测试通过 module 的业务 interface 和数据库最终事实验证规则，以便 implementation 重排不导致测试跟着重写。
59. 作为维护者，我希望使用真实临时 SQLite 验证写入与回滚，以便约束、触发器和事务行为不被简化的 fake 掩盖。
60. 作为维护者，我希望保留四条现有流程的高层测试，以便共同规则正确时仍能发现事务与流程接线错误。
61. 作为维护者，我希望来源兼容矩阵明确覆盖 nil、空值、锁、集合和错误差异，以便测试不会把来源语义强行统一。
62. 作为维护者，我希望新的 interface 测试替代失去价值的重复规则测试，以便测试数量增长不会成为重构的主要结果。
63. 作为维护者，我希望规则集中后仍保留有意义的并发、批量规模和扫描刷新验证，以便删除旧测试时不会丢失跨流程保护。
64. 作为管理员，我希望现有 HTTP 请求、响应、状态码和错误分类不变，以便前端和现有客户端无需同步升级。
65. 作为部署者，我希望此次改进不要求数据库格式迁移或重新导入，以便已有实例可以继续使用原数据。
66. 作为维护者，我希望疑似现有缺陷单独留下可核实线索，以便它们不会未经讨论被修复或被当作本期新增功能。
67. 作为维护者，我希望前端工作流及其他业务能力在后续分期处理，以便首期能验证整体方向而不扩成全仓重写。
68. 作为项目负责人，我希望本规格之后另行生成工单再实施，以便设计、任务拆分和实现完成状态保持清楚。

## Implementation Decisions

### module 与职责

- 新建独立的系列元数据 module，建议包名为 seriesmeta。名称是实现定位，不新增另一个领域概念；领域用语采用“系列元数据”。
- 共同拥有权是规则归属，不是所有相关表的独占物理写入权。全局标签字典维护、系列身份建立和其他范围外动作保留既有归属。
- metadata 继续负责外部来源与 AI；proposal 继续负责提案生命周期及字段裁决。新 module 不持有 Controller、不启动后台运行、不管理配置或全局生命周期。
- 依赖方向为调用流程到系列元数据 module，再到所需持久化能力；持久化 module 不反向调用新 module。

### interface 契约

- 采用人工替换、选区增量编辑、扫描元数据准备及关联追加、已裁决提案写入等来源明确的入口。具体导出符号可在实现时选定，但必须维持这些可辨认的意图，不能退化为字段 map 配任意策略标志。
- 人工输入保留标量与集合的现有值域及缺席语义。批量输入只表达当前支持的增量编辑。提案输入包含已选字段、既有系列快照及来源信息，不承接字段选择、fill_empty 判定或关单。
- 扫描准备结果只拥有元数据列及标题关联的首字母，不拥有身份、路径或计数；扫描将其合入原有系列 upsert。追加标签和作者由来源明确的入口承接，错误容忍保持原样。
- 首建和更新必须可以区分。首建元数据初值进入新 module，但扫描仍执行系列实体创建，保留首建失败对后续书入库的原有影响。
- 不公开持久化变更集、延期执行计划、来源注册机制或扫描 continuation 协议。implementation 内部可以组合规则，但不能增加调用方的跨阶段生命周期负担。
- 不为统一规则新增读取当前系列的通用步骤。人工、提案和扫描原有快照读取及缓存语义保持；人工的版本校验继续在原有事务内读取和比较。
- 元数据版本的内容指纹算法、覆盖字段、集合归一和响应值保持原样。计算与事务内加载可由新 module 统一提供，以避免多个持有者重新实现；请求解析与 HTTP 结果翻译仍归入站 adapter。

### 事务能力交接

- 新 module 不自行开始、提交或回滚事务，接受由调用流程交入的事务绑定查询能力，不接受全局 Store 或 Controller。
- 事务依赖使用编译期可满足的窄结构型查询契约，只包含本期所需读取、写入和必要的批量原语。生产上的事务绑定数据库查询对象直接满足契约；提案的事务查询契约组合这份能力，不以运行时类型断言转换具体对象。
- 该查询契约属于 implementation 的依赖 seam，不是另外一套可供业务调用方绕过 module 的字段修改 interface。不得为测试复制存储模型或提供原始 SQL 任意执行能力。
- 人工版本检查、内容与关联替换、统计刷新仍共同提交；提案内容、沿革、已处理字段删除或关单 CAS 与统计刷新仍保持原有事务关系。
- 扫描继续使用现有书批次事务；不得先提交一个空系列，再在另一事务写元数据，不得改变扫描缓存或首建/更新的错误路径。
- 批量高层编排迁到调用流程，事务仍覆盖整个选区。数据库只提供具体的事务绑定批量 SQL 原语，保留现有参数分块和集合式写入。
- 提交后的刷新保持原有归属和失败语义。若为迁移将某条刷新调用移动到调用流程，必须保持其相对于提交、关单、书入库和响应的原有关系，不能向调用方开放任意刷新策略。

### 来源兼容矩阵

| 来源 | 标量与集合 | 锁与沿革 | 事务及派生数据 |
| --- | --- | --- | --- |
| 人工 | 空字符串按现状保存为 NULL，非正评分按现状保存为 NULL；集合 nil 不改，非 nil 替换，空集合清空；不新增输入规范化。 | 人工可修改被锁字段和锁；不新增来源沿革。 | 事务内检查内容版本、写入并刷新系列统计；写入或刷新失败仍回滚。 |
| 批量 | 仅状态、出版社及标签增删；nil 不改；保持先加后删、缺失 ID 容忍、重复 ID 及空白处理。 | 不增加锁检查和沿革。 | 全选区一事务；保留现有 SQL 参数分块；提交后逐系列尽力刷新，失败告警不改变已成功结果。 |
| 扫描 | 首建标题取目录名、默认锁 title；更新保留既有标题及兜底规则；ComicInfo 标量按现状处理；标签、作者按现状追加。 | 使用原有缓存快照与锁判据；集合锁的现有差异保留；不新增沿革。 | 系列与书保持同一原批次事务；保留首建失败跳过和部分写入错误容忍；继续节流与收尾刷新。 |
| 提案 | 标量非空覆盖，状态按现状归一；仅参与写入的标签和作者整体替换；保留语言和锁。 | 保留二次锁保护、去重、已有沿革和 Bangumi 链接规则。 | 裁决仍归提案；元数据、沿革、字段删除或关单及统计保持现有原子关系。 |

- 提案来源默认置信度仍只有一份现有判据。提案流程可以交出按该判据得到的有效来源信息，新 module 负责保持既有写入格式与值；不得复制来源置信度表或引入新的来源判断。
- 现有集合判重键、作者角色、沿革排序与空集合沿革行为保持原样。来源链接的缺失判定和匹配条件不因名称看似合理而更改。
- 扫描状态字段的现有取值、未锁空标量的实际覆盖方式，以及集合追加未检查字段锁等差异，不在重构中修复。
- 人工、提案、批量和扫描的统计、dashboard cache、SSE、用户聚合刷新时机不做统一。新 module 不新增“写完自动刷新所有派生结果”的机制。

### 数据、契约与兼容

- 不改变数据库格式、业务表归属、既有 ID 或历史数据，不需要重新扫描或重新导入。
- 可以新增或调整必要的事务绑定批量查询，不能将批量操作改成逐系列读取和整行更新。既有搜索触发器和标签计数触发器继续工作。
- 不改变对外请求、响应、状态码、错误分类及客户端版本兼容；不增加前端功能或请求协议。
- 保留任务身份、运行、准入、重启注册与领域/落盘分工的既有 ADR 约束。资料库路径迁移的身份保持、持久化保护和失败恢复不得因扫描规则迁移受到影响。
- 四路径完成接入后删除失去职责的旧字段规则和旧批量业务写入入口。生成的底层查询以及范围外合法调用无需为形式上的唯一性删除。

## Testing Decisions

### 已确认的测试 seam

用户已确认两级测试：主要 seam 是系列元数据 module 按来源表达意图的业务 interface；补充 seam 使用四条现有高层流程入口，验证事务与协作。不会为每个私有 helper 新增独立测试面，也不新增通用测试框架。

好测试给出来源意图，经过正式 interface 与真实事务后，断言系列字段、关联、沿革、返回结果及回滚等可观察事实。它不依赖私有函数、内部变更数组、文件布局或导出方法数量。

### module 行为测试

- 使用真实临时 SQLite、既有迁移与事务查询 adapter，覆盖约束、触发器、批量语句和回滚；不使用会绕过这些行为的假存储作为唯一正确性证据。
- 按四种来源组织兼容矩阵，覆盖标量空值、集合 nil/empty、锁、标题与首字母、链接、作者角色、沿革和错误差异。
- 验证人工编辑的内容版本不因集合存储顺序变化而误变，也能感知本期其他来源和范围外标签维护造成的内容变化。
- 验证提案字段未参与写入与明确空集合的差别，保持整体替换、部分应用和锁定语义。
- 验证扫描首建与已有行的元数据准备结果不会覆盖身份、路径或计数；通过原扫描流程验证最终组合写入。
- 验证批量跨参数分块仍处于同一事务，包含大选区、缺失及重复 ID、同时添加和删除相同标签、失败后的整体回滚。
- 必要故障注入沿用既有事务能力，只针对需要观察的错误结果；不为注入故障引入新的公开业务接口。

### 保留的高层验证

- 人工入口：内容冲突及请求兼容、并发事务竞争、标签/作者/链接写入失败时的整体回滚、响应保持。
- 提案入口：字段筛选与 fill_empty、锁定结果、部分应用、终态 CAS 抢先与原有回滚、来源和关单的原子关系。
- 扫描入口：首建、已有系列、书记录与元数据同批写入、缓存更新时机、取消收尾、人工标题保留和派生统计节流。不靠耗时阈值替代正确性测试。
- 批量入口：全选区原子性、集合式写入、大选区 SQL 分块、提交后刷新失败仍保留既有成功结果。
- 验证其他字段、身份、阅读记录和范围外动作没有被新 module 意外修改。
- 检查依赖方向及旧规则退出；优先依靠清楚的依赖契约与代码审阅，只有编译器无法表达且存在实际绕过风险时才增加小范围结构守卫，不建设通用架构检查平台。

### 既有测试先例与门禁

- 人工编辑可沿用 TestUpdateSeriesInfoConcurrentEditConflict 及系列元数据原子性测试的行为形状。
- 提案可沿用 TestApplyRemovesTagsAndAuthorsMissingFromProposal、TestApplyKeepsLockedCollectionsIntact、并发裁决和来源沿革测试；现有提案查询归属守卫继续有效。
- 扫描可沿用人工标题/锁保留、增量扫描及 TestScanLibraryDeferredRefreshPopulatesStats 的高层验证。
- 大选区可沿用 TestBulkOperationsExceedVariableLimit，确保实现没有用逐行循环绕过原问题。
- 新 module 测试替代旧的重复字段规则测试；不删除仍验证事务、HTTP 或扫描接线的测试，也不以测试数变化作为完成标准。
- 实施后运行仓库要求的后端测试、gofmt 检查和 golangci-lint。若修改 sqlc 查询或 schema，按仓库要求在 PowerShell 生成绑定并检查漂移；本期不计划 schema 迁移或对外生成契约变化。
- 规格定义验收边界；实际实现、检查结果及限制见 verification.md，不以规格状态替代运行证据。

## Out of Scope

- 前端资料拥有权、刮削弹窗和提案工作流复用，导航与页面调整。
- 全仓目录重组、Controller 全面拆分、统一数据库抽象、数据库分裂或新的部署单元。
- 路径、身份、封面、书入库规则、阅读进度、活动、书签、关系、合集和自定义字段的业务改动。
- 全局标签改名、合并、删除流程迁入新 module；作者字典功能扩展。
- 改变人工、批量、扫描或提案支持的字段，统一来源锁/空值策略，新增来源沿革或修改 provenance 意义。
- 修改内容指纹为自增版本、强化或放宽现有提案并发语义、重新加载快照以修复覆盖问题。
- 改变扫描错误容忍、批量事务范围、SQL 分块策略、扫描节流或刷新失败对结果的影响。
- 通用事件总线、持久化变更集、来源插件框架、万能 patch 协议和全站缓存重构。
- 修复走读发现的旁支缺陷、承诺代码行数下降比例、提前生成工单或开始实现。
