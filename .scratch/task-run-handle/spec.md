# Spec: 任务体干活的资格收进一个句柄

Status: ready-for-agent

## Problem Statement

**任务**引擎已经有了**唯一启动入口**：调用方交出一份任务声明与一个任务体，槽位、上下文、后台
goroutine、三条**终态**分支全部由引擎承担。但任务体**自己**干活时需要的东西没有跟着收口——
它的签名给两样，实际要凑四样：

| 它需要什么 | 今天怎么拿到 | 在签名上看得见吗 |
| --- | --- | --- |
| 写这个任务的进度 | 形参 `tp` | 看得见 |
| 取消 | 同一个 ctx 的 `Done()` | 看得见 |
| **暂停闸门** | 藏在 ctx 的 value 里，靠手写 `taskcontrol.Wait(ctx)` | **看不见** |
| **磁盘作业**（含**存储令牌**） | `c.diskWork.Do(...)`，经 Controller 接收者 | **看不见** |

三类可观察的损害：

**对维护者。** 后两样没有任何结构承载，因此每处都靠抄。全仓 21 处手抄的闸门调用里，13 处
（api 8、`koreader` 5）落在任务体这条线上。**磁盘作业**的实况更麻烦：`diskwork` 刻意把耗时做成
**返回值**，于是调用方必须自己声明一个 `taskIOMetrics`、自己在每次 `Do` 之后吸收、自己上报——
这段样板在四个任务体里各写了一遍。

**跨包时它彻底散架。** `taskIOMetrics` 与进度句柄都是 `api` 的未导出类型，跨不了包，
于是每个长活自己发明一个回调：**5 处长活、3 个包、2 种形状**——`koreader` 与 `external` 用
`progress func(current, total int)`，api 自己那两处用
`progress func(current, total int, metrics taskIOMetrics)`；而**磁盘作业**的实况只能靠
`RebuildOptions.AbsorbDiskWork func(diskwork.Stats)` 这个 options 字段手工穿回来。一个批循环
因此要同时收下两个协作方，而它们来自同一个句柄。

**对终端用户。** 两处哈希回填今天对同一个指标给出不同答案：`hashed_files` 在文件身份重建里
是在错误检查**之后**才 +1，在 KOReader 的**指纹**重建里是在**之前**。也就是说被闸门或令牌挡下、
一个字节都没读的书，在后者里被计入「已哈希文件数」。慢盘上这个数字与实物脱钩，而它是任务面板
上用户唯一能看到的吞吐量。

**对测试。** `koreader` 的批循环不变量——指纹算不出只跳过这一本、游标仍推进；中止只由**磁盘
作业**入口返回的错误决定——今天要驱动它必须造一个真的 `diskwork.Runner` 和一个新建的调度器。
`external` 的传输扫描同理。两处都在为一个它们其实不关心的东西付测试成本。

## Solution

新增一个叶子包，把任务体干活所需的三样资格收进**一个**交下来的句柄：写进度、过闸门、发起
**磁盘作业**。句柄在 `Do` 返回时自己吸收实况，调用方不再声明、不再穿参数。

调用方视角的变化：

- 任务体的协作方从「一个形参 + 一个 ctx-value + 一个接收者字段 + 一个手卷的累加器」变成**一个形参**。
- 跨包的长活只收下一个协作方，而不是两个加一个 options 字段。
- 「这个任务哈希了几本书」只有一个答案，与调用它的是哪一处无关。
- `koreader` 与 `external` 各自声明它们真正需要的那几个方法，于是它们的用例用一个手写假体就能驱动。

## User Stories

1. 作为维护者，我希望任务体只收下一个句柄就能干活，这样我不必记住另外三样东西藏在哪。
2. 作为维护者，我希望**暂停闸门**在任务体的签名上看得见，而不是藏在 ctx 的 value 里靠约定。
3. 作为维护者，我希望过闸门是句柄上的一个方法，这样我不必在 13 处各抄一遍同一行。
4. 作为维护者，我希望发起一次**磁盘作业**不必够到 Controller 接收者，这样多数任务体不再需要它。
5. 作为维护者，我希望**磁盘作业**的实况由句柄自己吸收，这样我不必声明累加器、也不会忘记吸收。
6. 作为维护者，我希望「已哈希文件数」的计数规则只有一份，这样两处回填不会各给一个答案。
7. 作为维护者，我希望这条计数规则不依赖错误的出处——入口把闸门错、令牌错与闭包自己的错从同一个
   值里返回，分不出来，而「闭包有没有执行」分得出来。
8. 作为维护者，我希望跨包的长活只收下一个协作方，这样「进度」与「实况」不会走两条路回来。
9. 作为维护者，我希望 `AbsorbDiskWork` 这个 options 字段消失——它是一个协作方被拆成两半之后
   留下的疤。
10. 作为维护者，我希望 `progress func(current, total int)` 这个形状在全仓只有一份含义，而不是
    三个包各写各的。
11. 作为维护者，我希望 `koreader` 与 `external` 只声明它们真正用到的那几个方法，这样签名本身
    就回答了「它到底要什么」。
12. 作为维护者，我希望 `koreader` 与 `external` 的用例能用一个手写假体驱动，不必造调度器。
13. 作为维护者，我希望 `koreader` 的批循环不变量（算不出只跳过、游标仍推进、中止只由入口的错误
    决定）有毫秒级的用例，而不是穿过真调度器。
14. 作为维护者，我希望 i18n 码与**阶段**字面量继续留在 `api`，这样 `koreader` 不必认识文案。
15. 作为维护者，我希望句柄上那些零调用点的方法不要跟着搬进新包，这样新包的接口能完整读进上下文。
16. 作为维护者，我希望句柄的 doc 与事实相符——今天那句「日常上报请用 Advance / Phase / Item /
    Metrics / Labels」把两个零调用点的方法称作主用法。
17. 作为维护者，我希望句柄的全部方法都能从任意 goroutine 调用，这样我不必记住哪几个不行。
18. 作为维护者，我希望日后某个任务体把**磁盘作业**放进 goroutine 时不会静默出错。
19. 作为维护者，我希望**任务句柄**这个概念在词汇表里有名字，因为**进度句柄**已经盖不住它了。
20. 作为维护者，我希望这次不碰 `scanner`，因为它的扫描有四条不属于任何**任务**的入口。
21. 作为 AFK agent，我希望新增一个任务体时只需要认识一个类型，这样我不会遗漏那些没有编译期约束的步骤。
22. 作为 AFK agent，我希望新增一处跨包长活时，「它需要什么」写在需要它的那一侧。
23. 作为终端用户，我希望任务面板上的「已哈希文件数」等于真正被读过的书数，而不是被排队挡下的也算。
24. 作为终端用户，我希望其余任务的进度、文案、**终态**与并发徽章逐字不变。
25. 作为运维者，我希望限流与暂停的行为完全不变——这次只搬取用方式，不动 `diskwork` 与 `taskcontrol`。

## Implementation Decisions

### 深化后的模块与接口

**新模块**：一个叶子包，位于 `diskwork` 与 `taskcontrol` 之上、`api` 之下，由 `api` 构造，
`koreader` 与 `external` 只经各自声明的窄接口看见它。它不认识**任务键**、**作用域**与**终态**——
那些仍属于引擎。

**接口形状**（形状来自本次盘问，比散文更精确地编码了决定，故内联）：

```go
type Frame struct {
    Current *int
    Total   *int
    Phase   string
    Item    string
    Code    string
    Params  map[string]string
    Metrics map[string]int64
    Labels  map[string]string
}

type IOMetrics struct {
    StorageProfile string
    VolumeKey      string
    IOWaitMillis   int64
    PausedMillis   int64
    HashedFiles    int64
}

func New(
    report      func(Frame),
    mergeParams func(map[string]string),
    addMetrics  func(map[string]int64, map[string]string),
    disk        *diskwork.Runner,
) *Handle

func (h *Handle) Report(f Frame)
func (h *Handle) Advance(current, total int, code string, params map[string]string)
func (h *Handle) Phase(phase, code string, params map[string]string)
func (h *Handle) MergeParams(params map[string]string)
func (h *Handle) AddMetrics(increments map[string]int64, params map[string]string)
func (h *Handle) Checkpoint(ctx context.Context) error
func (h *Handle) Disk(ctx context.Context, w diskwork.Work, fn func() error) error
func (h *Handle) IOMetrics() IOMetrics
```

`Frame` 与今天的 `TaskFrame` 字段一致。零调用点的是 `Item` 与 `Labels` 这两个**写入方法**，
不是同名字段——`Item` 有 5 处、`Labels` 有 3 处生产写入点（扫描观察者、重建缩略图逐库观察者、
传输扫描、ComicInfo 写回、哈希进度）都经整帧上报走这两个字段。删字段会让任务面板的**当前条目**
与 `current_library` / `storage_profile` 等标签停止更新，那是一次没人要的对外行为变更。

### 关键决定

1. **只收任务体这条线上的取用点：`api` 的 17 个任务体、`koreader` 的 5 处调用、`external` 的
   1 处。`scanner` 一行不动。** 它的扫描有四条不属于任何**任务**的入口（watcher 派生的扫描、
   建库后的首扫、守护扫描、维护扫描），词汇表已把这条写进**扫描观察者**词条。句柄覆盖不到它们，
   因此 `scanner` 必须保留 `s.diskWork` 直连；给它开双入口等于让「走哪条」变成每个取用点要记的事，
   而走错不会有编译错误——那正是 `diskwork` spec 的关键决定 2 拒绝过的逃生舱。手抄的闸门调用
   因此从 21 处降到 8 处，**不会**归零，本次不追求归零。

2. **构造期注入三个函数值，不开接口。** 沿用 `newTaskEngine` 与 `diskwork.NewRunner` 的形状：
   用例里三行就能桩掉，且**任务键**由闭包在引擎侧绑定，句柄上不再出现它。给接口加 `key` 形参会
   把「谁有资格写由谁拿到句柄决定，而不是谁会拼那个字符串」这条结构约束重新打开。

3. **`Disk` 吸收，任务体显式取用。** 句柄持累加器，`Do` 返回时自动折进去；何时报仍由任务体决定
   （`IOMetrics()`）。不做「每一帧自动折进去」：那会让指标何时出现变成隐式的，而且参数那条旁路
   会从「逐库报文」这种低频路径变成逐帧，与它自己的 doc 相悖。

4. **`hashed_files` 的计数规则：工种是 `identity_hash` 且闭包真的执行了。** 实现上句柄包一层
   闭包记录 `ran`，不靠错误的出处判断——入口把闸门错、令牌错与闭包自己的错从同一个值里返回，
   分不出来。这条统一到今天文件身份重建的口径；**KOReader 的指纹重建是唯一的对外行为变更**，
   它今天在错误检查之前就 +1，因此把被挡下的书也算作已哈希。

5. **`koreader` 与 `external` 各自声明窄接口，两包都不 import 本模块。** `koreader` 声明三个
   方法（计数推进、过闸门、发起磁盘作业），`external` 声明一个（计数推进）。`*Handle` 结构化
   满足它们。这是 `external.Store` 那条已经用过的路子，changelog 也写过「Go 接口是结构化满足的，
   调用方今天就能自建窄接口」。

6. **每个任务自己的帧构造留在 `api`，用嵌入句柄的小适配器承载。** 跨包的计数推进只报两个数字，
   而一次 tick 要翻成哪一帧（哪个**阶段**、哪个 i18n 码、带不带 IO 指标）是 `api` 的事——
   `external.ScanSession` 的 doc 已经写明本包渲染文案会让英文用户看到中文。适配器嵌入 `*Handle`
   并只遮蔽计数推进那一个方法，过闸门与发起磁盘作业由嵌入白拿。写法与 `proposalDB` 遮蔽内嵌
   `Store` 的 `ExecTx` 同款。按帧构造分，适配器不超过四种。

7. **零调用点的三个上报方法不跟着搬。** `Item`、`Labels` 与 `Metrics` 在生产代码里各有 0 个
   调用点（这三样都只在整帧上报里出现，走的是 `Frame` 的同名字段而非方法）。`Phase`（6）与
   计数推进（1）保留——它们分别编码词汇表里**阶段**与**计数推进**这两个相互独立的概念，
   不是凑数的转发。今天那句把 `Item` / `Labels` 称作「主用法」的 doc 一并修正。

8. **累加器加互斥锁，句柄整体并发安全。** 上报那几个方法今天就会从任务体之外的 goroutine 被调用
   （**扫描观察者**把封面队列的报文写进来，见 ADR-0002），而累加器是新增的可变状态。加锁之后
   「这个句柄怎么调都行」一句话说完，不必留一条只写在注释里、跨过去也不报错的分界线。锁的开销
   相对它包着的一次整文件读取可忽略。

9. **`TaskRuntime` 不动。** 它是引擎内部登记的 ctx + 闸门 + cancel，供暂停/恢复/取消接口操作，
   **刻意从不交给任务体**。它在代码里已经叫**运行时句柄**——本次的新类型不得复用这个名字。

10. **引擎的启动入口、槽位申领、终态裁决、重启函数注册表全部不动。** 本次只改任务体收到什么。

### 词汇表

新增**任务句柄 (Task handle)**：任务体干活所需的全部资格——写这个任务的进度、在可中断点询问
**暂停闸门**、发起**磁盘作业**。任务体拿到它才能做这三件事，而不是谁拼对了**任务键**谁就能做。
_Avoid_: 进度句柄、回调、reporter。

同时**删除**旧词条**进度句柄 (Progress handle)**：它的外延已被上述词条覆盖，让一个词同时指
两者正是词汇表的 _Avoid_ 纪律要防的。原词条那句核心论断（资格由「谁拿到它」决定）原样继承。

### 迁移

分批提交，但旧接口的删除必须落在**同一个 PR** 内。理由沿用 `diskwork` 那次：本仓接口里那条
「i18n 码版／字面量版」的疤，就是一次停在半路的迁移冻结进签名的产物。

提交顺序：

1. 新包、完整接口、契约用例；`TaskProgress` / `TaskFrame` 机械搬迁；删掉三个上报方法；
   词汇表落地。零行为变化。
2. **`koreader`**——最难的排第二位，不留到最后。它是这套形状的证伪点：若嵌入式适配器装不下
   帧构造、或跨包读累加器不成立，要在第二个提交就暴露，而不是转完四处之后。它同时门控其余批次。
   **本次唯一的对外行为变更也在这里落地。**
3. `api` 自己的 8 处闸门与 2 处磁盘作业改走句柄。
4. `external` 的窄接口与 1 处适配器。
5. 删除 `taskIOMetrics` 与它的三个方法、`AbsorbDiskWork` 字段、三个 `progress` 形参；
   `CHANGELOG.md` 记一条对外行为变更。

## Testing Decisions

**什么是好测试**：只断言外部可观察的行为——交给注入函数的帧内容、闭包是否被执行、
`IOMetrics()` 的返回值、调度器快照里那块卷的在用数。不断言内部字段布局、不断言方法调用次数。

**唯一的新接缝**：新模块的构造点，注入三个记录用的桩函数与一个新建调度器上的 `diskwork.Runner`。
契约用例全部压在它上面，无数据库、无引擎、无文件树。

**契约用例**：

- **计数规则**：工种是 `identity_hash` 且闭包执行 → `hashed_files` 为 1；闭包未执行（闸门暂停、
  上下文已取消）→ 仍为 0；其余工种执行了也不计。（今天零覆盖，且本次改行为——这是最该写的一条。）
- **吸收**：等待与暂停时长累加；存储档位与卷键取最后一次非空的那次，闸门挡下的零值不覆盖已有值。
- **闸门先于令牌**：上下文携带的闸门处于暂停态时，`Disk` 的闭包不执行，且不占用令牌槽位。
- **过闸门**：暂停态阻塞、恢复后放行；上下文已取消时返回取消错误。
- **上报**：整帧上报、计数推进、**阶段**三条各自交给注入函数的 `Frame` 内容；合并参数与累加指标
  走各自那个函数。
- **并发**：`-race` 下，一个 goroutine 反复 `Disk`、另一个反复上报与读 `IOMetrics()`，不报竞态。

**下沉的用例**：`koreader` 与 `external` 包内改用手写假体驱动窄接口，于是这两组用例不再需要
`storageio.NewScheduler()` 与真 `diskwork.Runner`。借此把两条今天没有直接用例的批循环不变量补上：
**指纹**算不出只跳过这一本、游标仍推进（游标停住即死循环）；中止只由磁盘作业入口返回的错误决定。

**`api` 侧保留的用例**：适配器把一次 tick 翻成哪一帧——包括 IO 指标进整帧、参数走另一条通道。
既有的终态、文案码、并发徽章、任务键闸门用例原样继续绿。

**先例**：`internal/diskwork/runner_test.go` 是最贴近的一组——新建调度器、断言快照与闭包是否
执行、契约压在构造点上，本次照它的形状写。`internal/taskcontrol/pause_gate_test.go` 给出了驱动
暂停态的写法。`internal/api/task_engine_seam_test.go` 给出了「把后台执行换成同步执行、观测面
固定为投递出去的载荷」这套装置，`api` 侧的适配器用例继续压在它上面。

**回归面**：三个包的既有用例照跑。除**指纹**重建的 `hashed_files` 之外行为等价；
该变更由上述计数规则用例覆盖，不为它新增端到端用例。

## Out of Scope

- **`scanner` 的 5 处磁盘作业与 8 处闸门调用**。见关键决定 1：它有四条不属于任何**任务**的扫描
  入口，句柄覆盖不到，本次一行不动。
- **`diskwork` 与 `taskcontrol` 自身**：限流规则、上限表、闸门实现与它挂在上下文上的方式。
- **引擎的启动入口、槽位申领、终态裁决、异步落盘、投递节流、重启函数注册表**（ADR-0001）。
- **`TaskSpec` 的 14 个字段**，以及它记录在案的四对「接反不会有编译错误」（起始文案参数与任务参数、
  声明期标签与运行期标签、零值上限与零上限、三条默认终态码与单条覆盖）。那是另一条候选。

## Further Notes

- 词汇以仓库根部的领域词汇表为准，特别是本次新增的**任务句柄**词条与随之删除的**进度句柄**。
- 盘问中查实、值得在动手时确认的四件事：
  1. **运行时句柄**这个名字是占用的——它指 `TaskRuntime`，且刻意从不交给任务体。新类型不得叫它。
  2. `Item`、`Labels` 与 `Metrics` 三个方法在生产代码里各有 0 个调用点，而句柄的 doc 把前两个
     称作「主用法」。整份上报面的真实分布是：整帧上报 24、**阶段** 6、合并参数 4、
     **计数推进** 1、累加指标 1。**同名的 `Frame` 字段另算，它们有生产写入点，不得跟着删。**
  3. 两处哈希回填对 `hashed_files` 的口径今天就不一致，且没有任何用例守着这条差别。
  4. `external.ScanSession` 的 doc 已经写明它的进度回调刻意不带展示文案——那条理由原样适用于
     本次的窄接口，不必重新论证。
- `koreader` 的 5 处调用点分布在 4 个任务体上（**指纹**重建、进度对账、匹配刷新——它两样都用、
  低优先级哈希回填），因此适配器按帧构造分而不是按任务分。
