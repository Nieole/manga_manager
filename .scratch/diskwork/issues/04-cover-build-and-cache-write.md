# 04 — 封面构建与缓存写入改走磁盘作业模块

**What to build:** 扫描器剩下的两处**磁盘作业**改走新入口：从归档里读出封面那一页，以及把处理好的缩略图写进缓存目录。

缓存写入带来 `PolicyFrom` 的第一个生效路径。存储策略按**路径前缀**匹配资料库，而缓存目录通常落不进任何资料库的前缀、只能拿到全局默认档——可它和藏书在同一块盘上转。规则因此是：字节落在哪决定卷键，和谁抢同一块盘决定策略。

**本票带来唯一的对外行为变更**：用户按下暂停后，后台不再继续往盘上写缩略图。今天从上一次闸门检查到落盘之间隔着整个图片转码，暂停在这一段是不生效的。

## Comments

扫描器四处**磁盘作业**至此全部走完新入口，`acquireStorageToken` 在扫描器里只剩票 06 要删的那条
用例还在调用它。

本票新增了票面未要求的两条用例（`cover_build_test.go`）。封面构建的两条失败出口——归档打不开、
封面那一页读不出——此前**零覆盖**，而这一票删掉的正是守着它们的那个手写幂等归还闭包。用外置
硬盘档把封面并发压到 1（封面 worker 也随之只剩一个），漏掉的令牌会让坏档后面那本永远等不到
令牌。守卫有效性已实测：把 `defer releaseSourceToken()` 摘掉再跑，两条子用例都挂到超时后失败。

写缩略图那处的**暂停闸门**按 spec 不新增端到端用例——它由票 02 的契约用例（闸门先于令牌）覆盖。

两处偏离：

1. **`writeThumbnailFile` 收窄成一个纯 IO 的自由函数**：`(thumbDir, fullPath, data)
   (time.Duration, error)`，不再有接收者、`ctx`、`cfg` 与存储策略。`Do` 的调用与两处指标折算
   都留在 `generateBookThumbnail`，与前三处已迁移的取用点同形（`Do` → `absorbDiskWork`
   紧贴在调用点上）。这比「把 `metrics` 下沉进去吸收 `Stats`」更少分叉：那样同一个指标对象会被
   两处各折一半。作为副产品，「Queued thumbnail cache write completed」那条日志原地不动，
   字段集与触发条件（落盘或等令牌任一 ≥250ms）都不变。
2. **封面构建申领失败时的等待与暂停耗时现在也汇入指标**（旧代码在 acquire 出错时先 return，
   丢弃这两项）。与票 02 comment 3、票 03 comment 2 同因。缓存写入那处旧代码本就折算，不变。

一处不算偏离、但值得记下的口径修正：那条日志的 `storage_profile` 旧值恒取**藏书**那一侧的档位，
即使缓存目录在另一块盘上也照报；现在取模块返回的 `Stats`，即真正管住这次写入的那一档。
`volume_key` 由 `VolumeKey(fullPath)` 改为 `Stats.VolumeKey`（即 `VolumeKey(thumbDir)`），
同卷，值不变。
