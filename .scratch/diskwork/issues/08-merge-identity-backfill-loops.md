# 08 — 两份一模一样的指纹回填循环合成一处

**What to build:** 低优先级的全量哈希回填（`api.runBackfillFullHashesLowPriority`）在 `api` 里
重抄了一遍 KOReader 的**指纹**重建（`koreader.RebuildBookIdentities`）：数缺口 → 按游标切批 →
读一遍文件 → 回填 `file_hash`。票 07 抹平了两者最后一处差异——取不取**存储令牌**——之后，两段
代码完全同形。把循环留在 `koreader`（它本就拥有指纹），`api` 那份收成一个薄适配器。

节奏差异经一个选项结构表达，而不是靠第二份实现：批大小、批间停顿、匹配模式、实况沉降口。

用户侧无可观察变化：这是一次行为等价的合并。

**Blocked by:** 07 —— 它抹平的那处差异正是本票合并的前提；两票同一个 PR，理由沿用票 06：
停在半路的重复迟早各自漂移，而这一次的重复是票 07 自己造成的。

## Comments

循环留在 `koreader`，节奏差异经 `RebuildOptions` 表达：`BatchSize`、`BatchGap`、`MatchMode`、
`AbsorbDiskWork`。`api` 那份从 72 行的批循环收成 16 行适配器，只留自己的任务指标与两个节奏
常量。没有新增包间依赖：`api` → `koreader` 本就存在。副产品是票 07 评审提出的 Data Clumps
一并消失——两个结伴的回调里，实况沉降口进了选项，`progress` 仍是尾参。

`MatchMode` 钉住二进制哈希而不是跟着配置走，是刻意的行为保持：这个任务由**资料库扫描**收尾时
按「缺全量哈希的书有几本」发起，任务声明里报的也是这一档；跟着配置走的话，配置在发起与开跑
之间被改成路径模式，它就会掉头去写路径指纹、总数也换成另一批书。

三处不可观察的差异：坏书的警告文案统一成一条（已记进 CHANGELOG）、每本前多过一道**暂停闸门**
（二进制模式下与 `Do` 的闸门重复，路径模式下本就有）、`HashedFiles` 的计数时点从「`Do` 成功后」
移到沉降口里（只在申领失败那一次差一个计数，而那一次之后不再有进度上报）。

新增两条守卫，都是这次搬迁真正可能弄丢的东西：批间停顿（此前**零覆盖**，两处调用都传 0）与
「回填按哪一档盘算缺口」。守卫有效性实测：把停顿短路掉，那条用例失败；摘掉 `MatchMode`，
另一条报出 `file_path`。
