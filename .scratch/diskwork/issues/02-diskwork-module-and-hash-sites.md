# 02 — 磁盘作业模块落地，两处哈希先走通

**What to build:** 新增一个模块，对外只暴露**一个**入口：调用方交出一份**磁盘作业**声明（干哪一类活、字节落在哪）和一个闭包，模块负责其余全部——过**暂停闸门**、解析存储策略、按工种定并发上限、申领与归还**存储令牌**、等待过久时的观测，以及把等待与暂停的耗时作为**返回值**交回。

扫描器的全量哈希与快速哈希两处作为第一发曳光弹完整走这条新路径：它们是形状最干净的两处——取令牌、干一件事、立刻还。

新模块位于 `config`、`storageio`、`taskcontrol` 三个叶子包之上，由扫描器与 api 共用。旧的取令牌辅助方法原样保留，其余六处取用点一行不改，CI 全绿。

下列形状来自本次改造前的盘问，比散文更精确地编码了已定的决定，故内联：

```go
type Work struct {
    Kind       storageio.WorkKind
    Path       string  // 字节落在哪 → 决定卷键
    PolicyFrom string  // 与 Path 同卷时，IO 策略改从这个路径解析；留空表示同 Path
}

type Stats struct {
    Wait, PausedWait          time.Duration
    StorageProfile, VolumeKey string
}

func NewRunner(cfg func() config.Config, sched *storageio.Scheduler) *Runner
func (r *Runner) Do(ctx context.Context, w Work, fn func() error) (Stats, error)
```

`PolicyFrom` 本票只需存在并在留空时按 `Path` 解析；它的生效路径由票 04 带来。

## Comments

三处偏离验收清单字面的取舍，留给后续票：

1. **`PolicyFrom` 一次实现到底**，含同卷判定与卷键改回 `Path` 的分支，并配两条用例。本票只要求
   「存在并在留空时按 `Path` 解析」，但一个被声明却被静默忽略的字段是个陷阱——票 04 只需接上
   调用点。
2. **两处指纹的 `progress.publish("hashing", …)` 现在跑在闸门之前**（原为手抄闸门 → publish）。
   这两处的手抄闸门正是 spec「手抄闸门从 29 降到 23」要消掉的，顺序变化是它的必然结果；
   `publish` 本身有 250ms 节流，阶段字符串与紧随其后的那次一致。
3. **超时等待的日志放在申领错误检查之前**：等了很久最终被取消的申领也要留下记录，那正是慢盘上
   最该看见的一种。用例覆盖了取到令牌与排队中被取消两条路径。
