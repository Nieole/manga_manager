# Spec: 把一次磁盘作业收进一个模块

Status: done

## Problem Statement

后台**任务**每动一次磁盘，都要自己搭一遍同一套仪式：解析存储策略 → 按工种挑并发上限 →
申领**存储令牌** → 过**暂停闸门** → 干活 → 归还令牌 → 把等待与暂停的耗时折进指标。
全仓八个取用点各抄一份，`scanner` 与 `api` 还各自维护了一份取令牌的辅助方法（分别返回 4 元组与
5 元组）与一份逐字相同的「取正最小」函数。

这带来三类可观察的损害：

**对维护者。** 这套流程的正确性完全依赖「抄对」，而漏掉任何一步都不会有编译错误：漏了闸门，
任务暂停不了；漏了归还，那块盘的并发额度永久少一格；顺序反了（先取令牌再过闸门），
一个被暂停的任务会攥着令牌把别人堵死。已经留下的手工补丁能说明代价——两处为「提前归还 +
兜底归还」各手写了一个幂等布尔，一处为「取到令牌之后、干活之前再看一眼取消」手写了
`select`。此外还有两条只写在注释里、没有任何结构承载的顺序约束：闸门必须放在数据库遍历
**之后**（回调期间游标是开着的），以及取封面路径的回调里**不得**过闸门（会把一个数据库连接
按住不放）。

**对终端用户。** 同一个工种在两个包里拿到**两个不同的并发上限**——`identity_hash` 在扫描器
里是 min(扫描并发, 哈希并发)，在维护任务里是 min(哈希并发, 归档打开并发)；`metadata_scan`
同样分叉。「这个工种在这块盘上能并发几个」今天取决于调用它的是哪个包，而不是取决于工种。
另有两处直接的体验缺陷：写缩略图文件那一处从上一次闸门检查到落盘之间隔着整个图片转码，
用户按下暂停后它仍会继续往盘上写；而「等令牌等了很久」这条日志今天只有封面构建一处有，
扫描与哈希卡在令牌上是**无声**的。

**对测试。** api 侧的取令牌辅助方法与两份上限公式**零覆盖**——而本次恰恰要改上限的行为。
扫描器侧唯一相关的那条用例伸手进未导出的取令牌方法、靠固定时长的 sleep，测的其实是
`storageio` 自己的语义（同卷、上限 1、第二个要等），而 `storageio` 已有一条等价用例。
真正属于这一层的两条不变量至今零覆盖：令牌在**每条**出口（含闭包 panic）都被归还、
闸门先于令牌。

## Solution

新增一个模块，对外只暴露**一个**入口：调用方交出一份**磁盘作业**声明（干哪一类活、字节落在
哪）和一个闭包，模块负责其余全部——过闸门、解析策略、按工种定上限、申领与归还令牌、
等待过久时的观测，以及把等待与暂停的耗时作为**返回值**交回。

调用方视角的变化：

- 动一次磁盘从「七步仪式包着一层活」变成「一次调用包着一层活」。
- 「这个工种能并发几个」由工种单独决定，与调用方是谁无关。
- 令牌的归还不再是调用方要记得写的事，也不再需要发明幂等归还闭包。
- 等待与暂停的耗时是返回值，不是副作用；调用方只剩一行「把它折进我的指标」。

## User Stories

1. 作为维护者，我希望动一次磁盘只需要一次调用并把活写在闭包里，这样我不必记住七步顺序。
2. 作为维护者，我希望令牌的归还由模块保证，这样我不必在每条出口手写归还，也不会因为漏写而
   让那块盘的并发额度永久少一格。
3. 作为维护者，我希望闭包 panic 时令牌也必定被归还，并且这条路径有用例覆盖。
4. 作为维护者，我希望「提前归还 + 兜底归还」不再需要我发明一个幂等布尔——它是模块内部
   一个 `defer` 的事。
5. 作为维护者，我希望**暂停闸门**在取令牌**之前**被结构性地保证，这样「被暂停的任务攥着令牌
   把别人堵死」在结构上写不出来。
6. 作为维护者，我希望取令牌之前必然先看一眼取消，这样我不必手写 `select`，也不会浪费一个
   令牌槽位去执行一段马上要被丢弃的活。
7. 作为维护者，我希望「这个工种能并发几个」只有一个答案，这样我不必先判断自己身处哪个包。
8. 作为维护者，我希望上限公式有用例覆盖，这样改动它是一次会变红的改动，而不是一次静默的
   性能变更。
9. 作为维护者，我希望等待与暂停的耗时是**返回值**，这样为这个模块写用例只需断言返回值，
   不需要探针。
10. 作为维护者，我希望取用点上只剩一行「把耗时折进我的指标」，`nil` 守卫沉进那个方法里。
11. 作为维护者，我希望取令牌的辅助方法与挑上限的函数在全仓只有一份。
12. 作为维护者，我希望缓存写入「与藏书同盘时服从藏书那一侧的策略」这条规则写在模块里，
    因为它是关于磁盘作业的规则，不是某个调用点的怪癖。
13. 作为维护者，我希望为这个模块写用例时不需要数据库、文件树与扫描器，这样一条契约用例是
    毫秒级的。
14. 作为维护者，我希望用例里的令牌调度器是独立的，这样用例之间不会经由按卷计数的限流器
    互相污染。
15. 作为维护者，我希望不再有任何用例伸手进扫描器未导出的取令牌方法。
16. 作为维护者，我希望日后要为策略解析加缓存时，八个取用点一行都不用改。
17. 作为 AFK agent，我希望新增一处磁盘作业时只需要写「干哪一类活、字节落在哪」两样东西，
    这样我不会遗漏那些没有编译期约束的步骤。
18. 作为 AFK agent，我希望这个模块的接口小到可以完整读进上下文。
19. 作为终端用户，我希望按下暂停之后，后台不再继续往盘上写缩略图。
20. 作为终端用户，我希望所有后台磁盘作业在限流上表现一致，而不是取决于它由哪个子系统发起。
21. 作为终端用户，我希望在慢盘上排队等令牌时，日志里能看到是哪一类作业在等、等了多久——
    不只是封面构建那一类。
22. 作为终端用户，我希望前台的阅读取页继续优先于一切后台作业，且**不**受任何任务的暂停影响。
23. 作为终端用户，我希望默认配置下的行为完全不变——不取令牌、不排队。
24. 作为运维者，我希望手工把某个库的四项并发配成不同正值时，生效的那一项是与该工种真正
    相干的那一项。

## Implementation Decisions

### 深化后的模块与接口

**新模块**：一个独立的包，位于 `config`、`storageio`、`taskcontrol` 三个叶子包之上，由
`scanner` 与 `api` 共同使用。三个依赖包今天彼此零依赖，因此不成环。

**不放进 `storageio`**：那会一次踩碎该包文档里明写的三句边界——它不认识资料库与路径策略、
何时取令牌由调用方决定、单个任务的暂停闸门与后台 IO 暂停是两件事。新模块恰好要做的正是
这三件被排除的事，所以它是**上面一层**，不是那一层的扩张。

**接口形状**（形状来自本次盘问，比散文更精确地编码了决定，故内联）：

```go
type Work struct {
    Kind       storageio.WorkKind
    Path       string  // 字节落在哪 → 决定卷键
    PolicyFrom string  // 与 Path 同卷时，IO 策略改从这个路径解析；留空表示同 Path
}

type Stats struct {
    Wait, PausedWait          time.Duration
    StorageProfile, VolumeKey string
}

func NewRunner(cfg func() config.Config, sched *storageio.Scheduler) *Runner
func (r *Runner) Do(ctx context.Context, w Work, fn func() error) (Stats, error)
```

### 关键决定

> **计数修订**：本节写作时按 `scanner` 与 `api` 两个包清点，得数「八处」。KOReader 的书籍指纹
> 重建（`koreader` 包）也是一次**磁盘作业**，写这份 spec 时就已漏掉——实为**九处**，第九处由
> 票 07 收进来，票 08 顺势把它与低优先级回填的重复合掉。下文的「八处」「两个包」照原样保留，
> 它们记的是这份计划当初的样子。

1. **只收后台的八处磁盘作业**。前台的阅读取页维持直接向调度器申领：它不过暂停闸门、
   它的上下文是刻意去掉取消的、它的耗时进请求诊断而非任务指标。把它收进来只会换得一个
   「这几件事都反着来」的开关，那正是**浅**的定义。词汇表已把这条排除写进**磁盘作业**词条。

2. **单一闭包入口，不留句柄式逃生舱**。八处的令牌持有区间无一需要跨函数边界存活，闭包
   装得下全部。逃生舱一开，第 4 条统一掉的上限立刻可以被绕过而不报错。

3. **闸门先于令牌，收进入口内部**。八处里七处今天已被闸住（六处紧贴、封面构建那处在上一层
   帧）。唯一的行为变化是写缩略图文件那处新增一次闸门检查——那是修正，不是回归。
   闸门在未暂停时返回上下文错误，因此这一步同时是取消检查。

4. **上限由工种单独决定**，调用方不再传。生效的那一项按「这个工种到底在干什么」裁定：

   | 工种 | 它在干什么 | 生效上限 |
   | --- | --- | --- |
   | `metadata_scan` | 打开归档读元数据 | 归档打开并发 |
   | `identity_hash` | 直接流式读整个文件，**不开归档** | 哈希并发 |
   | `cover_build` | 打开归档读一页 | min(归档打开并发, 封面并发) |
   | `cache_write` | 写缓存文件，不开归档 | 封面并发 |

   两个包今天各自额外与之取小的那一项（扫描并发 / 归档打开并发）都是各自语境的产物：
   前者是「这次扫描的总闸」而维护任务根本不是扫描，后者对一个不开归档的哈希完全不相干。

5. **耗时是返回值，不是副作用**。模块不持有、不上报任何指标；两个包各自实现一个吸收
   `Stats` 的方法（扫描器那份用原子加，api 那份直接加），接收者为 `nil` 时直接返回，
   于是取用点上的 `nil` 守卫也一并消失。**不**在模块上开指标接缝——模块这一侧没有变化点，
   它永远只产出同样四个值；两份吸收实现是**调用方**的差异，不该反映成模块的接口。

6. **`PolicyFrom` 承载「同盘则服从源」这条规则**。存储策略按**路径前缀**匹配资料库，
   而缓存目录通常落不进任何资料库的前缀、只能拿到全局默认档——可它和藏书在同一块盘上转。
   规则因此是：字节落在哪决定卷键，和谁抢同一块盘决定策略。不提供「传入已解析的策略」
   这条旁路，那等于给第 4 条开后门。

7. **构造期注入两样能力**：一个读取当前配置的函数、一个令牌调度器。配置用函数而不是配置
   管理器——两个包的取配置方法逐字相同，交出这个函数即可，用例里一行就能桩掉。调度器必须
   注入：沿用包级实例会让用例经由按卷计数的限流器互相污染，而 `storageio` 自己的用例
   全部新建调度器，本仓早已用脚投过票。生产构造点三个（扫描器一个、控制器一个，以及
   KOReader 服务一个——它由控制器构造，转交控制器已建好的那个 `Runner`），都传包级实例。

8. **「等令牌等了很久」的观测收进模块**，统一对八处生效。今天这条日志只存在于封面构建
   一处——最不关键的那一处——而扫描与哈希卡在令牌上反而无声。它是关于磁盘作业的事实，
   不是关于缩略图的事实。

9. **每次调用重新解析策略**，不做缓存、不加「先绑定再执行」的两步形状。一次调用比今天多
   两次小结构体克隆，而它守着的是打开归档并读完整个文件——量级差三四个数量级。日后若
   profile 真指到这里，缓存可以整个塞进实现内部，八个取用点一行不动。

10. **归档打开那一处顺带修掉一处虚占**。今天令牌被握着多跑了一段纯 CPU 的路径解析与排序号
    提取，虚占归档打开的并发额度。闭包会把持有区间钉死在真正的 IO 上，这段挪出去是重构的
    自然结果。

11. **保持不变的不变量**：默认档与 SSD 档下四项并发全为零，取正最小得零，因此**不取令牌**——
    这条短路必须原样保留，它是绝大多数部署的实际路径。

### 迁移

分批提交，但两份旧辅助方法与两份旧上限函数的删除必须落在**同一个 PR** 内。理由沿用任务引擎
那次：本仓接口里那条「i18n 码版／字面量版」的疤，就是一次停在半路的迁移冻结进签名的产物。

提交顺序：

1. 新模块、作业声明、上限表、契约用例；两个生产构造点接上；只转**两处哈希**
   （形状最干净：取令牌 → 干一件事 → 立刻还）。
2. **归档打开那一处**——最难的排第二位，不留到最后。它是这套形状的证伪点：若闭包装不下
   「令牌跨打开、读页目录、读 ComicInfo、关闭，且要把纯 CPU 段挪出持有区间」，要在第二个
   提交就暴露，而不是转完六处之后。它同时门控其余全部批次。
3. 封面构建与缓存写入两处（含 `PolicyFrom`）；`SameVolume` 的调用点随之消失，
   写缩略图那个函数的四元组签名收窄。
4. api 侧三处（维护任务两处、ComicInfo 回写一处）。
5. 删除两份取令牌辅助方法与两份上限函数；删除下述那条用例；`CHANGELOG.md` 记两条对外
   行为变更。

## Testing Decisions

**什么是好测试**：只断言外部可观察的行为——入口的返回值、闭包是否被执行、调度器快照里
那块卷的上限与在用数。不断言内部字段布局、不断言方法调用次数。

**唯一的新接缝**：新模块的构造点，注入一个新建的调度器与一个桩配置函数。契约用例全部压在
它上面，无数据库、无文件树、无扫描器。

**契约用例**：

- **上限表**：四个工种各一条。闭包执行期间，调度器快照里该卷的上限等于表里那一项。
  （今天零覆盖，且本次改行为——这是最该写的一条。）
- **短路**：上限为零或卷键为空时不取令牌，闭包照常执行。
- **闸门先于令牌**：上下文携带的暂停闸门处于暂停态时，闭包不执行，且**不占用**令牌槽位。
- **取消**：上下文已取消时返回取消错误，闭包不执行。
- **归还的必然性**：闭包返回错误、以及闭包 panic，两条路径上快照的在用数都回零。
- **`Stats` 如实返回**：等待与暂停时长、存储档位与卷键。

**删除一条用例**：扫描器里那条守「同卷、上限 1、第二个要等」的用例。它守的是 `storageio`
自己的语义，而该包已有一条等价用例；它今天还是从扫描器内部、伸手进未导出方法、靠固定时长
sleep 去测另一个包的行为。删掉之后，扫描器包内不再有任何用例触碰取令牌的内部。

**不新增第二个接缝**：调度器**不**抽成接口。它的快照已经把「实际要到的上限」与「在用数」
暴露出来，用真调度器就能断言全部契约——「一个适配器是假想接缝」这条在这里成立。

**先例**：`storageio` 自己的那组用例——全部新建调度器、断言快照与阻塞时序，是本仓这一层
最快也最精确的一组。契约用例照它的形状写。`taskcontrol` 的那组用例给出了驱动暂停态的写法。

**回归面**：扫描器与 api 的既有用例照跑。八处里七处行为等价；唯一的行为变更是写缩略图文件
前新增一次闸门检查，由上述契约用例覆盖，不为它新增端到端用例。

## Out of Scope

- **前台阅读取页的取令牌**。它不是**磁盘作业**（见词汇表），维持直接向调度器申领。
- **另外 23 处 `taskcontrol` 的闸门调用**。它们是循环顶部的取消/暂停检查，附近没有磁盘
  动作。手抄的闸门调用总数会从 29 降到 23，**不会**归零，本次不追求归零。
- **`storageio` 自身**：排队规则、阅读优先、后台整体暂停、快照结构、包级实例的存在。
- **`taskcontrol` 自身**：暂停闸门的实现与它挂在上下文上的方式。
- **策略解析的缓存**。见关键决定 9：日后可整个塞进实现，届时接口不变。
- **封面队列的所有权与关闭**（今天由 `sync.Once` 懒建、无人关闭、扫描器上没有停止方法）。
  它与本次相邻但正交，是另一条候选。
- **两条只写在注释里的顺序约束**（闸门必须在数据库遍历之后、取封面路径的回调里不得过闸门）。
  它们约束的是那 23 处独立闸门调用，不是磁盘作业，本次不动。
- **配置结构、落盘结构、线上契约、前端任何代码。**

## Further Notes

- 词汇以仓库根部的领域词汇表为准，特别是本次新增的**磁盘作业**词条，它同时钉死了范围
