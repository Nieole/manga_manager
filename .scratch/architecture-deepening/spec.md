# Spec: 全项目架构深化与功能规则归属

Status: ready-for-agent

阶段：需求已经批准并进入实施验收；此 Status 表示规格就绪。当前实现和实际门禁见 [集成记录](implementation.md) 与 [联合验收](acceptance.md)，不能以本页状态代替运行证据。

## Problem Statement

作为长期维护和使用 Manga Manager 的人，用户希望程序在继续增加功能时，理解、修改和验证成本不再随文件数量持续上升。现有目录已经拆分，但完整功能的知识仍散布在不同输入、请求处理、后台发起与页面总装中。一次阅读状态修改、资料库操作或藏书编排调整，经常需要同时追踪多个地方，才能判断规则是否一致、收尾是否完整。

后台请求处理与应用装配、后台生命周期、跨功能协调混在一起；前端导航又承担连接、刷新和运行观测。已有独立 module 没有消除全部重复知识，继续把文件切小并不能自动改善 depth、locality 或测试成本。

部分历史分叉已成为可观察的不一致：同一离线进度通过不同传输方式会得到不同的时间和冲突结果；KOReader 对书的投影保留早期最远页策略，而 Web 已支持有效回退；批量已读的活动统计在不同路径中不同；部分提交后失败没有完整刷新缓存。用户要求先判断差异的依据，纠正可确认的遗漏，对不清楚的产品取舍再确认，而不是把所有旧行为冻结成兼容要求。

## Solution

以完整功能拥有规则为目标，同时推进应用编排、阅读状态、前端应用会话与一致性、藏书编排四个方向。按完整用例表达 interface，让输入 adapter 传达意图，功能 module 隐藏规则、持久化协调和必要后续动作，应用编排接管跨功能协作与生命周期。

保留现有部署方式、SQLite、sqlc 和已经建立的领域分工，按功能逐批迁移并保持每批可验证、可发布。先迁阅读状态的完整链，再推进相关阅读能力、藏书编排、前端一致性与后台编排；过渡期允许现有装配继续连接新旧落点，但迁移完成的规则只有一个权威归属。

统一已确认的阅读语义：阅读位置表示当前位置，允许有效的新报告回退；同页的新阅读刷新最近阅读时间；批量标记已读统一计入活动，标记未读只重置读态且保留过去活动；补传与重放按原事实时间处理；内部未知页数哨兵不进入真实页数统计。

成功标准是相同规则集中、修改涉及的知识减少、调用方学习负担减少、功能能够通过合适的 interface 验证。净删行数是辅助信号，不代替行为和结构验收。

## User Stories

以下故事共同构成验收范围。维护者与实现代理的故事约束结构，阅读者与管理员的故事约束功能结果。

1. 作为维护者，我希望四个架构方向有一张统一职责图，以便局部迁移不会各自形成互相冲突的结构。
2. 作为维护者，我希望按完整功能理解规则，以便不必在输入 adapter 与多个辅助文件之间重建执行配方。
3. 作为维护者，我希望功能 module 通过用例表达意图，以便调用时不必组合一组策略开关才能得到正确行为。
4. 作为维护者，我希望应用编排只组合跨功能动作，以便新的应用总对象不会再次吸收全部业务规则。
5. 作为维护者，我希望新功能 module 不反向依赖请求处理或应用总对象，以便依赖方向能够持续保持。
6. 作为维护者，我希望每个功能只依赖需要的数据能力，以便全量存储接口不会成为默认的知识入口。
7. 作为维护者，我希望保留已经有效的任务、提案、系列元数据与迁移分工，以便重构不会推翻已有 depth。
8. 作为维护者，我希望按照规则集中和验证成本验收，以便不会为删行数牺牲必要保护。
9. 作为维护者，我希望有明确依据的业务差异被保留，以便统一代码不会抹平真实的用户意图。
10. 作为维护者，我希望可确认的实现遗漏被纠正，以便历史偏差不会成为新 module 的公开策略。
11. 作为实现代理，我希望产品裁决与可自行选择的工程细节被区分，以便不会因包名或内部拆分反复打断用户。
12. 作为维护者，我希望迁移完成后移除被替代的规则副本，以便后续只需维护一份权威 implementation。
13. 作为阅读者，我希望阅读位置表示当前读到哪里，以便重新阅读或回翻后可以从新的位置继续。
14. 作为阅读者，我希望 Web 与 KOReader 的有效新报告都能回退当前位置，以便设备来源不会改变同一用户的位置含义。
15. 作为阅读者，我希望比当前变更更旧的位置报告被拒绝覆盖，以便延迟补传不会冲掉较新的阅读或标记操作。
16. 作为离线阅读者，我希望批量补传和逐本回退采用同一时间规则，以便传输方式不会决定哪台设备的进度胜出。
17. 作为离线阅读者，我希望接受的补传保留阅读发生时间，以便联网时间不会冒充最近阅读时间。
18. 作为阅读者，我希望缺少发生时间的新报告使用服务端接收时间，以便现有在线客户端与设备协议仍可正常保存。
19. 作为阅读者，我希望同页发生较新的有效阅读也刷新最近阅读时间，以便稍后继续读同一页会反映在最近阅读中。
20. 作为阅读者，我希望同一可识别报告的重试不形成新的阅读事实，以便重试不会改写阅读日期或制造活动。
21. 作为维护者，我希望补传、对账与恢复重放使用原事实时间，以便后台处理不被误当成用户刚刚阅读。
22. 作为阅读者，我希望标记未读后旧记录重放不能恢复清除前的位置，以便明确的清除操作持续有效。
23. 作为阅读者，我希望清除后新的有效阅读仍可建立位置，以便重放保护不会永久阻止继续阅读。
24. 作为阅读者，我希望上述清除保护跨服务重启有效，以便重启不会让旧设备记录再次复活进度。
25. 作为阅读者，我希望清除动作的时间依据与最近阅读时间分开，以便标记未读不会被展示成一次新阅读。
26. 作为阅读者，我希望自己的进度、书签和活动保持隔离，以便任何输入路径都不会串到其他用户。
27. 作为维护者，我希望没有用户身份的兼容路径也遵守相同业务含义，以便兼容实现不会继续维持另一套阅读规则。
28. 作为阅读者，我希望合法页码和未知页数继续被正确处理，以便快速扫描尚未得出页数时仍能保存合理位置。
29. 作为管理员，我希望按书批量标记已读统一计入阅读活动，以便不同用户路径得到一致结果。
30. 作为管理员，我希望按系列批量标记已读采用相同活动规则，以便操作入口不会改变活动统计。
31. 作为管理员，我希望批量标记未读只清除读态，以便它不会凭空增加阅读活动。
32. 作为阅读者，我希望标记未读保留过去的活动，以便重读准备不会抹掉已有阅读经历。
33. 作为管理员，我希望未知页数的书标记已读仍可产生活动，以便它不会因为缺少页数而从活动日期和涉及书的统计中消失。
34. 作为阅读者，我希望未知页数哨兵不进入活动、聚合或展示中的真实页数，以便统计不会出现凭空增加的巨大页数。
35. 作为阅读者，我希望有效离线活动归属于可证明的原阅读日期，以便联网当天不会代替实际阅读日期。
36. 作为管理员，我希望批量标记活动归属于标记发生日期，以便同一次操作的重试不会制造另一天活动。
37. 作为阅读者，我希望重复传输不会重复增加同一事实的活动，以便故障恢复不会改变阅读经历。
38. 作为维护者，我希望只使用队列或记录能证明的日期，以便不会凭一条最终位置补造多日阅读历史。
39. 作为维护者，我希望现有活动页数的统计含义被准确保留和说明，以便每日每书最大绝对页码不会被误称为真实翻读页数增量。
40. 作为阅读者，我希望已有历史活动不被猜测重算，以便此次规则统一不会覆盖缺乏原始证据的旧记录。
41. 作为大资料库管理员，我希望批量读态继续分批提交，以便大量书的操作不会长时间占用 SQLite 写锁。
42. 作为阅读者，我希望每批进度与系列聚合保持一致，以便读取不会看到本批进度已变而聚合未更新。
43. 作为管理员，我希望后批失败时保留前批已提交的工作，以便可重试操作不会被伪装成整体回滚。
44. 作为阅读者，我希望部分提交后相应缓存仍被失效，以便界面不会因为最终返回错误而继续显示旧统计。
45. 作为阅读者，我希望进度已保存但统计失败时能准确区分结果，以便不会被告知进度没有保存。
46. 作为维护者，我希望统计失败仍有可观察告警，以便尽力而为不会变成静默丢失。
47. 作为 KOReader 使用者，我希望书位置投影失败与设备协议记录保存被分别表达，以便诊断准确且协议兼容。
48. 作为维护者，我希望兼容期间的全局与每用户统计按需要独立尝试，以便其中一路失败不会无理由阻断另一路。
49. 作为阅读者，我希望时长归属与活跃性判断继续正确，以便迁移不会把隐藏页面或重复上报算成额外时长。
50. 作为阅读者，我希望书签操作保持用户隔离和页码约束，以便归属调整不会损坏已有书签。
51. 作为阅读者，我希望继续阅读与按用户叠加状态使用共同规则，以便列表、详情与继续阅读不再各自解释读态。
52. 作为维护者，我希望时长、书签与阅读判定逐步拥有阅读状态归属，以便进度首批迁移不会被误认为整个阅读方向已经完成。
53. 作为管理员，我希望人工合集的成员规则有明确归属，以便添加、移除和删除操作遵守同一所有权规则。
54. 作为管理员，我希望智能书架继续按保存条件动态计算成员，以便迁移不会把它变成固定名单。
55. 作为管理员，我希望智能书架的计数与成员查询使用同一条件含义，以便显示数量与实际列表一致。
56. 作为管理员，我希望智能书架成员能跨页完整读取，以便重构不会重新引入只显示首屏的限制。
57. 作为管理员，我希望固化智能书架是明确的一次性动作，以便后来条件或藏书改变不会回头覆盖固化结果。
58. 作为管理员，我希望快照落地后的合集可以人工维护，以便它不会因来源字段被当成持续推导对象。
59. 作为管理员，我希望作品群仍由系列关系推导，以便人工合集操作不会覆盖推导规则。
60. 作为管理员，我希望作品群继续拒绝人工成员和身份修改，以便被重建覆盖的编辑不会被错误接受。
61. 作为客户端使用者，我希望未改变身份的作品群重建保留合集标识，以便已有链接与协议收藏继续有效。
62. 作为管理员，我希望作品群按实际成员差异更新，以便重建不会重置未变化成员的加入时间。
63. 作为管理员，我希望作品群只在需要时更新相关变化时间，以便无变化的重建不会制造虚假的更新。
64. 作为管理员，我希望接受 AI 分组与生成合集作为完整动作执行，以便内容创建与裁决状态不会分离。
65. 作为管理员，我希望不同合集创建来源共享名称约束，以便人工、快照与 AI 分组不会各自允许冲突。
66. 作为管理员，我希望 AI 候选中已消失的系列继续按已确认规则处理，以便落地不会因陈旧裸标识破坏事务。
67. 作为维护者，我希望 AI 分组建议与系列元数据提案保持不同概念，以便导航合并不会导致领域模型被错误合并。
68. 作为客户端使用者，我希望 OPDS 与 Mihon 继续读取相同的合集身份，以便规则迁移不破坏协议访问。
69. 作为阅读清单使用者，我希望成员顺序及进度回填保持有效，以便有序清单不会被当作无序合集处理。
70. 作为维护者，我希望藏书编排通过真实用例提供 interface，以便不会形成一套依赖任意类型和策略开关的通用分组框架。
71. 作为前端维护者，我希望连接与一致性知识独立于导航视图，以便调整导航不需要重新理解推送恢复逻辑。
72. 作为普通用户，我希望保留藏书刷新消息，以便管理员完成扫描后我的视图仍能更新。
73. 作为管理员，我希望运行观测继续可用，以便能够看到工作状态、历史与必要诊断。
74. 作为普通用户，我希望无法接收管理员专属运行内容，以便重组后的连接不会泄露路径或任务参数。
75. 作为用户，我希望每个前端应用实例只维护所需的一条连接，以便功能消费者不会各自重复建连。
76. 作为用户，我希望主导航内的订阅继续有效，以便重构不改变已有页面的实时能力。
77. 作为阅读器或独立图谱使用者，我希望本轮保持现有连接范围，以便结构调整不会顺带引入新的常驻连接。
78. 作为用户，我希望连接关闭后继续按已有策略重连，以便暂时故障不会让实时刷新永久停止。
79. 作为管理员，我希望漏帧后能补拉恢复，以便任务视图不会静默停留在旧状态。
80. 作为维护者，我希望推送连续性仍按投递链判断，以便正常节流导致的序号空档不会触发错误补拉。
81. 作为管理员，我希望运行槽位等实况汇总仍以后端为准，以便局部运行列表不完整时不会显示错误数量。
82. 作为维护者，我希望任务实况、历史、气泡与外部传输分别拥有功能投影，以便共享会话不会成为所有页面数据的大对象。
83. 作为用户，我希望功能操作成功或部分提交后相关视图得到必要刷新，以便不同页面不会继续各自维持陈旧副本。
84. 作为页面维护者，我希望筛选、选中项和弹窗仍属于局部视图，以便共享状态更新不会重置当前操作。
85. 作为用户，我希望切换身份时旧连接与敏感投影被清理，以便新身份不会继承之前用户的观测内容。
86. 作为离线阅读者，我希望暂时断网或会话过期不被当成显式登出，以便本机离线内容和待回传记录继续受到正确归属保护。
87. 作为阅读者，我希望当前书视图与跨书下载保持不同生命周期，以便自动换书不会错误显示或取消上一书的下载状态。
88. 作为用户，我希望设备级偏好保持原有生命周期，以便账户与会话整理不会顺带改变偏好归属。
89. 作为维护者，我希望前端消费者不再解释底层传输事件名称，以便连接协议与功能投影之间有明确 seam。
90. 作为维护者，我希望手动、定时和监听发起完整功能时遵守同一准入，以便不会再出现彼此不知情的任务守卫。
91. 作为管理员，我希望重启函数在开放运行能力前完整登记，以便服务重启后历史运行仍可按规则重试。
92. 作为管理员，我希望一致性恢复先于后台工作与请求开放，以便恢复中的资料库不会被提前访问。
93. 作为管理员，我希望任务与运行继续区分身份和一次执行，以便重试不会覆盖历史。
94. 作为管理员，我希望任务键继续用于日志辨认而不重新承担寻址，以便控制动作不会误指向另一条运行。
95. 作为维护者，我希望任务规则与落盘保持既有分工，以便此次应用编排调整不会重新引入 SQL 耦合。
96. 作为管理员，我希望资料库迁移继续保留资料库、系列和书的身份，以便阅读记录与关联不会被重新导入取代。
97. 作为管理员，我希望迁移与保护恢复共同保持排他访问、路径配置一致性及派生处理，以便完成状态不会早于实际恢复完成。
98. 作为管理员，我希望迁移恢复失败时相关资料库保持受保护，以便部分恢复不会开放不一致路径。
99. 作为管理员，我希望监听扫描等待真实运行完成后再清理，以便排队、合并或停发不会被误当成扫描成功。
100. 作为阅读者，我希望改名重连先于失踪清理，以便监听处理不会抢先删除书及阅读记录。
101. 作为管理员，我希望封面批在实际运行开跑时认领，以便发起合并不会丢失待生成封面。
102. 作为管理员，我希望扫描与封面仍分别拥有运行，以便槽位、暂停、恢复与观测保持明确。
103. 作为大资料库管理员，我希望封面发起不阻塞扫描入库，以便编排收拢不会降低扫描吞吐。
104. 作为用户，我希望扫描完成后的统计失效、必要预热与语义推送保持完整，以便缓存与界面不会因回调覆盖失去更新。
105. 作为管理员，我希望停止时按受控顺序停配置监听、排空请求并等待后台退出，以便资源不会在后台仍使用时提前关闭。
106. 作为维护者，我希望后台任务的日志保留运行上下文，以便功能迁移后仍可按运行查看日志。
107. 作为维护者，我希望每批迁移可独立验证和发布，以便不必等到整个应用装配重写完才获得收益。
108. 作为维护者，我希望功能规则测试无需初始化整个请求控制对象，以便验证不再被无关能力和后台资源拖累。
109. 作为维护者，我希望保留必要的 HTTP、协议、页面和生命周期回归，以便集中规则测试不会遗漏 adapter 集成。
110. 作为实现代理，我希望必要存储变更能够兼容已有数据库并跨重启保持正确，以便新保护不以丢失旧数据为代价。
111. 作为维护者，我希望生成契约、代码格式及仓库门禁保持一致，以便分批交付持续满足现有工程要求。
112. 作为维护者，我希望规划完成与实现完成明确区分，以便规格就绪不会被误报为程序行为已经改变。

## Implementation Decisions

### 结构与依赖

- 建立阅读状态、藏书编排和应用编排的明确 module 归属，前端建立独立于导航视图的会话与一致性归属。目录命名及私有拆分是工程选择，不以移动文件数量验收。
- 输入 adapter 负责解析、身份提取、授权入口与响应转换。功能 module 接收明确主体和意图，不依赖全局当前用户，也不反向依赖请求处理或应用总对象。
- 应用编排拥有跨功能协作和生命周期，不为每个简单功能调用新增转发层，不吸收功能内部规则。
- 延续任务与运行、任务领域与落盘、系列元数据多来源规则、提案裁决和资料库迁移的已有分工。尊重 ADR 0001、0003、0004、0005、0006、0007、0008、0009 的有效决定；被取代决定不恢复为约束。
- 保留 SQLite、sqlc 和现有数据模型作为迁移基础。按真实使用面渐进收窄全量存储依赖，不先重写所有查询或机械复制一套领域对象。

### 用例 interface 与后续动作

- 采用按完整用例命名的 interface。位置上报、批量同步、标记书或系列读态、人工成员编辑、保存智能书架条件及接受分组等意图各自可理解。
- 不以减少方法数量为由引入宽泛命令、任意 profile 或策略组合。在线和离线共享位置规则，传输形态不成为业务策略。
- 事务、系列聚合、活动及必要缓存失效由完整功能接管。返回结果表达成功、跳过、提交范围与告警，不把需要调用方自行执行的后续步骤作为配方返回。
- 对跨 module 的后续动作建立唯一编排所有者，通过明确依赖协作；不引入万能事件总线或通用流程框架。

### 阅读位置与报告时间

- 阅读位置是当前位置，不是历史最远页。有效的新报告可前进或回退，适用于 Web、离线和匹配成功后的 KOReader 书位置投影。
- 有发生时间的报告使用原时间进行新旧判断与保存；没有发生时间的旧客户端或设备新推送按接收时间处理。保留已有时区归一化与服务端本地日历口径。
- 批量与逐本回退共用核心 implementation，消除逐本回退接受后改写为接收时间的遗漏。
- 同页、较新且有效的阅读刷新最近阅读时间；可识别的同一事实重试不刷新。已有节流用于减少写负载，不能决定不同输入的业务含义。
- KOReader 设备账号、认证、指纹匹配、协议规范记录和诊断仍归 KOReader；百分比转换使用匹配到的书事实。没有客户端时间的新设备推送按新推送处理，对账重放则使用原设备记录时间。
- 被拒旧的位置报告不改变当前位置和最近阅读时间。本期不凭被拒旧报告推断额外历史活动，也不从一条最终位置恢复完整阅读轨迹。

### 持久化清除依据与幂等

- 标记未读清除展示读态，同时持久保存足以拒绝旧报告的变更依据。该依据跨重启有效，不借用最近阅读时间，不生成阅读活动。
- 必要的最小存储元数据至少能表达主体、书、最近有效变更时间和清除事实，并能识别已处理的可识别报告或批量操作。可以扩展现有持久化或增加相关记录，具体表形状由实现选择。
- 新前端操作应保留稳定的事实身份或等价发生时间，使重试沿用原操作依据；批量操作重试沿用最初标记日期，已提交部分不能被重新解释为另一日的新标记。
- 对缺少稳定身份和发生时间的兼容输入，不承诺推断两次完全相同载荷究竟是重试还是新用户操作；继续兼容接收时间与必要节流。协议本身没有的证据不被伪造。
- 存储升级保留现有书、系列、用户、进度和活动身份。旧数据缺少清除或事件依据时不猜测回填；新规则从有可靠依据的变更开始生效。

### 阅读活动、未知页数与时长

- 按书和按系列批量标记已读均计入活动。新标记使用操作发生日期；标记未读既不新增活动也不删除已有活动。
- 有效离线阅读按可证明的原阅读日期归属，按既有本地日历口径计算，不把同步到达日期当作阅读日期。
- 未知页数的已读状态与真实页数分开表达。内部哨兵不能进入活动、系列聚合、总页数或展示中的真实页数统计；活动可具有书与日期而不编造页数。
- 现有活动页数使用每日每书最大绝对页码的含义，本期不改造成精确增量翻页统计。同日重复输入不累计重复页数，缺失的旧历史不重建。
- 实际阅读时长继续遵守活跃性、可见性和既有短时尽力而为约束。已有时长输入没有完整历史事件或可信发生日期时，不虚构离线时长和跨日分配。
- 书签、时长、每用户状态叠加和继续阅读判定纳入阅读状态归属。归档、转码、页图缓存与离线字节下载延续已有能力，不整体塞入同一个阅读对象。

### 事务、部分提交与错误

- 保留适合大选区的分批提交；每批的进度与派生系列聚合原子更新。后批失败保留前批提交，不承诺全量事务。
- 功能结果在失败时仍准确保留已提交范围，必要缓存失效根据提交事实执行，不再仅因最终成功才执行。
- 进度存储失败与活动统计告警分开。已提交进度不因软统计失败被描述成未保存，告警必须可观察；需要的全局与每用户统计独立尝试。
- KOReader 协议记录和书位置不合并为跨功能大事务。保留设备协议的保存与响应兼容性，真正的位置写入失败仍形成准确诊断。
- 现有响应字段、控制标识和协议路由原则上兼容。为幂等及准确结果增加的元数据采用兼容方式，不以重构为由要求旧客户端一次性升级；已裁决的语义纠正不因旧实现曾不同而撤销。

### 藏书编排

- 人工合集、动态智能书架、一次性快照和关系推导作品群分别保持其规则，不统一成任意类型的通用集合模型。
- 作品群保留稳定自然身份、成员差集、无变化时的更新时间约束以及人工只读。智能书架快照和 AI 分组落地后的合集归人工所有。
- AI 分组的合集建议不属于系列元数据提案。接受分组、名称检查、消失成员处理、创建合集及裁决状态推进作为完整用例维护其事务一致性。
- 合集计数、列表和分页使用一致查询含义，保留按用户计算的筛选结果。OPDS 与 Mihon 继续访问相同合集身份。
- 有序阅读清单保留独立顺序语义与进度回填；可以共享归属下的基础能力，但不复用一个抹平有序和无序成员差异的规则。

### 前端应用会话

- 应用会话集中连接、协议解码、重连、投递链连续性信号和共享刷新协调，路由集成声明订阅活跃范围。
- 本期保持主导航路线内的既有连接范围，不给独立阅读器和图谱增加常驻连接；单连接约束以一个前端应用实例为单位。
- 普通用户继续接收藏书刷新，敏感运行数据由后端按管理员权限过滤；鉴权仍由既有身份 module 持有。
- 身份变化时清理旧连接与角色投影；临时断网或会话过期不等于显式登出，不因此删除已有离线内容与待回传队列。
- 保留投递链前序关系、漏帧补拉、必要轮询与后端实况汇总。消费者不按序号相邻判断丢帧，也不从局部运行列表自行计算全局汇总。
- 任务实况、历史、气泡和外部传输分别持有功能投影；页面保留局部筛选、选中项和弹窗，应用会话不持有所有页面结果。
- 当前书、跨书下载、离线归属与设备偏好保持不同生命周期。共享刷新不破坏请求竞态防护、未保存输入或页面选区。

### 应用编排与完整协作链

- 手动、定时、监听输入使用相同功能准入与任务能力，重启函数装配期完整登记，任务与运行身份、发起方、变体、重启入参与声明标签的含义保持一致。
- 启动先登记能力并恢复一致性，再恢复运行、开放后台和请求。停止按既有承重顺序停止配置监听、排空请求与推送、停止目录监听、取消运行并等待后台退出。
- 资料库迁移与保护恢复共同保持排他访问及相交目录保护、数据库路径与配置策略一致性、阅读路径缓存清除、外部会话失效和目录监听切换；全部必要效果成功后才完成并开放访问。
- 监听扫描等待真实运行完成，再允许清理。发起成功、合并、停发与仍在排队不等同于扫描完成；改名重连不得被清理抢先。
- 封面批在实际运行开跑时认领；任务合并不丢批，封面发起不阻塞扫描入库，扫描和封面继续分别建运行并遵守槽位与暂停。
- 扫描批事件保留统计失效、完成时的必要预热和语义推送，回调归属迁移不能覆盖其中部分效果。
- 后台任务日志继续使用带运行上下文的记录方式。页图读路径与迁移访问版本的配合不因阅读状态迁移而丢失。

### 分批交付与清理

- 先形成统一归属和行为矩阵，以阅读位置、读态、活动、聚合为首条完整迁移链，随后接入其余阅读状态能力。
- 藏书编排按真实用例分批；前端按稳定推送语义接管会话；后台逐条接管完整协作链，最后收拢进程装配。
- 允许过渡期继续使用既有装配和短期兼容转发；阶段完成必须删除已经被替代的权威规则副本。
- 不把完整迁移链拆成多批互不知情的调用方责任。顺序可按实际依赖交错，但每批能独立验证与发布。
- 后续文档按当前实现核实 ADR 的过期实施状态；保留有效决定，不以旧状态文字推断功能尚未实现。

## Testing Decisions

### 测试 seam

用户已确认：从完整功能的 interface 验证规则，以真实临时 SQLite 验证事务；前端验证应用会话与功能消费者的可见行为，并保留 HTTP、协议和页面回归。

- 优先使用现有任务、迁移、提案、存储与传输行为 seam。新的规则测试面放在完整阅读或藏书编排用例的最高有效 seam，不给每条查询、内部 helper 或私有步骤新增公开 interface。
- 本项目涉及多个不同生命周期的完整功能，不为追求一个测试入口而创建应用总对象。每个功能通过自己的公共 interface 测试，跨功能协作通过应用编排的行为 seam 验证。
- 时钟、故障、发布与生命周期能力只在确有需要时形成 internal seam。真实 SQLite 测试验证外键、聚合、事务和批次提交，不能用一组 mock 调用次数代替这些事实。
- 好测试断言用户可见结果、持久化状态、权限、可观察告警与资源释放；不锁死内部函数划分、私有状态布局或机械调用顺序。

### 阅读状态

- 以同一行为矩阵覆盖 Web 在线、离线批量、逐本回退、按书和按系列标记，以及 KOReader 匹配后的投影。
- 验证两条离线输入顺序与时间胜负一致，特别覆盖先补传较旧报告被改写成接收时间后错误阻断较新报告的场景。
- 验证较新的回退被接受、同页新事实刷新、重复事实不刷新、清除后旧重放被拒、清除依据跨重启存活及新阅读可恢复位置。
- 验证各主体隔离、未知页数与合法页码、已读活动、未读不新增或删除活动、原日期归属、未知页数不放大任何真实页数统计。
- 制造批内聚合失败和后批失败，验证批内回滚、前批保留、失败结果中的提交事实及必要缓存失效。
- 分别制造进度与活动失败，验证结果和诊断准确；验证 KOReader 设备规范记录和书位置未被错误合并成一个事务。
- 沿用已有页码夹取、用户隔离、离线时间归一化、进度冲突、书签、时长与继续阅读测试的 fixture 和行为断言；原有测试只守旧偏差时，按本规格更新期待而非机械保留。

### 藏书编排

- 通过功能 interface 验证人工可编辑性、作品群只读、智能条件、计数列表一致、跨页成员、快照所有权与名称约束。
- 使用真实 SQLite 验证 AI 分组裁决与建合集一致性、消失成员和名称冲突处理。
- 沿用既有作品群身份稳定、无关合集不变、成员加入时间及更新时间、智能书架计数和快照测试；补充跨输入覆盖，避免规则仅在一个 adapter 正确。
- 保留 OPDS、Mihon 与有序阅读清单的对外身份和顺序回归。

### 前端与应用生命周期

- 沿用 CLOSED 重连、任务投递链、运行补拉、任务气泡、页面请求竞态和离线 owner 测试，验证换路由、身份变化、重连和漏帧后的完整结果。
- 验证普通用户刷新和管理员运行观测的权限区别，独立阅读器与图谱没有新增连接，页面局部状态不被共享刷新冲掉。
- 通过可控制后台依赖的装配与生命周期测试验证登记、恢复、开放、停止顺序；不要求每个功能规则测试启动完整请求控制对象。
- 保留迁移修复与异常保护、相交资料库访问、监听改名后清理、封面合并和运行停止等既有集成先例，覆盖每条完整协作链的失败及取消路径。

### 门禁与阶段验收

- 后端变更执行仓库规定的 Go 测试、格式检查与 lint；前端变更执行测试、构建及适用 lint。SQL 和生成契约变化遵守仓库既有生成与漂移检查规则。
- 规则行为测试完整替代的 helper 镜像测试可以删除；仍验证不同故障、协议或用户行为的回归必须保留。
- 结构验收检查依赖方向、唯一规则归属及 adapter 是否仍掌握步骤配方。仅完成目录移动、转发抽取或新增 interface 不能视为完成。
- 每批记录实际验证结果。规格就绪、工单就绪、结构迁移与运行行为验证分别陈述，不互相代替。

## Out of Scope

- 微服务化、拆库、更换数据库、ORM、前端框架或为未来可替换性建立通用基础设施。
- 一次性搬空全部请求处理与页面，机械统一所有数据类型、拆分每个 helper，或以净删行数作为硬性门槛。
- 推翻现有任务、运行、系列元数据、提案和迁移的有效领域决定；重新引入独立扫描准入或将任务领域与落盘合并。
- 将所有历史差异冻结为业务规则，或在没有依据和用户裁决时扩大产品行为变更。
- 新增历史最远阅读位置、完整阅读事件溯源、精确翻读页数统计，或者猜测补造、重算已有阅读历史。
- 凭现有单条离线最终位置恢复完整多日阅读，或为不携带身份和时间的协议推断可靠的重复事件身份。
- 将资料库路径迁移改成文件搬运、重新导入、记录自动合并或通过扫描猜测内部重排。
- 将 AI 分组建议并入系列元数据提案，将所有合集、智能书架、作品群与阅读清单统一为一个无差别容器。
- 为独立阅读器、图谱或浏览器标签增加新的全局连接机制，新增全站离线下载管理，或改变设备偏好的账户归属。
- 重写归档、图片转码、阅读渲染及离线字节缓存，或改变其已有性能和生命周期取舍。
- 规格编写阶段生成实施工单、修改程序实现、提交、推送或发布；后续实施阶段的授权和结果分别记录。

## Further Notes

本规格保存架构体检、grill 裁决及已确认的测试 seam；[工单索引](queue.md) 提供实施拆分，[联合验收](acceptance.md) 提供对应实现和实际执行证据。

已确认的业务纠正包含当前位置回退、同页新阅读刷新、各批量已读路径计活动、未读不新增活动及未知页数不伪造统计。已查明的遗漏包含离线逐本回退时间漂移、部分提交后缓存失效缺口、状态失败与统计告警混合；这些纠正属于本规格，不作为无关行为变更移出。

具体包名、私有 interface 拆分、最小存储元数据的表形状以及生成结果由实现按约束确定；这些工程选择不得改变已确认语义。若实现发现新的产品岔口，先依据事实判断，真正不明的取舍再请用户裁决。

本规格的 `ready-for-agent` 表示规格已经具备实施依据，不表示四个方向已经实现或程序测试已经通过。
