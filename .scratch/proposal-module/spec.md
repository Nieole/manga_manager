# Spec: 把提案裁决抽成模块

Status: done

## Problem Statement

**提案**是本仓库最重的一个子域：一条刮削结果要经过字段草稿构建、与 pending 及最近拒绝记录的签名去重、**锁定字段**过滤、部分应用裁决、终态 CAS，最后才写进**系列**。这套逻辑今天没有自己的模块——它住在 `internal/api/metadata_review_controller.go`（1282 行）里，与 HTTP handler、JSON 视图映射同居一个文件；真正动系列的那 168 行写入器又在 `scrape_controller.go`。

这带来五类可观察的损害：

**同一套五步被抄了两遍，且两遍的结论不一致。** 单条应用与批量应用各自重写「读提案 → 判 pending → 读字段行 → 按 mode 筛 → 读系列 → 裁决 → 解释错误」。两处对**同一组**哨兵错误分类不同：单条把「全被锁定」与「无变更」回成 200 + outcome 标签，批量把它们塞进 skipped 桶，而「被并发抢先」在单条是 409、在批量是 failed。拒绝路径同样抄了两遍，其中一遍此前漏掉 pending 守卫，导致已应用的提案可以被改成已拒绝、行上两个时间戳同时非空——这条缺陷是补出来的，不是设计出来的。

**用户看不出「被别人抢先」和「真的失败」的区别。** 批量路径把「查不到这条提案」与「它已经不是 pending」揉进同一个判断，一起落进 failed 桶。而后者是日常情形——另一个标签页、另一个人、或上一次批量操作已经处理过它。用户得到的是红色的「失败 N 项」，实际什么也没坏。

**良性结果用 error 表达，漏一个就是 500。** `queueOutcomeForError` 的注释自己写着：「必须都在这里识别并映射为良性 outcome，漏掉的会被上抛为 HTTP 500，用户看到『服务器错误』」。三个刮削调用点各自依赖这一句纪律。用户该看到的是「数据已是最新」或「解锁后再试」，而不是「服务器错误」。

**事务边界穿过接缝。** 写入器带一个 `afterInTx func(*database.Queries) error` 参数，存在的唯一理由是让提案裁决把「写元数据」与「关单」并进同一个事务。这个参数在生产上只有一个实参来源，而那个来源本该与写入器同属一个模块。与此同时，写入器那条不带 hook 的包装在生产上**没有任何调用方**，只有两个测试在用。

**接口不是测试面。** 六个提案测试文件全部经 `newTestController`——要测一次签名去重，得先建临时目录、跑完整 migration、造 `config.Config` 的九个字段、初始化 `parser` 全局池、建一个真 `Scanner`。`internal/api` 的 345 个用例因此跑 14.4 秒。

同一个领域问题今天还存在两套实现：「给我这批提案的字段行」，收件箱路径用批量查询，系列详情页仍在 reviews 上逐条查——那正是收件箱早已修过的 N+1 形状。

## Solution

**提案**子域拿到自己的模块 `internal/proposal`，形状照 `internal/koreader` 的 `Service`：HTTP 层只做解码、调用、序列化，裁决、写入与读取全在模块内。

模块对外六个方法——入队、应用、拒绝、按系列列出、收件箱分页、待裁决计数。调用方交出一个提案 id 和一个模式，拿回一个**已经分类好的结果**；加载、事务、终态 CAS、部分应用的取舍全部在模块内部完成。哨兵错误不再跨接缝：良性结局是结果值，`error` 只留给真正的故障。

调用方视角的变化：

- 应用一条提案从「四次加载 + 一次裁决 + 三次 `errors.Is`」变成「一次调用 + 一次 switch」。
- 批量路径只剩累加成桶——分类是领域知识，累加不是。
- 入队的三种良性结局（无差异 / 差异字段全被锁 / 此前已拒绝）与「复用了已有提案」成为同一个枚举上的值，「漏一个就 500」在结构上写不出来。
- 事务不再跨接缝：`*database.Queries` 不再作为参数递给任何 api 层的函数。

用户视角的变化只有两处，都是修复：

- 被别人抢先处理掉的条目单独成桶，不再混在「失败」里报红。
- 系列详情页的提案加载不再随提案条数发起 N+1 查询。

## User Stories

1. 作为维护者，我希望应用一条**提案**只需要交出它的 id 与模式，这样「读提案 / 判 pending / 读字段行 / 按 mode 筛 / 读系列」这五步不必在单条与批量两个 handler 里各抄一遍。
2. 作为维护者，我希望裁决返回一个已分类的结果，这样两个调用点不可能对同一种结局给出不同的分类。
3. 作为维护者，我希望入队的三种良性结局是结果值而不是哨兵错误，这样新增一种结局时，忘记在调用点处理它会是一个编译期可见的分支缺失，而不是一次线上 500。
4. 作为维护者，我希望拒绝一条提案也走同一个模块入口，这样「pending 守卫」不可能在第二个调用点上被漏掉——那正是此前发生过的事。
5. 作为维护者，我希望元数据写入器与提案裁决同属一个模块，这样「写元数据」与「关单」的原子性由模块内部保证，不必把 `*database.Queries` 递过接缝。
6. 作为维护者，我希望写入器那条 hook 参数消失，这样它不会再被误解为一条可以从外部注入行为的接缝——它只有一个实参来源。
7. 作为维护者，我希望模块只能看见它需要的那二十余个查询，这样「在一批提案上逐条取字段行」这类 N+1 在编译期就写不出来。
8. 作为维护者，我希望「给我这批提案的字段行」只有一种实现，这样系列详情页与收件箱不会一个是批量、一个是 N+1。
9. 作为维护者，我希望模块的构造签名上不出现 `database.Store`，这样收窄这件事在读接口的人眼里立得住，而不是内部窄、门口宽。
10. 作为维护者，我希望有一条守卫用例守住「`internal/api` 内不再直接查提案表」，这样这条约束不依赖任何人记得住——编译器在这里拦不住，所以守卫有真实对象。
11. 作为维护者，我希望测一次签名去重不需要 `Scanner`、`config.Manager` 与 `parser` 全局池，这样用例的装配从九步降到三步。
12. 作为维护者，我希望「锁定状态按当前值算」这条规则住在模块里而不是视图映射里，这样它是一条裁决规则，不是一个渲染细节。
13. 作为维护者，我希望 `*View` 结构体留在 HTTP 层，这样 JSON 标签与 `jsonResponse` 待在一起，前端契约的归属不被打散。
14. 作为维护者，我希望模块内部只认字段名（`title` / `summary` / …），这样新模块诞生时不带任何面向用户的字面量。
15. 作为维护者，我希望审核中心的角标经一个专门回答「有多少条待裁决」的方法取数，这样不必为它在收件箱方法上开一个 `limit=0` 的约定——那是哨兵值形状的接口，仓库刚从任务引擎里清掉过。
16. 作为维护者，我希望迁移与删除旧接口落在同一个 PR 内，这样不会再造出一条「新路径 / 旧路径」的分裂轴——仓库已经为这种半路停下的迁移付过一次代价。
17. 作为维护者，我希望 AI 分组的合集提案不被卷进来，这样模块名与 CONTEXT.md 里**提案**的定义严格对齐，而不是变成一个「所有待裁决的东西」的杂物袋。
18. 作为维护者，我希望 CONTEXT.md 明说 AI 分组不是**提案**，这样下一个人不必重新推导一遍这个边界。
19. 作为维护者，我希望模块有自己的测试文件与用例命名，这样下一个人找「部分应用为什么不关单」时，能在模块目录里找到，而不是在一个 1282 行的 controller 文件旁边。
20. 作为终端用户，我希望批量处理时「已被别人处理过」的条目单独成桶，这样我不会为一堆并没有坏掉的东西看到红色的失败提示。
21. 作为终端用户，我希望这个新桶不把整条提示变成错误色，这样提示的颜色仍然只在真的出错时才变红。
22. 作为终端用户，我希望「解锁后再试」与「数据已是最新」这类可行动的提示不会退化成「服务器错误」，这样我知道下一步该做什么。
23. 作为终端用户，我希望批量应用后仍留在收件箱里的那些**提案**不被报成「已应用」，这样我不会以为已经处理完了——这条既有行为必须在搬迁后原样保留。
24. 作为终端用户，我希望打开一个有多条待裁决**提案**的系列时，页面不因提案条数增多而变慢。

## Implementation Decisions

### 模块边界与命名

- 新建 `internal/proposal`，只装**元数据提案**。AI 分组产出的是合集成员建议，与元数据提案零共用代码、不同表、不同裁决语义，本次不动。
- 包名取领域词而不是跟随 sqlc 生成的类型名。错配只落在改不动的生成类型上（schema 不动是本次明确的范围外）。
- 同批修改 CONTEXT.md 的**提案**词条，补两点：AI 分组产出的合集成员建议不是提案；存储与路由把它拼作 review，读代码时不要当成第二个概念。

### 对外接口（六个方法）

| 方法 | 承担 |
| --- | --- |
| 入队 | 收系列、刮削结果、数据源名、查询串与选项；返回已分类结果 |
| 应用 | 收提案 id 与模式；返回已分类结果 |
| 拒绝 | 收提案 id；返回已分类结果 |
| 按系列列出 | 收系列 id；返回该系列的提案与来源沿革 |
| 收件箱 | 收分页与过滤条件；返回一页待裁决提案与总数 |
| 待裁决计数 | 只回答「有多少条待裁决」，供审核中心角标 |

- 入队仍收一个已加载的**系列**而不是系列 id：三个调用点都已经握着它，而批量刮削那处在循环里，改成 id 会多出一次每系列查询。
- 应用与拒绝收 id，模块自己加载。这是把两处重复的五步收进模块的前提。
- 计数单独成一个方法，不复用收件箱方法传 `limit=0`：后者要么白跑一次列表查询，要么在模块里为 `limit==0` 开特例分支，那是必须先知道才能用对的约定。
- 批量应用与批量拒绝**不进模块**：handler 循环调用单条入口并累加成桶。分类是领域知识，累加不是。
- 结果类型区分至少这些结局：已入队 / 复用了既有提案 / 无差异 / 差异字段全被锁 / 此前已拒绝（入队侧）；全部应用 / 部分应用 / 全被锁跳过 / 无变更跳过 / 被抢先（应用侧）；已拒绝 / 被抢先（拒绝侧）。`error` 只表示故障。
- 模块不导出哨兵错误供调用方 `errors.Is`。既有的 `errNoMetadataChanges`、`errAllFieldsLocked`、`errMetadataReviewRejectedBefore`、`errMetadataReviewNotPending` 在收缩票中删除。

### 元数据写入器

- 写入器整体迁入模块，成为其内部实现。
- `afterInTx` 参数删除：「写元数据 + 关单」在模块内是同一次事务的两段，不需要一条把 `*database.Queries` 递出去的接缝。
- 那条不带 hook 的包装（生产零调用方、仅两个测试使用）一并删除，其测试改打模块接口。
- 人工编辑**系列**那条路径**不**并入本模块：它同样写系列元数据，但不因提案而写、也不记来源沿革，是一条独立的合法路径。因此本次不设「只有模块能写系列元数据」这种保证。

### 与数据库的接缝

- 模块声明两个接口：一个是事务内可用的查询集合（二十余个方法），一个是「开一次事务」的能力。生产上 `*database.Queries` 天然满足前者。
- **适配器写在 `internal/api` 侧**，模块的任何签名都不提及 `database.Store`。装配处把 store 包成模块要的形状再传入。
- 查询集合里**只放批量版**字段行查询，逐条版不进接口。
- 诚实说明：参数与返回值仍是 `database` 包的类型，import 边一分不减。收窄的正当性只有一条——让某类查询在模块内写不出来——与 `internal/external` 的窄 Store 同一个立场，不宣称解耦，也不宣称是为替身准备的。

### 读路径与 N+1

- 「按系列列出」与「收件箱」两条读路径进模块。留在 api 就意味着它们仍握着全量 store，那个 N+1 仍然写得出来、也仍然在那儿。
- 迁移时系列详情页改用批量字段行查询，与收件箱同一条通路。这是一次性能修复，须记进 CHANGELOG。
- 审核中心角标的计数改走模块的计数方法。AI 分组与 KOReader 未匹配那两个数不动，仍由 api 直接取——那个 handler 是跨子域聚合器，本就该向三个子域各要一个数。

### 视图与文案

- `*View` 结构体与 `*ToView` 映射函数留在 `internal/api`，它们是 HTTP 契约。
- 「锁定状态按**当前**值算」这条规则迁入模块：模块返回的字段上，锁定标志已是终值，视图映射里那个 `||` 消失。
- 字段标签与 outcome 提示文案全部留在 api 视图层。模块内部只认字段名。
- 本票**不**收敛 i18n。已知的两条语种缺陷——字段标签对中文用户显示英文、入队提示对英文用户显示中文——另立一票，届时只改 api、前端与两个语种文件，不碰模块。

### 冲突桶（前端契约变更）

- 批量应用与批量拒绝的响应各新增一个 conflict 桶，收「这条提案已经不是 pending」这一种结局。
- **不分是哪一步发现的**：前置检查命中与事务内 CAS 撞上，都归 conflict。只收后者的话，日常最高频的「另一个标签页已处理」仍落 failed，新桶的收益基本落空。
- failed 收窄为真故障：查询报错、写入失败、提案查不到。
- 前端同批改动：批量结果的累加、汇总提示的传参，以及两个语种的批量结果文案模板（占位符从五个变六个）。
- 提示的严重度仍**只**看 failed。被抢先不是错误，不该让整条提示变红。
- 单条应用与单条拒绝维持 409 不变——那是正确的 HTTP 语义，本次统一的是批量侧。

### 结构性保证

- 验收标准：`internal/api` 内不再出现任何提案表的查询调用。
- 由一条源码扫描守卫用例守住，按符号名扫描。这条守卫**有真实对象**——`api` 仍握着全量 `database.Store`，编译器拦不住——因此不适用「结构性成立后守卫失去对象就该删」的先例。
- 守卫不开白名单。第一条白名单会让它从此变成一份需要维护的例外清单。

### 装配

- `Controller` 新增一个模块字段，在 `newControllerCore` 中构造，与 `koreader.NewService` / `external.NewManager` 并列。
- 模块不持有生命周期、不开 goroutine、不碰 SSE。
- 模块只依赖数据库一样东西：置信度默认值是常量表，不吃配置。

### 不改动的东西

- 数据库 schema 与 `sql/query.sql` 不变。
- 除 conflict 桶外的响应形状不变：bulk 其余各桶、单条的 outcome 标签与 200 + `applied:false` 一字不改。
- HTTP 路由与状态码不变。

## Testing Decisions

### 什么是好用例

只测模块**接口**上可观察的行为：交进去一份刮削结果与一个系列，断言拿回的结果分类与库里的行；不断言模块内部调用了哪个查询、也不断言事务分成几段。判据是：把实现换一种写法而行为不变时，用例应当仍然通过。

现有用例里有一批正是这个形状，可直接作为迁移的样板——它们断言的是「第二次入队复用了同一条提案」「部分应用后提案仍为 pending 且只剩未应用的字段行」「拒绝之后同一份提案不再入队」，全部只看输入与库里的结果。

### 测哪些模块

**主接缝：模块接口。** 裁决用例全部搬到 `internal/proposal` 的测试里，用真 SQLite（`database.Migrate` + `NewStore` + 适配器，三步），不再构造 `Controller`、`Scanner`、`config.Manager` 与 `parser` 全局池。需要覆盖：

- 字段草稿：空提案不入队、与当前值相同不入队、**锁定字段**不入队且只统计「不锁就会入队」的那些。
- 签名去重：与 pending 相同则复用；与最近拒绝记录相同则报「此前已拒绝」；显式忽略拒绝记录时可重新入队；不同系列之间互不干扰。
- 部分应用：只应用一部分时提案保持 pending、已应用的字段行被删除、剩余字段仍可再应用。
- 终态 CAS：并发抢先时整体回滚，且不会出现同时带应用时间与拒绝时间的行。
- 被抢先的两条发现路径（前置检查、事务内 CAS）返回**同一个**结局分类。
- 入队后加锁：应用时被当前锁定集过滤，全被过滤时报「全被锁定」而不是静默成功。
- 读路径：按系列列出返回的字段锁定标志按当前锁定集算，而不是入队瞬间的快照。
- 写入器：锁定字段不被覆盖、标签与作者 upsert 并去重、来源沿革记录、Bangumi 外链只在该数据源下写入且不重复。

**既有接缝：HTTP。** `internal/api` 只保留验证传输语义的用例——状态码（400 / 404 / 409）、bulk 响应的各个桶（含新增的 conflict）、单条的 200 + `applied:false` + outcome 标签。它们继续走 `newTestController`。

**结构守卫。** 一条扫描 `internal/api` 源码的用例，断言提案表相关查询的符号不出现在该包内。

**前端。** 批量结果累加与汇总提示的既有 vitest 用例补上 conflict：断言 conflict 不计入失败、不把提示置为错误色。

**不做内存替身。** 不为查询集合写 fake：终态 CAS 的守卫、去重比对与级联删除的语义都在 SQL 里，手写替身等于把「守卫必须落在 SQL 的 `WHERE` 里」那条注释所防的东西重新实现一遍，测出来的是一个谎。这也意味着那条接缝在生产与测试里都只有一个适配器，其正当性只落在编译期约束上。

### 先例

- `internal/koreader/service_test.go` 的 `newTestService`：同样是真 SQLite + 三步装配的子域模块用例，本次的模块测试照此写。
- `internal/external/prepare_transfer_test.go` 的计数替身：如果需要为「批量版查询确实只被调一次」加一道回归守卫，照它的写法，而不是造行为替身。
- `internal/api/metadata_review_*_test.go` 现有四个文件：断言形状可直接沿用，只换调用入口与装配。

## Out of Scope

- **AI 分组的合集提案**：不迁移、不改动。
- **i18n 收敛**：字段标签与入队提示的两条语种缺陷另立一票。本票只给既有的批量结果文案加一个占位符，不动任何既有字面量。
- **收件箱的分页与过滤能力**：只搬运，不新增维度。
- **`database.Store` 的整体收窄**：本次只为**提案**模块画一条窄接缝，`scanner` / `koreader` / `api` 其余部分仍依赖全量 Store。
- **人工编辑系列那条写入路径**：不并入模块。
- **conflict 之外的契约变化**：不新增桶、不改单条路径的状态码。
- **围绕 conflict 的交互设计**（例如提示里给一个「刷新看看」的入口）：本次只把它从 failed 里分出来，怎么引导用户另议。
- **`Controller` 上其余子域的切分**：架构评审里的候选 4，另议。

## Further Notes

- ADR-0001（**重启函数**在装配期注册）不受本次影响：提案子域不拥有任务类型，注册表不动。
- CHANGELOG 除架构改动外，须记两条用户可见变化：批量处理时被别人抢先的条目不再报成失败；系列详情页的提案加载不再随提案条数发起 N+1 查询。除这两条外若发现还有行为变化，那是一个需要回到本 spec 讨论的信号，不是一条顺手写进 CHANGELOG 的注脚。
- 收缩票必须与迁移票落在同一个 PR。仓库里那条「i18n 码版 / 字面量版」的分裂轴，就是一次停在半路的迁移冻结进签名的产物；用同样的方式收尾只会再造一条相同的疤。
- 迁移过程中若发现某段注释解释的是**历史**而非当前结果，按 `docs/agents/doc-style.md` 处置，不要原样搬运。
