# 任务是身份，运行才是一行

状态：已裁决，尚未实施（2026-09-06）。

**任务**在库里是一个身份——由类型、**作用域**、作用域 id 与**变体**四项唯一确定，
行上只有身份与它的长期属性（是否禁用、上次成功、连败次数、**退避**到什么时候）。
**运行**才是一行一次：自增主键、外键指回任务、带**发起方**与第几次尝试。
「同一个任务同时只能有一次活动运行、外加最多一次排队中的运行」由两条部分唯一索引保证，
而不再由内存表判定。**重试**因此是同一个任务的新一次运行，上一次原样留着。

改这一层是因为旧模型把**任务键**当主键、写入走 upsert：一个任务键在库里永远只有一行。
于是重试当场抹掉被重试的那次记录，同一个库的两次扫描无从对比，而**运行事件**、**采样**、
逐次的指标根本没有地方可挂——**可观测性**的每一条都卡在这里。词汇表其实一直是对的
（**任务**是身份，一次执行是**运行**），错的只是存储层把它压成了一对一。

## 落盘不留 JSON 堆

旧表 16 列之外的一切都编码进一个 `params` TEXT：展示态、累计指标、并发上限、i18n 占位参数、
以及**重启函数**要读回的原始入参——五类语义挤在一个命名空间里，靠一对手工配对的编解码函数
维持，注释自己写着「只加一侧不会有编译错误」。新形状把它们拆到各自的表与列上：
指标进 `run_metrics` 因此可查询可聚合（「这个库最近十次扫描平均多久」是一句 SQL），
上限进 `run_limits`，入参进 `run_args`，展示态升为 `runs` 的真列。

代价是新增一个上限字段要改 schema，而不是往 map 里塞一个键。这是明知的交换：
那批字段本来就是有限且稳定的，而「往 map 里塞」正是今天指标不可查询的原因。

## 考虑过并否掉的

**只加一张历史归档表**（主表继续一键一行，终态时复制一份进历史）。它改动小，但「当前」与
「历史」两份形状要各自维护，同一个任务的数据来自两张表，而列表要把两边合起来排序——
今天内存表与 DB 合并那套复杂度会再来一遍。

**不动模型、只补可观测性**（日志带 run_id、阶段时间线、失败明细）。它治不了「重试后原记录
当场消失」，也没有承载多次运行的地方。

## 为什么记下来

`runs` 按 `task_id` 外键、而 `tasks` 行上没有任何状态快照，读起来像是白白多了一次 join——
一张表明明装得下。会这样想的人看到的是稳态，看不到的是：这两张表回答的是两个不同的问题，
一个是「这活该不该继续自动跑」，另一个是「上礼拜三那次跑成什么样」。
