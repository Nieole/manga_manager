# 扫描观察者活得比扫描调用久，不设撤销机制

**扫描观察者**由调用方在发起扫描时交出，它的寿命**超出**那次调用：封面生成是异步的，
`ScanLibrary` 返回后，封面队列仍会经同一个观察者推进 `generated_covers`。

因此不要给它加「扫描返回即撤销」的语义——那看起来是显然正确的收尾（谁交出去的谁收回来，
与**运行时句柄**的 release 对称），但它会打断缩略图重建：该任务在全部资料库扫完之后才
`WaitForCoverQueue`，那一段等待期间界面上唯一还在动的就是封面计数，而那些帧全部来自
已经返回的扫描调用。撤销观察者会让进度条在最后一段彻底静止，且用户无从判断它是在工作还是卡住。

## 为什么记下来

2026-08 把扫描进度的接缝从装配期挪到调用点时，中途确实提过一次「观察者应当随调用结束而失效」。
它有很强的表面正确性：接缝搬到调用点之后，寿命跟着调用走是最自然的读法；而且不加撤销就意味着
一个已经返回的调用仍能写调用方的状态，看起来像泄漏。拦下它的是上述那个事实，而这个事实
不在扫描器这一侧——要走到缩略图重建的任务体里才看得见。没有这条记录，下一次评审会再提一次。

## 附带结论

扫描任务这一侧不需要撤销：任务体收尾后，迟到的封面帧由任务引擎既有的终态守卫丢弃
（`applyTaskProgress` 对非**活动态**任务一律忽略）。也就是说「谁来挡住迟到的帧」这个问题
已经有归属，不该在扫描器里再答一遍。
