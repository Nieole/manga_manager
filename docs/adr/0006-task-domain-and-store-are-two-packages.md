# 任务子域拆成领域包与落盘包

状态：已裁决，尚未实施（2026-09-06）。

任务子域拆成两个包：`internal/task` 放**任务**与**运行**的领域模型、状态机、队列与槽位、
**退避**、保留裁剪，它**不知道 SQL**；`internal/taskstore` 放表结构与查询。
`internal/api` 只剩 HTTP handler 与装配，**重启函数**继续在装配期注册（沿用 ADR 0001）。

在此之前整个子域住在 `internal/api`：任务引擎、启动仪式、模型转换与 HTTP 层合计约 1950 行，
与另外六十来个 handler 文件同居一个包，而 AGENTS.md 的规矩是「handlers 要薄，逻辑推进
`internal/*`」。这次要往里加的东西——排队与槽位、退避、分层保留、**运行事件**与**采样**的
写入——只会让它更重。

## 这与仓内其余子域的写法不一致

`proposal`、`koreader` 都是「单包 + `database.Store` 接口」，包里既有领域也有查询。
按那个惯例，这里应该只开 `internal/task` 一个包。选两包多出一层 DTO 与一层接口，
换来的是领域层可以纯内存测试——状态机、排队与合并、退避曲线、保留裁剪这几样的正确性
都只与规则有关，与 SQLite 无关，而它们恰恰是这次新增的、最需要被密集测试的部分。

代价是明知的：多一层转换，且这个仓库里从此有两种子域写法。

## 为什么记下来

「把 `taskstore` 合回 `task`」和「让 `task` 直接依赖 `database.Store`」都会显得像是在
拨乱反正——它们让这个子域与 `proposal`、`koreader` 一致，而一致性通常是对的。
合并本身不难，难的是合并之后领域层的测试会重新长出一个 SQLite 依赖，
而那批测试正是这次拆包想换来的东西。
