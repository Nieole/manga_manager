# 凡动磁盘的后台工作都建运行，准入闸门只留一处

状态：已实施（2026-09-06）。定时守护扫描、监听器派生的扫描与清理、建库后的首扫都已建**运行**
并标出**发起方**，`scanner.ErrScanAlreadyRunning` 已删除，准入只剩任务那一处；封面生成是每库
一条**串联**发起的运行，作业自带它属于哪一次运行，扫描在归档处理完就完成。

定时守护扫描、watcher 派生的扫描与清理、建库后的首扫、异步的封面生成，都要各自建一次
**运行**，并在**发起方**上标出是谁叫来的（手动 / 定时 / 监听 / 串联 / 恢复）。
毫秒级的内存活（作品群重建、仪表板统计预热）不建。

在此之前这几条路径一律交出 nil **扫描观察者**，不留任何痕迹：用户半夜听见硬盘响、机器变卡，
任务中心一片空白，而且**没有任何东西可以暂停或取消**。这不是疏漏而是当时的设计，
词汇表里甚至把它写成了既定事实——所以要改，得先把那句话改掉。

同一条决定连带删掉 `scanner.ErrScanAlreadyRunning`。此前系统有两套互不知情的准入闸门：
引擎按**任务键**判，扫描器按扫描目标判。两者判据不同，靠后者兜住守护扫描与手动扫描撞车。
自动扫描也建运行之后，同一件事有两处能拒绝它，而它们对「什么叫已经在跑」的答案不一样。
合并之后准入只剩任务这一处，且由 DB 的部分唯一索引兜底（见 ADR 0004）。

## 冲突不再靠丢弃

闸门只剩一处之后，撞车的处理从「静默跳过、等下一个 tick」改成排队：同一个任务已有活动运行时
后来者进**排队中**；已经有一条排队的，再来的**合并**进那一条并计数。守护扫描要的只是
「确保扫过」，合并与各排一条效果相同，而后者会堆成一串一模一样的运行。

槽位按**单一全局数字**限（默认 2，设置可改），而不是按 `storageio` 已有的卷键限。
按卷限更贴近真实瓶颈——两个库在两块盘上本可以并行——但一个数字更好解释、界面上也画得出
「槽位 2/2」。这是知情的取舍：多盘用户会看到一条运行在排队，而它要等的那块盘是空的。

## 封面帧走封面自己的通道

封面作业在入队时就带上「它属于哪一次运行」，报文因此直接写进那条封面运行，
**扫描观察者**只管扫描本身。这与此前把扫描进度的接缝从装配期挪到调用点是同一个思路：
让报文自带去处，而不是让接收侧靠一张带锁的侧表按身份反查。

一次扫描排出去的封面收成**一批**，交给那个库的封面运行去跑：那条运行把批里的作业逐个派进
共享的 worker 池，因此**运行槽位**与**暂停闸门**都拦得住它——还没轮到的封面运行一张都不会
开始生成。全局的封面等待计数随之改成按批计数：要回答的问题是「我这一批还剩几张」，
而两个库的封面在同一个池里交错推进。

批与运行**在运行开跑时才配对**，不在发起时绑定。发起与开跑之间隔着队列：槽位满或这个库已经
有一条封面运行时，本次发起只落成一条排队中，甚至被合并进已经排着的那一条——挂在某一次发起上，
被合并掉的那次就把这一批带进了坟墓，那个库的封面从此静默不再生成。

代价是 ADR 0002 被本文取代：它当时判定观察者不设撤销机制，理由正是「封面帧还要经它推进」，
而那个前提到此为止。缩略图重建也不再需要把归档处理与封面生成拼成一个分母来避免过早 100%——
它的第二阶段从此是另一条运行。

## 为什么记下来

删掉一个包内自洽的 already-running 守卫，看起来像是把 `scanner` 的健壮性拆了——
它是那个包对「同一个库被扫两遍」的唯一防线，而防御性检查通常没人反对。
再加回去的代价不是多一次检查，而是「什么叫已经在跑」重新有了两个答案，
且只有在守护扫描与手动扫描恰好撞上时才看得出来它们不一致。

同理，「守护扫描不该占用户的任务列表」听起来也很有道理。它成立的前提是任务列表只给
用户自己发起的活看——而这次恰恰是把那个前提推翻了：用户要回答的问题是「我的盘现在在干什么」，
不是「我刚才点了什么」。淹没的问题由界面结构解决（实况区置顶、清单按任务折叠），
不靠不记录来解决。
