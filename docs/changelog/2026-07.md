# 2026-07

### 📌 增量记录 — 2026-07-29（扫描器边界 · 审核状态机）

#### 扫描与文件监听
- **尊重库级 `scan_formats`**：该字段前后端俱全（设置页可勾选 cbz/cbr/zip/rar），但扫描器与 watcher 一直用的是全局白名单——用户勾了「只扫 cbz」，rar/zip 照样被打开入库。新增 `LibraryScanOptions.IgnoreFormatFilter`：格式过滤的语义是「导入哪些文件」，不该殃及已入库的内容，因此重建缩略图这类维护扫描必须看得见全部书籍，否则被排除格式的书会永久失去封面。新增 `format_filtered_archives` 指标，静默少扫变得可见。
- **修复 watcher 的兄弟目录串台**：此前用无分隔符的 `strings.HasPrefix` 判断事件属于哪个库，`/data/manga2` 的事件会被判成属于 `/data/manga`；两处匹配又都是「第一个命中就 break」，而 Go 的 map 迭代顺序随机，所以受害的是哪个库每次都不一样。改用 `filepath.Rel`（Windows 另做大小写归一），并改为对**所有**包含该路径的库排期（嵌套库共享子树）。
- **watcher 派生的扫描/清理纳入停机管辖**：此前用 `context.Background()` + 裸 goroutine，既不可取消也不被优雅关闭追踪，`srv.Shutdown` 返回之后它们仍在往一个即将关掉的 store 里写。`Stop()` 现在取消并等待它们退出；`CleanupLibrary` 补三处取消早退。
- **递归注册遇错继续**：`watchRecursive` 此前首个错误就中止整棵 `WalkDir`，一个不可读的子目录会让它之后的整片子树静默失监。现在返回 `WatchReport` 分项记账，inotify 配额触顶（ENOSPC）单独标记。另修一处：旧代码先登记再 `Add`、失败才删，而 `exists` 短路一旦命中就永久跳过——现在改为 Add 成功之后才登记。
- **支持符号链接**：把外置盘上的系列目录软链进库根（多盘位 NAS 的常见组织方式）此前整棵被跳过，用户只看到「扫描完成，0 本新增」；软链的归档文件又用 lstat 取 size/mtime，而链接自身的 mtime 只在重建链接时才变，导致目标被替换后增量扫描永远判定「毫无变化」。新增 `walkDirFollowingSymlinks`（扫描器与 watcher 共用）：报出的路径改写回链接一侧，按解析后的真实路径防环，两个链接指向同一目录时只遍历一次。
- **整文件哈希可取消**：新增 `koreader.FingerprintFileContext`。一本几 GB 的归档读完要几十秒，此前期间取消信号完全传不进来。

#### 元数据审核
- **补齐 reject 的 pending 守卫，并把守卫下沉到 SQL**：四条终态推进路径里只有单条 reject 漏了检查，于是一条已 applied 的审核可以被改成 rejected；而 SQL 里 `applied_at`/`rejected_at` 是「CASE … ELSE 保留旧值」的累加写法，结果是同一行同时带两个终态时间戳，`series_metadata_provenance` 还指着它——审计链变成「系列的元数据来自一条已被拒绝的审核」。守卫改为 `ResolvePendingMetadataReview` 的 `AND lower(status) = 'pending'`，影响行数为 0 即冲突，同时堵住了「HTTP 层读到 pending → 写入」之间的 TOCTOU 窗口。**对外行为变更**：重复 reject / 对终态 review 操作由 200 变为 **409**。
- **删除死列 `metadata_review_fields.status`**：唯一写入点硬编码 `'pending'`，全仓无 UPDATE/DELETE，且两条把字段送到前端的读路径都只查 pending review——写进别的值也永远读不出来。字段级的应用结果本就由 `series_metadata_provenance` 承担，留着只会成为第二真相源。迁移里以 `PRAGMA table_info` 探测后 `DROP COLUMN`（本身不幂等），API 响应 `fields[]` 随之少一个恒为 `"pending"` 的 key。**升级后不可回滚到本版之前的二进制**（旧版 SELECT/INSERT 显式带该列）。

- **部分应用不再让提案永久消失**：bulk-apply 的默认 `fill_empty` 模式只写「当前值为空」的字段，却把**整条**审核标成已应用，而收件箱只查 pending——被筛掉的提案从此在界面上彻底消失，用户想应用它只能重新刮削一遍。单条 apply 遇到部分锁定字段时同理。现在只有全部提案都处理完才关单；否则删掉已写入的字段行，让审核带着剩下的提案继续待处理。删行而非留着，是因为已应用字段的 `current_value` 已经过时，留下会在收件箱里陈列一个「当前值 == 提案值」的假差异。批量响应新增 `partial` 桶（与 `applied` 分开：这些条目还留在收件箱里）。
- **锁定字段不再入队与静默丢弃**：字段锁的语义是「这个值我手动定过，别让刮削覆盖」，但此前它只在写入的最后一步生效。锁定字段照样入队为待审提案，用户点「应用」后被静默跳过，整条审核却算已应用。现在入队侧直接跳过；展示侧的锁徽章改为按**当前** `locked_fields` 判定（行上那个是入队瞬间的快照，「先入队、后加锁」的字段在界面上没有任何标记）；应用侧全被锁时明确报「差异字段均已锁定」且**不消费**该审核。
- **良性结果不再报 500**：「差异字段均已锁定」与「无变更」此前一律返回 HTTP 500，用户看到的是「服务器错误」。现在返回 200 + `applied:false` + 具体 `outcome`，批量侧从 `failed` 改落 `skipped`。
- **接上未匹配 KOReader 计数**：`/api/reviews/inbox/summary` 的 `koreader_unmatched` 恒为 0，导致设置页显示「未匹配 N 条」而审核中心显示 0。只按 KOReader 是否启用门控（与健康报告同口径），且**刻意不并入 `total`**——它没有逐条 apply/reject 的状态机，混进去会让首页的待审核横幅常亮且点进去无事可做。

- **被拒绝的提案不再被反复塞回队列**：入队去重此前只跟 pending 记录比。用户拒掉一条之后，下一次刮削（尤其是定时的全库刮削）会把逐字相同的东西原样再塞回来——「拒绝」这个动作实际不产生任何持久效果。现在会再跟最近 20 条拒绝记录比一遍，命中时返回 `rejected_before`。同时提供 `?force=1` 出口：没有它，误拒一次就是死胡同，同一份数据再也进不来。刮削的三种「良性跳过」（无变更 / 差异全被锁 / 此前已拒绝）在后台批量任务里也不再计入失败，否则一次完全正常的全库刮削会在任务面板上报出一片红。
- **AI 分组审核列表消掉两层 N+1**：每页 30 条审核，此前逐条查候选合集（30 次），再对每个候选合集逐个查系列名（30 × 合集数，实测 150+ 次单行查询）。改为一次批量取全部候选合集 + 一次批量取涉及的所有系列名。更要紧的是那两处查询的错误此前被 `_` 吞掉：DB 故障时接口照样返回 200 且候选合集全空，用户会以为 AI 一个分组都没分出来，现在改为 500。

#### KOReader
- **自助注册的设备账号不再被错误归属到管理员**：设备自助注册没有站点用户上下文，此前一律把新账号绑到 id 最小的管理员。多用户站点里这是纯粹的错误归属——普通用户拿设备注册之后，同步进度会顺着账户的 `user_id` 写进**管理员**的 `user_book_progress` 与 `user_reading_activity`（连热力图和连续天数都算进去），而他自己账号下的进度全丢。现在只有单用户站点（唯一用户即唯一可能的归属，猜测无歧义）才自动归属，多用户站点留 `user_id=0`（进度回落全局），由管理员在设置里显式指派。**行为变更**：多用户站点新注册的 KOReader 设备在被指派之前，其进度不计入任何用户。
  - 注意这次只修掉了「错误归属」，没有改变自助注册端点本身的开放性：`koreader.allow_registration` 打开后仍是未鉴权可注册，单用户站点的行为与修复前一致。把自助注册改成「需管理员批准」是另一件事，未在本次范围内。

#### 外部库传输
- **传输改为原子落盘**：此前直接往目标路径写。目的地通常是 USB/SD 外接盘，单本几百 MB、整个系列跑几十分钟——进程被强杀或外接盘中途掉线就会留下一个截断的 `.cbz`。而后续两处「已存在」的判定都只看路径不看内容，于是这本坏书在阅读器上永远打不开，**重传多少次都会被当成「已经有了」而跳过**。现在先写同目录临时文件、Sync 之后再 `os.Rename`，失败时清理临时文件。临时文件名与源文件名无关（漫画文件名最容易逼近 NAME_MAX，中文名 UTF-8 每字 3 字节只够约 85 字，把原名嵌进去会让一批今天能正常传输的书直接报「文件名过长」）。
  - 注意：本次只阻止**新的**截断文件产生，用户盘上**已经存在**的坏书不会被自愈——需要手动删除后重传。

#### KOReader 设备诊断
- **冲突列表的 `id` 不再是语义二义的裸整数**：该列表是 `koreader_progress` 与 `koreader_sync_events` 的 UNION，两张表各有独立自增序列、都从 1 开始，同一个 id 同时是两边的合法主键。前端把它当进度主键传给「重置进度」，删掉的是**另一台设备的阅读进度**。现在 `id` 改为 `"<来源表>:<主键>"` 的复合标识（只用于列表 key），另给 `source_table` 与 `progress_id`——后者只在这一行确实对应一条进度记录时才有值，「重置进度」只能用它。
  - 注意：重置端点本身仍是「按任意整数无条件删」，没有归属校验。本次只是让接口不再下发会被误传的 id，删错的能力本身还在。
- **身份索引回填不再顶起 `books.updated_at`**：`file_hash` / `quick_hash` / `path_fingerprint*` 是 KOReader 匹配用的内部索引，不构成「这本书变了」。此前无条件刷新，于是一次「重建 KOReader 索引」把整库的 `updated_at` 推到同一秒——三条健康报告查询的 `ORDER BY b.updated_at DESC` 第一排序键全部相等、退化成按 id，前端封面 URL 上的 `?v=updated_at` 也整库失效（等于让所有人重下一遍全部封面）。同时给 UPDATE 加了「真的有变化才写」的守卫。**语义收窄**：`books.updated_at` 从此只表示书籍内容/元数据的变更。存量已被历史回填推平的值不可回溯，也不做迁移回填（没有数据源）。
- 前端封面 URL 去掉 `?v=book.updated_at` 的兜底（显式重建封面后的 `coverBust` 保留）：常规刷新交给 HTTP 缓存，封面端点本就是 `must-revalidate` + 弱 ETag。

#### 外部库鉴权与路径范围
- **会话读接口收为管理员专属**：外部库传输本身是管理员功能，POST 因为是改写方法一直被挡着，而 GET 落进「读方法一律放行」分支——任意已登录的普通账号都能拿到会话快照，里面带着服务器上的**绝对路径**（`external_path` 与 `library_path`）。读写鉴权不对称正是这条缺陷的形状。前端也相应对普通用户隐藏外部库入口（否则点进去只会吃 403）。
- **外部路径不再接受相对路径与库内路径**：`external_path` 此前传什么存什么。相对路径（`.`）被静默解释成**服务进程的工作目录**——用户以为传到了外接盘，实际写进了服务的运行目录；`/` 会让扫描去遍历整个文件系统；指向资料库自己的子目录时，传输产生的副本会被下一次扫描收编成重复书籍。判定刻意放过 Windows 的卷根（`D:\`、`\\server\share\`）：「整块外接盘 / NAS 根目录当外部库」是这个功能的头号用法，误杀它才是回归。
- **传输规划不再跑两遍、不再 N+1、不再重复规划同一个系列**：HTTP 层为了决定回 200 还是 202 会先完整规划一次，算完整个丢掉，后台任务再用同一份入参重算一遍；规划内部又是逐系列一次 `SELECT *`（books 表 24 列、含 summary 长文本），选几百个系列就是几百次往返再乘以 2。现在规划只跑一次并把结果交给后台任务，书籍查询改为一次批量取齐。`series_ids` 同时补上去重与 2000 的数量上限——此前 `[7,7]` 会把系列 7 的每本书规划两遍，用户看到的 `missing_books` 翻倍、任务进度条分母也是错的，同一个源文件还会被拷两次到同一目标。
  - 重叠判定目前只挡**本库**：`external_path` 指向另一个资料库根时后果一样，但那需要拉全部库列表，留作后续。

#### 前端体验与可访问性
- **设置页「保存本分区」不再顺手提交其他分区的草稿**：保存动作此前直接把整份 config state 发给后端，而那份 state 里带着用户在其他分区改了却没保存的内容——点一下「保存媒体设置」，把没打算提交的 AI 密钥、扫描并发数一起写了进去，界面上没有任何提示。现在以服务端最近一次下发的配置为底，只叠加本分区的字段；保存后的刷新同样只覆盖本分区（否则会反过来把别处的草稿静默抹掉）。协议开关（连接页）此前是同一个根因的另一处，一并收进同一套语义。
- **补齐前端角色门禁**：资料库的增删改、扫描、AI 分组与系统设置在后端都是管理员专属，前端却照样把入口渲染出来——普通用户点了只会吃 403 加一句泛化的失败提示，像系统坏了而不是没权限。五处入口加门禁，并给设置页加路由级守卫（隐藏入口挡不住直接输 URL 或旧书签）。
- **共享弹窗补焦点管理与陷阱**：全站弹窗都套在同一个壳上。此前有 `role="dialog"` 与 `aria-modal` 但没有任何焦点管理：打开时焦点留在背景里、Tab 会走出弹窗落到背后被遮住却仍可点击的链接上、关闭后焦点回到页面开头。Toast 补 `role="status"` + `aria-live="polite"`（容器恒定渲染，否则读屏软件会漏读第一条）。
- **换人时清理离线残留**：清理此前只挂在显式登出上，而登出恰恰是共享设备上最少发生的换人路径。登录、刷新、会话过期三条都不经过它，于是新用户打开任意阅读器页面就会把上一个人排队的进度同步进自己账号。离线书目索引也一并清——Service Worker 断网时直接从缓存命中，不经任何服务端鉴权。
- **活跃热力图不再错行**：日期串用 UTC、行位置却用本地星期几，本地时刻跨过 UTC 日界时整张网格相对星期标签统一错开一行。
- **刮削源列表不再被一次瞬时错误永久毒化**：失败结果此前被缓存成空数组，一次网络抖动就让整个会话的刮削菜单永远为空。
- 日志页性能看板的 7 处中文硬编码接上 i18n。

#### 前端架构
- **抽出 `useLibraryForm`**：「新增资料库」与「编辑资料库」此前是两套完全平行的实现（各七八个 state、各一份逐字段 setter 与手拼的提交载荷）。两套代码做同一件事，代价是漂移——给表单加字段时很容易只改一边。`Layout.tsx` 1013 → 993 行、`useState` 37 → 23 个。重构前把现有行为列成 12 条基准逐条核对，其中 4 条是两条路**本来就该不同**、最容易在「统一」时被合掉的（新增重置表单而编辑不重置、只有新增拨 refreshTrigger、编辑的格式回落到后端支持集合、失败文案不同）。
- **离线下载中途失败后这本书仍出现在离线书架上**：书目索引此前是整个下载循环跑完之后才写的，下到一半断网时那几百页留在缓存里、界面上却看不到这本书，用户没有入口删除它（只能「清空全部」，连带删掉别的书）。改为先登记再下载。
- 补齐 Service Worker 与页图缓存的测试：前者守「哪些请求断网时还能读」以及**激活时的旧缓存清理不能碰离线书缓存**（漏掉这一条，一次版本升级会把所有用户已下载的书删光）；后者守 Object URL 的释放（不显式 revoke 就不会被回收，整本书读下来能积几百 MB 且全程无报错）。

> 资料库网格的虚拟化经评估**暂不实施**：`react-virtuoso` 的 `endReached` 在同一 `totalCount` 下只触发一次，把「是否该加载下一页」的判定搬进它的回调会让任何一次被挡掉的触发永久丢失、无限滚动就此停住；而现行的 IntersectionObserver 实现每次重渲染都会重建观察器，被挡掉的触发总会重试。另外卡片高度并不统一（简介块是条件渲染），而网格虚拟化假定项目等高。两条都需要先改动别的东西才谈得上虚拟化，不适合夹在本批里做。

#### 后端架构
- **franchise 合集改用稳定自然键**：这条重建路径在**每次**新增/删除/修改系列关系时都会跑一遍，而它此前是「整体删掉再全部重建」——用户加一条关系，所有 franchise 合集就换一遍 id。而合集 id 是对外暴露的：`/mihon/collections/{id}/series` 与 `/opds/collections/{id}` 都按它取数，外部阅读器书库里记下的条目会集体失效。合集**名**同样不稳定：它取自连通分量的「第一个」成员，而那个第一个来自 Go 的 map 随机迭代——同一批关系每次重建都可能算出不同的名字。现在按「连通分量的最小系列 id」做稳定键 upsert + 成员差集增删。
  - ⚠️ **升级后首次重建会让现有 franchise 合集的链接失效一次**：存量行没有键，会被换成带键的新行（id 变化）。这是一次性的，之后就稳定了。如果你在 Mihon/OPDS 客户端里按 id 收藏过 franchise 合集，或在站内存了合集链接，需要重新添加一次。手工创建的合集完全不受影响。
  - 键在「有更大 id 的系列加入」「关系类型变化」这些常见改动下都不变；只有一个 id 更小的系列并进来时才换键——那种情况下两个 franchise 实际发生了合并，换 id 是诚实的。
  - 已知遗留（本次未改）：扫描清理删除系列时会经外键级联改变 franchise 图，但**不会**触发重建，于是可能留下一个只剩单个成员的空壳合集，一直挂到下一次有人改系列关系或手动重建。

### 📌 增量记录 — 2026-07-16（性能：修复 RAR/CBR 整卷阅读 O(N²)）

> 落实第 3 批曾因「本环境无法生成多页 RAR 夹具」而暂缓的 RAR O(N²) 项。现已提交由 `rar` 生成的二进制夹具（CI 用纯 Go 的 rardecode 只读、无需任何 rar 工具），实现会话缓存并配套回归测试与基准。

#### 优化
- **RAR/CBR 会话缓存**：`rar.go` 的 `RarArchive` 引入随读取前滚的持久游标 + 有界 FIFO 字节缓存。此前每次 `ReadPage` 都重开归档并从头 `rr.Next()` 顺序查找目标页（RAR 是前向只读流、无法 seek），整卷阅读退化为 **O(N²)**，且 `Close()` 是 no-op 使归档池对 RAR 毫无收益。现在途经页的字节被缓存、后续翻页命中即 O(1)；只有反向跳读到已被淘汰的页才重开——整卷顺序阅读降到 **O(N)**。游标 / 缓存由互斥保护，池内共享的同一归档可安全并发读取（同档读取串行化，与 RAR 顺序解码本就一致）。`Close()` 现在真正关闭游标并释放缓存。
- 缓存按字节上限（默认 64 MiB/档）FIFO 淘汰，覆盖顺序阅读的滑动窗口；单页超限时兜底最多超出一页。
