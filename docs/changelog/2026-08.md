# 2026-08

### 📌 增量记录 — 2026-08-17（扫描进度改由调用方接住）

> 扫描器此前在装配期注册一个进程级的进度回调，对此后每一次扫描生效，因此每份报文都要自带
> 作用域与 id，再由 api 层查一张侧表反查回它所属的任务。现在进度与指标的接收器随每次扫描调用
> 传入：报文不再带身份，「这次扫描的进度写给谁」由发起方交出的那个**扫描观察者**回答。
> 无归属的扫描（守护扫描、watcher 派生的扫描、建库后的首扫）交出一个空值，与此前「侧表里查不到」
> 是同一个语义。
>
> 数据库结构、SSE 契约与任务快照的落盘结构均未改动。

#### 修复
- **缩略图重建的「已完成 N / 总数」少报一个库。** 扫完两个库中的第一个时显示的是「已完成 0 / 2」，
  最后一个库扫完时显示「已完成 1 / 2」——这个计数此前来自库切换的通知，而定版一个库的指标发生在
  切到下一个库**之前**。现在它就是「已定版的库数」，不再有第二个来源。
- **缩略图重建每扫完一个库会闪一帧错的进度。** 那一帧写着「正在重建 *刚刚扫完的那个库*，
  第 N+2 / 总数」——库名是上一个、序号多算了一个，最后一个库时会显示成「第 3 / 2」。
  它此前立刻被下一个库的那帧盖掉，只有最后一个库那次会停留到进入等待封面队列的阶段。
  库切换现在只有一处通知，这一帧随之消失。

> 后台**任务**的启动、进度上报与收尾此前由 17 个启动点各自手抄同一套五步流程（申请槽位 → 写元数据
> → 写并发上限 → 建可取消可暂停的上下文 → 起后台 goroutine 并在其中手写三条收尾分支），正确性完全
> 依赖「抄对」。本批把这套仪式整个收进任务引擎：调用方提交一份任务声明和一个任务体，其余全部由引擎
> 承担。17 个启动点逐个转换完毕，老接口在同一批里删除。
>
> 数据库结构、SSE 契约与任务快照的落盘结构均未改动。

#### 修复
- **三个维护任务 panic 后会永远卡在「运行中」，只能重启进程才能恢复。** 缩略图清理、文件身份重建、
  低优先级哈希回填此前直接开裸 goroutine，没有 panic 兜底：任务体一崩就走不到任何收尾，而活动任务
  既不被淘汰、也不被清空任务列表删除。三者此后的表现各不相同——
  - **缩略图清理**与**文件身份重建**：那个**任务键**从此恒定返回「同类任务已在运行」，
    用户点按钮再无反应。
  - **低优先级哈希回填**没有按钮可点（它由扫描任务体在收尾时串联发起），表现是此后每次扫描收尾的
    自动哈希回填**静默不再发起**，任务中心多一条永远运行中的幽灵任务；而且它归还任务上下文的那次
    调用写在任务体之后而非 `defer`，panic 时句柄反而留着，用户点一次取消就会让它永远停在「取消中」。

  现在三者都经引擎的统一入口启动，panic 一律转成一次显式失败。
- **失败的任务不再带着「暂停原因」进终态。** 暂停中失败的任务此前保留 `pause_reason`，
  任务中心把它渲染成一行「暂停原因：手动暂停」——一条自称手动暂停的失败任务。
- **索引重建在关服时会留下一条「失败」。** 此前关服取消它时落的是失败**终态**、文案却写着「已取消」
  ——状态与文案自相矛盾。现在由引擎按任务体返回的错误裁决，落**已取消**。
- **缩略图重建在「清空封面索引」这一步被取消时显示为失败。** 用户按下取消，看到的是一条红色的
  「清空封面索引失败」。现在专属失败文案让位给取消，落**已取消**。
- **已经结束的扫描任务还会继续变动。** 资料库扫描、系列扫描与缩略图重建进入**终态**之后，迟到的
  扫描器报文仍会改写它们的进度与参数（封面队列在扫描主流程收尾后仍会上报），任务面板上一条已完成的
  任务会自己动起来。同一处还修掉：重建缩略图期间并发的系列扫描会把自己的指标并进重建任务，把它的
  指标和进度条分母一起抬高。现在进度写入资格由「有没有拿到这个任务的进度句柄」决定，写入者拿不到
  句柄就是无操作。

#### 任务文案的本地化
> 后端与扫描器不再渲染任何面向用户的文字，一律只下发 i18n 键与占位参数。以下几处此前是硬编码，
> 英文用户在任务中心看到的是中文。

- **ComicInfo 回写**：起始、逐条目与**完成**三处文案改为按语种渲染（完成那句此前由后端拼成
  「已写入 N 本，跳过 N 本，失败 N 本」，翻译不了），三个计数改走占位参数。逐条目进度期间显示的
  也不再一直是启动时那句话——此前每条进度带的文案是空串，整个回写过程界面上都停在启动文案上。
- **ComicInfo 回写被取消时**显示本任务专属的已取消文案，此前显示的是通用的「正在取消任务...」
  ——一条**终态**在说自己正在取消。
- **ComicInfo 回写在任务中心的任务类型标签与阶段名**不再显示成裸文案键。这两个键此前两个语种都缺，
  不补的话上面那条「英文用户不再看到中文」会变成「英文用户改看到 `task.type.write_comicinfo`」。
- **索引重建的失败与取消文案**改为按语种渲染（此前对所有用户固定为英文），且失败提示不再把技术
  错误串拼进展示文案——错误详情走单独的通道，展示文案保持可翻译。
- **缩略图清理的逐条目进度文案**与**外部库扫描的逐条目进度文案**改为按语种渲染（此前对所有用户
  固定为中文）。两句硬编码中文从扫描器与外部库会话管理器里删除。
- **任务体崩溃时的失败提示**改为按语种渲染。此前引擎在 panic 兜底里下发一句硬编码英文
  「Background task panicked」，没有任何地方能翻译它。panic 值本身仍单独走错误详情那条通道。

#### 外部库扫描与传输
- **进度推送变密**：这两条路径的任务体里手写的 500ms 节流删除（扫描一处、传输两处，共三处），
  改由引擎统一的 200ms 水位承担。
  - 这是**量**的改善不是质的：水位比对的是状态、阶段与文案，不比对当前条目，因此一本几百 MB 的书
    的开工帧若落进 200ms 窗口内仍会被吞，气泡在拷贝那几分钟里还是停在上一本书上。要兑现成质的
    改善得改水位的判定规则，那是另一件事。
- **传输的逐条目文案不再逐本来回切换**。此前每传一本书报两次、两句文案交替出现（「正在传输 X」与
  「已传输 k / N 本资源」）。现在逐条目只在拷贝之前报一帧，统一为「正在传输 X」；计数那句移到
  收尾帧——拷一本书要几分钟，那几分钟里用户需要看到的是正在传哪一本，而进度条本就在报计数。
  - 合成一帧不只是为了好看：引擎的水位把文案也算进展示态，两个文案码逐本交替就等于每帧都判
    「变了」而放行。照搬两句文案会让这条路径失去节流，而一次传输最多 2000 个系列，全部命中
    「目标已存在」时循环两次系统调用就过一本——那样的投递量会触发 SSE 的背压（断开客户端连接）。
    老路径没有这个问题，因为它前面挡着自己那层 500ms 节流。

#### 架构
- **任务引擎对外只剩一个启动入口**：`taskEngine.Run(TaskSpec, 任务体)`。启动相关接口从约 25 个方法
  收到 9 个（启动入口 1 个，进度句柄 8 个方法加一个帧结构），17 处手抄的五步流程归零，25 处「以
  已取消终态收尾」的手写分支归零。
- **任务体只返回错误，由引擎裁决终态**。「取消」「失败」「**完成**」三条分支不再被手抄 17 遍；
  终态文案的默认值写在任务声明里，「部分成功」「第一阶段失败」这类变体由任务体在返回时指定，
  常规任务因此不必为收尾写任何代码。
- **「做完了多少」与「在做什么」拆成两个方法**，播报**阶段**不必再编造一个凑数的计数值，
  「别动总数」由「不设这个字段」表达，`-1` 哨兵值消失。
- **消息词汇只剩 i18n 码一种**，字面量文案那一整支接口删除。
- **进度写入资格从「谁会拼那个任务键字符串」变成「谁被交给了进度句柄」**。刮削任务体里此前出现
  8 次的那个任务键，现在一次都不出现。
- **后台 goroutine 的申领、停机登记与 panic 兜底由引擎统一完成**，「多套一层 goroutine 导致任务
  被静默丢弃」这类缺陷在结构上写不出来；**运行时句柄**的清理由引擎保证，不再依赖每个启动点手写。
- 新增此前无法覆盖的不变量的用例：任务体 panic 后必定置为失败态、任何退出路径上运行时句柄都被
  清理、同一任务键已有活动态任务时任务体一步都不执行。契约用例全部在引擎构造点这一个注入面上，
  不需要数据库、配置管理器与扫描器。
